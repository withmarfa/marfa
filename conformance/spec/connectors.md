# Connectors

The smallest door a process outside the server needs: it registers with a name and a description under the key it holds, heartbeats, and reports each run with its outcome, and the server lists what registered. No runtime, no supervision, no manifests: a reader decides what a stale heartbeat or a failed run means.

## Registration

1. `POST /connectors` with `{name, description?}` registers the caller's key as a connector and answers `201` with `{id, key_id, source, name, description, registered_at, updated_at, last_heartbeat_at, last_run}`, `source` being the key's; `last_heartbeat_at` and `last_run` are `null` until a heartbeat or a run arrives. A name outside 1 to 200 characters, or a description over 2000, answers `400 validation_error`. `compliance/connectors.test.ts › registers the key as a connector and lists it`, `› refuses a name or a description outside the bounds`.
2. One registration per key: the same key registering again updates the name and the description and answers `200` with the same `id`, its `updated_at` moved and its `registered_at` kept. `compliance/connectors.test.ts › registers once per key, updating on repeat`.
3. `GET /connectors` lists every registration to any key, the newest registration first, each with its `key_id`, the key's `source`, its `last_heartbeat_at` and its `last_run`; `GET /connectors/{id}` answers one, and an id no registration carries answers `404 connector_not_found` on it and on every door under it. `compliance/connectors.test.ts › registers the key as a connector and lists it`, `› answers 404 for an unknown connector, where a registered one answers`.
4. `DELETE /connectors/{id}` removes the registration, its runs, and its inbound webhook endpoints with every delivery they stored (`inbound-webhooks.md` 4), to the connector's own key or the operator key; another key is refused `403 forbidden` and the registration stands. `compliance/connectors.test.ts › removes a registration for its own key or the operator, never another`.
5. A registration outlives its key: revoking the key leaves the registration and its runs listed under the `key_id` they were written with, and the key's heartbeats answer `401 unauthorized` from then on, until the operator removes it. Nothing supervises a registration whose process can no longer reach it; what a stale heartbeat means is the reader's to decide. `compliance/connectors.test.ts › keeps a registration whose key was revoked, until the operator removes it`.

A session token an app holds is not a key: `POST /connectors` refuses it `403 forbidden`, because the token is renewed on every refresh and a registration keyed to one would be orphaned by the next, and the doors that admit the connector's own key alone refuse it the same way. The referee mints no session token, so it is not a statement here; `packages/server/src/routes/connectors.test.ts` proves both, beside the same token reading the listing. The same file proves that a key minted later under a revoked key's `source` is another key to statement 5's registration: a source is unique among live keys only, and the registration is the key's.

## Heartbeats and runs

6. `POST /connectors/{id}/heartbeat` from the connector's own key answers `200 {last_heartbeat_at}`, the server's clock, and the listing carries it; another key, the operator's included, is refused `403 forbidden` and the stamp does not move. `compliance/connectors.test.ts › takes a heartbeat from the connector's key alone`.
7. `POST /connectors/{id}/runs` with `{outcome, started_at, finished_at, summary?, error?}` from the connector's own key records a run and answers `201` with it, `reported_at` being the server's clock; `outcome` is `succeeded` or `failed` and anything else answers `400 validation_error`, as do a `started_at` or `finished_at` that is not a timestamp, a `finished_at` before `started_at`, and a `summary` or `error` over 2000 characters; another key, the operator's included, is refused `403 forbidden`. `compliance/connectors.test.ts › records a run from the connector's key and refuses an outcome it does not know`.
8. `GET /connectors/{id}/runs` lists a connector's own runs to any key, newest by `reported_at` first, `limit` at most 200 and 50 unless given, a `limit` outside that answering `400 validation_error`, and a page the `limit` cut answering a `next_cursor` that reaches the rest; the listing's `last_run` is the connector's newest by the same order. `compliance/connectors.test.ts › lists runs newest first and names the last on the registration`, `› keeps the last hundred runs`.
9. The server keeps the last 100 runs per connector: the 101st reported drops the oldest. `compliance/connectors.test.ts › keeps the last hundred runs`.
10. Every registration, first or repeat, and every removal write audit rows (`connector.register` carrying whether it created the row, `connector.delete`); heartbeats and runs do not. `compliance/connectors.test.ts › audits every registration and a removal, not a heartbeat or a run`.
11. `GET /` names `connectors` among its features. `compliance/instance.test.ts › describes itself at the root`.
