# Edges

A typed, directed relationship between two items, with its own id, properties and version.

## Creation and reading

1. `POST /edges` with `source_id`, `target_id` and `edge_type` answers `201` with `edge` carrying an id, the triple, `properties`, `created_at`, `updated_at` and `version: 1`. `correctness/edges/edges-crud.test.ts › edges CRUD` (one case per shipped edge type), `correctness/edges/edges-list.test.ts › reads an edge by id with its version`.
2. Each of the nine shipped edge types `about`, `parent-of`, `in-thread`, `attached-to`, `authored-by`, `derived-from`, `supersedes`, `references` and `in-collection` is creatable and lists at `GET /edge-types`. `in-collection` constrains its target by role rather than by type: the target must declare `container`, which the shipped `core.media.album`, `core.media.series` and `marfa.podcast.show` do, and so may any type a publisher registers. `correctness/edges/edges-crud.test.ts › edges CRUD` (one case per shipped edge type), `compliance/edge-types.test.ts › lists the shipped edge types and a registered one`.
3. A caller may mint the edge id; a repeat under the same id naming the same triple answers the stored row and announces nothing; an id naming a different triple is refused `409 id_reused`, with `details.differs` naming which of `source_id`, `target_id` and `edge_type` disagrees — the same code `POST /items` answers for a reused item id (`items.md` 3), because it is the same mistake: a caller minted an id and the id is taken by a row it is not describing. `sync/identity.test.ts › keeps the id a client mints for an edge`, `sync/acknowledged.test.ts › answers an edge repeat with the stored row and announces nothing`, `› refuses an edge id that names a different triple`.
4. A body missing `source_id` or `target_id` answers `400 missing_required_field`. `correctness/edges/edges-crud.test.ts › rejects POST /edges missing required fields`.
5. `GET /edges/{id}` returns the edge; an unknown id answers `404 edge_not_found`. `correctness/edges/edges-list.test.ts › reads an edge by id with its version`, `› refuses an unknown query key and an unknown edge id`.
6. `GET /edges` lists edges, narrowed by `edge_type` and `updated_after`, paginated by cursor, and refuses an unknown query key `400` naming it in `details.unknown_parameters`. `correctness/edges/edges-list.test.ts › lists edges by type, excluding other types`, `› bounds a listing by updated_after with an excluded control`, `› paginates with a cursor and delivers every edge once`, `› refuses an unknown query key and an unknown edge id`, `sync/time-filters.test.ts › narrows an edge listing by modification time`.
7. `GET /items/{id}/edges` lists an item's outbound edges and `GET /items/{id}/backrefs` its inbound ones, both narrowed by `edge_type` and paginated; an unknown item answers `404 item_not_found` and a malformed id `400 invalid_id`. `correctness/edges/edges-crud.test.ts › edges CRUD`, `correctness/edges/edges-response.test.ts › per-type hydration caps with has_more=true when over limit`, `› answers 404 for an unknown item and 400 for a malformed id`, `correctness/edges/edges-backrefs.test.ts › GET /items/:id/backrefs returns inbound edges`, `› ?edge_type filter narrows to one type`, `› paginates via cursor across many inbound edges`, `› answers 404 for an unknown item and 400 for a malformed id`.
8. `GET /items/{id}` hydrates edges keyed by type with at most 50 per type, `has_more` and a `next_cursor` when more exist. `correctness/edges/edges-response.test.ts › GET /items/:id returns hydrated edges keyed by edge_type with has_more`, `› per-type hydration caps with has_more=true when over limit`.
9. `GET /items?edge[<type>]=<id>` narrows a listing to items with that outbound edge, combinable with `type`; the full form `filter=edge[<type>] eq "<id>"` returns the same set. `correctness/edges/edges-query.test.ts › edge[about]=<id> shorthand returns items with outbound about edge to id`, `› filter=edge[X] eq "Y" full form returns the same set`, `› combines edge filter with type to narrow results`.

## Updating and deleting

10. `PATCH /edges/{id}` merges `properties` over the ones it was not given, advances the version, and announces `edge.updated`; a stale `version` is refused. `correctness/edges/edges-crud.test.ts › updateEdge patches properties only`, `› updateEdge merges over the properties it was not given`, `compliance/events-contract.test.ts › announces edge.updated when an edge's properties change`, `sync/edge-version.test.ts › refuses an update naming a stale version and accepts the current one`.
11. `DELETE /edges/{id}` removes the edge; later listings exclude it. `correctness/edges/edges-crud.test.ts › deleteEdge removes the edge; subsequent list excludes it`.
12. `POST /items` with `edges` creates the item and its edges in one write. `correctness/edges/edges-crud.test.ts › POST /items with edges creates item + edges atomically`.
13. `POST /edges/bulk` reports per-edge outcomes; `upsert` replaces properties on a duplicate triple, `create_only` reports `skipped` with reason `duplicate_edge`, `atomic` rolls the batch back on a refusal with `bulk_atomic_rollback` and no edge written, at the inner refusal's status — `403` where that refusal is a permission, `400` otherwise, as on the item door (`items.md` 31), and an unknown edge type lands as `errored` in non-atomic mode. `compliance/edges-bulk.test.ts › creates edges in bulk and returns per-edge outcomes`, `› upsert mode replaces properties in place on duplicate triples`, `› create_only surfaces duplicates as skipped with reason duplicate_edge`, `› atomic=true rolls back the whole batch on validation error`, `› atomic=true rolls back a batch naming an item that does not exist`, `› atomic=false collects errors and continues`, `› unknown edge_type lands as errored in non-atomic mode`.

## Cardinality and cycles

14. `parent-of` allows one parent per child at any depth; `in-thread` is many-to-one; `supersedes` is one-to-one on both ends; many-to-many types accept any number; a refusal is `400 edge_constraint_violation`. `correctness/edges/edges-cardinality.test.ts › parent-of is one-parent-per-child: second parent rejected`, `› in-thread is many-to-one: source can only join one thread`, `› supersedes is one-to-one: rejects second outbound from same source`, `› supersedes is one-to-one: rejects second inbound to same target`, `› many-to-many edge types accept multiple edges`, `› parent-of deep nesting respects the one-parent-per-child rule at depth`.
15. `parent-of` and `supersedes` refuse an edge that would close a cycle, direct or deep, with `400 edge_cycle`; a self-loop is refused `400 edge_cycle` on every edge type, cycle-prone or not, because one edge closes it. `correctness/edges/edges-cycle.test.ts › supersedes direct cycle: A→B then B→A rejected`, `› supersedes deep cycle: A→B→C then C→A rejected`, `› parent-of direct cycle: A→B then B→A rejected`, `› parent-of deep cycle: A→B→C then C→A rejected`, `› self-loop rejected: A→A on parent-of`, `› self-loop rejected: A→A on about`.

## Cascade

16. Deleting a `parent-of` parent trashes its children; `supersedes`, `about`, `attached-to` and `references` orphan the other end; a custom edge type with `cascade_on_delete: cascade` cascades and one with `block` refuses the delete with `400 edge_constraint_violation` naming the blocking edges. `correctness/edges/edges-cascade.test.ts › deleting a parent-of parent cascades to children`, `› supersedes defaults to orphan: deleting head leaves predecessor intact`, `› about defaults to orphan: deleting source leaves target intact`, `› attached-to defaults to orphan: deleting the host leaves the attachment intact`, `› references defaults to orphan: deleting the referenced target leaves the source intact`, `› custom edge-type with cascade_on_delete=cascade cascades on source delete`, `› custom edge-type with cascade_on_delete=block refuses source delete while edges exist`.
17. An edge removed by cascade is announced `edge.deleted` like one removed by its own route. `sync/deletions.test.ts › announces an edge removed by cascade, not only one removed by its own route`.

## Edge types

18. `POST /edge-types` registers a custom type with a cardinality, optional endpoint type constraints and a cascade behavior, answering `201`; it needs `metadata.edge_types:write` (`403 forbidden`); an id colliding with a shipped type answers `409 conflict` and an `extends` field answers `400 validation_error` (`compliance/edge-types.test.ts › custom edge-type registration`); the type is then usable in `POST /edges`, and a shipped name always resolves to the shipped type. `compliance/edge-types.test.ts › registers a custom edge type and answers 201`, `› a key without metadata.edge_types:write cannot register an edge type`, `› rejects a custom type whose id collides with a core edge type`, `› registered edge type is usable in POST /edges`, `› core-first resolution: edge_type="about" always routes to core semantics`.
19. Endpoint type constraints are checked on every edge write and walk the parent chain, so a subtype satisfies a constraint naming its parent. `correctness/edges/edges-type-constraints.test.ts › source / target type constraints: matching types accepted`, `› non-matching source type rejected`, `› non-matching target type rejected`, `› inheritance-aware: constraint accepts inheriting child type`.
20. `GET /edge-types` lists the shipped types and every registered one with its cardinality; `DELETE /edge-types/{id}` removes a registered one, after which the listing omits it and a second delete answers `404 edge_type_not_found`, as does any unknown id. `compliance/edge-types.test.ts › lists the shipped edge types and a registered one`, `› deletes a registered edge type and answers 404 for it afterwards`, `› answers 404 when deleting an edge type that does not exist`. The delete takes `schema.write`, refusing a key without it `403 forbidden`. `compliance/edge-types.test.ts › refuses a delete to a key without schema.write, and declares the refusal`. It does not consult the edges: existing edges of the type survive the removal and keep naming it, where the sibling `DELETE /types/{id}` refuses `409 type_in_use` (`findings.md` 9). `compliance/edge-types.test.ts › deletes an edge type while edges of it exist, and leaves them naming it`.

## Permissions

21. Writing an edge needs write on the source item's type and on the edge type, and the two halves answer differently: the source-type half is refused `403 type_not_permitted`, the edge-type half `403 edge_permission_denied`. A key with `edge.about:write` cannot write `parent-of`; `edge.*:write` writes any type; `edge.about:read` lists but does not write; the gate holds when the source is trashed, on `PATCH` and `DELETE` too. The document declares no 403 for the edge doors (`findings.md` 6). `compliance/edge-permissions.test.ts › dual-gate: source-type write + edge-type write required`, `› a key holding every edge type creates any edge`, `› narrow scope: key with edge.about:write cannot create parent-of edges`, `› wildcard edge_permissions: edge.*:write creates any edge type`, `› trashed source: PATCH/DELETE edge still gated on source type`, `› edge read scope: key with edge.about:read can list but not write`.
