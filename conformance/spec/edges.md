# Edges

A typed, directed relationship between two items, with its own id, properties and version.

## Creation and reading

1. `POST /edges` with `source_id`, `target_id` and `edge_type` answers `201` with `edge` carrying an id, the triple, `properties`, `created_at`, `updated_at` and `version: 1`. `correctness/edges/edges-crud.test.ts › edges CRUD` (one case per shipped edge type), `correctness/edges/edges-list.test.ts › reads an edge by id with its version`.
2. Each of the ten shipped edge types `about`, `parent-of`, `in-thread`, `attached-to`, `authored-by`, `derived-from`, `supersedes`, `references`, `in-collection` and `in-folder` is creatable and lists at `GET /edge-types`. `in-collection` constrains its target by role rather than by type: the target must declare `container`, which the shipped `core.media.album` and `core.media.series` do, and so may any type a publisher registers. `in-folder` places an item in a folder: it runs from any item to a `system.folder` (`items.md` 49) and nothing else, is many-to-many, carries `path`, the file's path relative to the folder's root, and orphans the other end when either is deleted; it declares no reverse name and is written at its source. `correctness/edges/edges-crud.test.ts › edges CRUD` (one case per shipped edge type), `compliance/edge-types.test.ts › lists the shipped edge types and a registered one`, `› ships in-folder from any item to a system.folder, carrying its path`. **Every door that writes an `in-folder` edge requires its `path` and takes nothing else**: a create, a change by `PATCH /edges/{id}` or a bulk upsert, judged on the properties as they would stand, refuses a `path` that is missing, empty, over 1024 characters, absolute, drive-absolute, carries a backslash or NUL, climbs out of the folder or names its root, and any other property, `400 validation_error` naming `properties.path` or the other property. An inline edge on the item doors (12, `items.md` 23) carries no properties, so they refuse an `in-folder` one the same way. A path that climbs and comes back inside is taken. `compliance/edge-types.test.ts › refuses an in-folder path that is missing or leaves the folder, and any other property, on every door that writes one`. **A revoked folder takes no new placement**: an `in-folder` edge to one is refused `400 edge_constraint_violation` with `details.constraint: "revoked"`, the code the edge doors answer for an edge its endpoints cannot hold, and the placements it held when it was revoked stay. `compliance/edge-types.test.ts › refuses a new placement in a revoked folder with edge_constraint_violation, and keeps the ones it held`. Two of them declare a **reverse name**, the name the edge goes by read from its target: `parent-of` is `child-of` from the child, and `attached-to` is `has-attachment` from the host. Every edge type also declares where it is **written at**, the end whose file writes it, which is the source unless it says otherwise: `parent-of` is written at its target, as `child-of`, and `attached-to` at its source. What a folder does with the two is `folders.md` 11's; how an edge is stored and read does not change. `compliance/edge-types.test.ts › lists the reverse names the shipped edge types declare`, `› lists the end whose file writes each shipped edge type`.
3. A caller may mint the edge id; a repeat under the same id naming the same triple answers the stored row and announces nothing; an id naming a different triple is refused `409 id_reused`, with `details.differs` naming which of `source_id`, `target_id` and `edge_type` disagrees — the same code `POST /items` answers for a reused item id (`items.md` 3), because it is the same mistake: a caller minted an id and the id is taken by a row it is not describing. `sync/identity.test.ts › keeps the id a client mints for an edge`, `sync/acknowledged.test.ts › answers an edge repeat with the stored row and announces nothing`, `› refuses an edge id that names a different triple`.
4. A body missing `source_id` or `target_id` answers `400 missing_required_field`. `correctness/edges/edges-crud.test.ts › rejects POST /edges missing required fields`.
5. `GET /edges/{id}` returns the edge; an unknown id answers `404 edge_not_found`. `correctness/edges/edges-list.test.ts › reads an edge by id with its version`, `› refuses an unknown query key and an unknown edge id`.
6. `GET /edges` lists edges, narrowed by `edge_type` and `updated_after`, paginated by cursor, and refuses an unknown query key `400` naming it in `details.unknown_parameters`. A credential whose type map reaches no type is refused `403 type_not_permitted`, as `GET /edges/{id}` beside it already refuses one (`keys-and-oauth.md` 1). `compliance/key-management.test.ts › the operator key is refused the data plane, reading as well as writing`. `correctness/edges/edges-list.test.ts › lists edges by type, excluding other types`, `› bounds a listing by updated_after with an excluded control`, `› paginates with a cursor and delivers every edge once`, `› refuses an unknown query key and an unknown edge id`, `sync/time-filters.test.ts › narrows an edge listing by modification time`.
7. `GET /items/{id}/edges` lists an item's outbound edges and `GET /items/{id}/backrefs` its inbound ones, both narrowed by `edge_type` and paginated; an unknown item answers `404 item_not_found` and a malformed id `400 invalid_id`. `correctness/edges/edges-crud.test.ts › edges CRUD`, `correctness/edges/edges-response.test.ts › per-type hydration caps a block and carries a next_cursor when over the limit`, `› answers 404 for an unknown item and 400 for a malformed id`, `correctness/edges/edges-backrefs.test.ts › GET /items/:id/backrefs returns inbound edges`, `› ?edge_type filter narrows to one type`, `› paginates via cursor across many inbound edges`, `› answers 404 for an unknown item and 400 for a malformed id`.
8. `GET /items/{id}` hydrates edges keyed by type, each block a page: at most 50 edges under `data`, and a `next_cursor` that `GET /items/{id}/edges?edge_type=<type>` continues, `null` when the block holds them all; a backrefs block continues at `GET /items/{id}/backrefs` the same way. `correctness/edges/edges-response.test.ts › GET /items/:id returns hydrated edges keyed by edge_type, each block a page`, `› per-type hydration caps a block and carries a next_cursor when over the limit`, `› continues a hydrated inbound block at the backrefs listing`.
9. `GET /items?edge[<type>]=<id>` narrows a listing to items with that outbound edge, combinable with `type`; the full form `filter=edge[<type>] eq "<id>"` returns the same set. `correctness/edges/edges-query.test.ts › edge[about]=<id> shorthand returns items with outbound about edge to id`, `› filter=edge[X] eq "Y" full form returns the same set`, `› combines edge filter with type to narrow results`.

## Updating and deleting

10. `PATCH /edges/{id}` merges `properties` over the ones it was not given, advances the version, and announces `edge.updated`; a stale `version` is refused. `correctness/edges/edges-crud.test.ts › updateEdge patches properties only`, `› updateEdge merges over the properties it was not given`, `compliance/events-contract.test.ts › announces edge.updated when an edge's properties change`, `sync/edge-version.test.ts › refuses an update naming a stale version and accepts the current one`.
11. `DELETE /edges/{id}` removes the edge; later listings exclude it. `correctness/edges/edges-crud.test.ts › deleteEdge removes the edge; subsequent list excludes it`.
12. `POST /items` with `edges` creates the item and its edges in one write. `correctness/edges/edges-crud.test.ts › POST /items with edges creates item + edges atomically`.
13. `POST /edges/bulk` reports per-edge outcomes; `upsert` replaces properties on a duplicate triple, `create_only` reports `skipped` with reason `duplicate_edge`, `atomic` rolls the batch back on a refusal with `bulk_atomic_rollback` and no edge written, at the inner refusal's status — `403` where that refusal is a permission, `400` otherwise, as on the item door (`items.md` 31), and an unknown edge type lands as `errored` in non-atomic mode. `compliance/edges-bulk.test.ts › creates edges in bulk and returns per-edge outcomes`, `› upsert mode replaces properties in place on duplicate triples`, `› create_only surfaces duplicates as skipped with reason duplicate_edge`, `› atomic=true rolls back the whole batch on validation error`, `› atomic=true rolls back a batch naming an item that does not exist`, `› atomic=false collects errors and continues`, `› unknown edge_type lands as errored in non-atomic mode`.

## Cardinality and cycles

14. `parent-of` allows one parent per child at any depth; `in-thread` is many-to-one; `supersedes` is one-to-one on both ends; many-to-many types accept any number; a refusal is `400 edge_constraint_violation`. `correctness/edges/edges-cardinality.test.ts › parent-of is one-parent-per-child: second parent rejected`, `› in-thread is many-to-one: source can only join one thread`, `› supersedes is one-to-one: rejects second outbound from same source`, `› supersedes is one-to-one: rejects second inbound to same target`, `› many-to-many edge types accept multiple edges`, `› parent-of deep nesting respects the one-parent-per-child rule at depth`.
15. `parent-of` and `supersedes` refuse an edge that would close a cycle, direct or deep, with `400 edge_cycle`; a self-loop is refused `400 edge_cycle` on every edge type, cycle-prone or not, because one edge closes it. `correctness/edges/edges-cycle.test.ts › supersedes direct cycle: A→B then B→A rejected`, `› supersedes deep cycle: A→B→C then C→A rejected`, `› parent-of direct cycle: A→B then B→A rejected`, `› parent-of deep cycle: A→B→C then C→A rejected`, `› self-loop rejected: A→A on parent-of`, `› self-loop rejected: A→A on about`.

## Cascade

16. Deleting a `parent-of` parent trashes its children; `supersedes`, `about`, `attached-to` and `references` orphan the other end; a custom edge type with `cascade_on_delete: cascade` cascades and one with `block` refuses the delete with `400 edge_constraint_violation` naming the blocking edges. `correctness/edges/edges-cascade.test.ts › deleting a parent-of parent cascades to children`, `› supersedes defaults to orphan: deleting head leaves predecessor intact`, `› about defaults to orphan: deleting source leaves target intact`, `› attached-to defaults to orphan: deleting the host leaves the attachment intact`, `› references defaults to orphan: deleting the referenced target leaves the source intact`, `› custom edge-type with cascade_on_delete=cascade cascades on source delete`, `› custom edge-type with cascade_on_delete=block refuses source delete while edges exist`. The server records which rows a trash took this way, and restoring the row trashed brings them back (`items.md` 27).
17. An edge removed by cascade is announced `edge.deleted` like one removed by its own route. `sync/deletions.test.ts › announces an edge removed by cascade, not only one removed by its own route`.

## Edge types

18. `POST /edge-types` registers a custom type with a cardinality, optional endpoint type constraints and a cascade behavior, answering `201`; it needs `metadata.edge_types:write` (`403 forbidden`); an id colliding with a shipped type answers `409 conflict` and an `extends` field answers `400 validation_error` (`compliance/edge-types.test.ts › custom edge-type registration`); the type is then usable in `POST /edges`, and a shipped name always resolves to the shipped type. `compliance/edge-types.test.ts › registers a custom edge type and answers 201`, `› a key without metadata.edge_types:write cannot register an edge type`, `› rejects a custom type whose id collides with a core edge type`, `› registered edge type is usable in POST /edges`, `› core-first resolution: edge_type="about" always routes to core semantics`. **A registration may declare a `reverse_name`, and every name a folder may read as an edge type belongs to one type.** The reverse name takes the edge-type identifier grammar, refused `400 validation_error` otherwise, and it is listed and answered with the type. So is `written_at`, `source` or `target`, `source` where the registration names none; `target` without a reverse name is refused `400 validation_error`, since the target's file has no other name to write the edge under. An id another type holds as its reverse name, a reverse name another type holds as its id or its reverse name, and a reverse name that is the type's own id are each refused `409 conflict`. A folder reads a frontmatter key as the edge type it names, so a name two types held would say two things at once. `compliance/edge-types.test.ts › registers an edge type with a reverse name and lists it`, `› refuses a reverse name another edge type already uses as a name`, `› refuses a reverse name that is not an edge type identifier`, `› registers an edge type written at its target, and refuses one with no name to write it under`.
19. Endpoint type constraints are checked on every edge write and walk the parent chain, so a subtype satisfies a constraint naming its parent. `correctness/edges/edges-type-constraints.test.ts › source / target type constraints: matching types accepted`, `› non-matching source type rejected`, `› non-matching target type rejected`, `› inheritance-aware: constraint accepts inheriting child type`.
20. `GET /edge-types` lists the shipped types and every registered one with its cardinality; `DELETE /edge-types/{id}` removes a registered one, after which the listing omits it and a second delete answers `404 edge_type_not_found`, as does any unknown id. `compliance/edge-types.test.ts › lists the shipped edge types and a registered one`, `› deletes a registered edge type and answers 404 for it afterwards`, `› answers 404 when deleting an edge type that does not exist`. The delete takes `schema.write`, refusing a key without it `403 forbidden`. `compliance/edge-types.test.ts › refuses a delete to a key without schema.write, and declares the refusal`. It consults the edges, in the shape its sibling `DELETE /types/{id}` has for items: `409 edge_type_in_use` with `details.edge_type` while any edge of the type is stored, and `?force=true` to delete the registration anyway. Forcing orphans rather than cascades — the edges stay, still naming a type the instance no longer holds — because deleting rows nobody asked to delete is the worse of the two surprises. A new code rather than `type_in_use`, matching the `edge_type_not_found` that already sits beside `type_not_found`. `compliance/edge-types.test.ts › refuses to delete an edge type while edges of it exist, and orphans them on force`, `› deletes an edge type no edge names, without force`.

## Permissions

21. Writing an edge needs write on the source item's type and on the edge type, and the two halves answer differently: the source-type half is refused `403 type_not_permitted`, the edge-type half `403 edge_permission_denied`. A key with `edge.about:write` cannot write `parent-of`; `edge.*:write` writes any type; `edge.about:read` lists but does not write; the gate holds when the source is trashed, on `PATCH` and `DELETE` too. `compliance/edge-permissions.test.ts › dual-gate: source-type write + edge-type write required`, `› a key holding every edge type creates any edge`, `› narrow scope: key with edge.about:write cannot create parent-of edges`, `› wildcard edge_permissions: edge.*:write creates any edge type`, `› trashed source: PATCH/DELETE edge still gated on source type`, `› edge read scope: key with edge.about:read can list but not write`. The target's type is not asked, so a key holding write on `core.note` and on `in-folder`, and nothing on `system.folder`, places a note in a folder, while every door that would write the folder row itself still refuses it `403 type_not_permitted` (`items.md` 16, 50). `compliance/edge-types.test.ts › writes an in-folder edge from a key holding the source's type and the edge type, and nothing on system.folder`.

22. **`GET /edges` answers only the edges the credential may read**, holding each row to the two permissions `GET /edges/{id}` asks for: read on the source item's type, and read on the edge type. A row failing either is left out of the page rather than refusing it, because a refusal would say a row exists. A page can therefore be shorter than `limit`, and empty with a `next_cursor` still to follow; the cursor comes from the whole listing, so paging still reaches the end of it, and a caller stops on `next_cursor: null` rather than on an empty page. A trashed source is read like any other, because a source read away is a source with no type to refuse. `compliance/edge-permissions.test.ts › drops an edge whose source is a type the credential cannot read`, `› drops an edge of an edge type the credential cannot read`, `› drops it still when the source is trashed, which is when a null source would read as no source at all`, `› pages to the end of the listing though whole pages are dropped`.

23. **Every plural door answers the same two questions, and so does the stream.** `GET /items/{id}/edges` and `GET /items/{id}/backrefs`, the edges and backrefs carried on an item read, the edges carried on an item listing and on `POST /items/bulk-get`, the edge lines of `GET /export`, and every `edge.*` frame on `GET /events` are each held to read on the edge type and read on the source item's type. The outbound doors already settled the source, because their anchor is every row's source; the inbound ones settled neither, because their anchor is the target while readability is the source item's. A row failing either is left out rather than refusing the answer, on the same terms as 22: the store's cursor is untouched, so a page or a block can be short while there is more to page for, and a hydrated block that empties is removed rather than left standing under an edge type's name. On the stream the withholding is per subscriber and applies to a replay from a cursor as it does to a live frame.

**A filter term naming an edge type is refused rather than dropped, on both doors that take one.** `GET /items?edge[<type>]=<id>`, `?backref[<type>]=<id>`, the same terms in the full `filter=` form, and `GET /search`'s `filter=`, all answer with the items on the other end of a relationship, so honoring one would say an edge of that kind joins two items the caller named and the page named. A term naming an edge type the credential may not read answers `403 edge_permission_denied`; a `backref` term anchored on an item whose type it may not read answers `403 type_not_permitted`, because on that side the caller names the source and an edge's readability is the source's. Refused and not dropped, because a dropped term would answer a different question under the same status, which is the unfiltered page an unknown parameter is refused to prevent. Both doors ask through one function, because a listing and a search that disagreed about one term would be the same disclosure reached through the other. `compliance/edge-permissions.test.ts › refuses a filter term naming a relationship the credential may not read`. Outbound webhook delivery is not one of these doors: a subscription is the instance's own outbound wire, narrowed by its event list and its type filter and by nothing else, for items as much as for edges. `compliance/edge-permissions.test.ts › leaves an edge of an unreadable kind out of GET /items/{id}/edges`, `› leaves an edge with an unreadable source out of GET /items/{id}/backrefs`, `› narrows the edges carried on an item read and on a bulk read` (which covers the item listing and `POST /items/bulk-get` through the same hydration), `› pages a per-item door to the end though whole pages are dropped`, `compliance/export.test.ts › carries only the kinds of relationship the credential may read`, `compliance/edge-events.test.ts › withholds a live edge frame the credential could not read singly`, `› withholds the same frames on a replay from a cursor`.
