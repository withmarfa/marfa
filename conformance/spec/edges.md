# Edges

A typed, directed relationship between two items, with its own id, properties and version.

## Creation and reading

1. `POST /edges` with `source_id`, `target_id` and `edge_type` answers `201` with `edge` carrying an id, the triple, `properties`, `created_at`, `updated_at` and `version: 1`. `correctness/edges/edges-crud.test.ts › edges CRUD` (one case per shipped edge type), `correctness/edges/edges-list.test.ts › reads an edge by id with its version`.
2. Each of the ten shipped edge types `about`, `parent-of`, `in-thread`, `attached-to`, `authored-by`, `derived-from`, `supersedes`, `references`, `in-collection` and `in-folder` is creatable and lists at `GET /edge-types`. `in-collection` constrains its target by role rather than by type: the target must declare `container`, which the shipped `core.media.album` and `core.media.series` do, and so may any type a publisher registers. `in-folder` places an item in a folder: it runs from any item to a `system.folder` (`items.md` 49) and nothing else, is many-to-many, carries `path`, the file's path relative to the folder's root, and orphans the other end when either is deleted; it declares no reverse name and is written at its source. `correctness/edges/edges-crud.test.ts › edges CRUD` (one case per shipped edge type), `compliance/edge-types.test.ts › lists the shipped edge types and a registered one`, `› ships in-folder from any item to a system.folder, carrying its path`. **Every door that writes an `in-folder` edge requires its `path` and takes nothing else**: a create, a change by `PATCH /edges/{id}` or a bulk upsert, judged on the properties as they would stand, refuses a `path` that is missing, empty, over 1024 characters, absolute, drive-absolute, carries a backslash or NUL, climbs out of the folder or names its root, and any other property, `400 validation_error` naming `properties.path` or the other property. An inline edge on the item doors (12, `items.md` 23) carries no properties, so they refuse an `in-folder` one the same way. A path that climbs and comes back inside is taken. `compliance/edge-types.test.ts › refuses an in-folder path that is missing or leaves the folder, and any other property, on every door that writes one`. **A revoked folder takes no new placement**: an `in-folder` edge to one is refused `400 edge_constraint_violation` with `details.constraint: "revoked"`, the code the edge doors answer for an edge its endpoints cannot hold, and the placements it held when it was revoked stay. `compliance/edge-types.test.ts › refuses a new placement in a revoked folder with edge_constraint_violation, and keeps the ones it held`. Two of them declare a **reverse name**, the name the edge goes by read from its target: `parent-of` is `child-of` from the child, and `attached-to` is `has-attachment` from the host. Every edge type also declares where it is **written at**, the end whose file writes it, which is the source unless it says otherwise: `parent-of` is written at its target, as `child-of`, and `attached-to` at its source. What a folder does with the two is `folders.md` 11's; how an edge is stored and read does not change. `compliance/edge-types.test.ts › lists the reverse names the shipped edge types declare`, `› lists the end whose file writes each shipped edge type`.
3. A caller may mint the edge id; a repeat under the same id naming the same triple answers the stored row and announces nothing; an id naming a different triple is refused `409 id_reused`, with `details.differs` naming which of `source_id`, `target_id` and `edge_type` disagrees — the same code `POST /items` answers for a reused item id (`items.md` 3), because it is the same mistake: a caller minted an id and the id is taken by a row it is not describing. An id naming an edge the caller may not read, by its source's type or its edge type, is refused `409 id_reused` with `existing_id` alone, on `POST /edges` and on each `POST /edges/bulk` entry, so it says the id is taken and nothing of that edge (`keys-and-oauth.md` 20). `compliance/unreadable-items.test.ts › POST /edges and POST /edges/bulk naming the id of an edge it cannot read learn the id is taken, and nothing of the edge`, `sync/identity.test.ts › keeps the id a client mints for an edge`, `sync/acknowledged.test.ts › answers an edge repeat with the stored row and announces nothing`, `› refuses an edge id that names a different triple`.
4. A body missing `source_id` or `target_id` answers `400 missing_required_field`. `correctness/edges/edges-crud.test.ts › rejects POST /edges missing required fields`.
5. `GET /edges/{id}` returns the edge; an unknown id answers `404 edge_not_found`, and so does an edge the key may not read (25). `correctness/edges/edges-list.test.ts › reads an edge by id with its version`, `› refuses an unknown query key and an unknown edge id`.
6. `GET /edges` lists edges, narrowed by `edge_type` and `updated_after`, paginated by cursor, and refuses an unknown query key `400` naming it in `details.unknown_parameters`. A credential whose type map reaches no type is refused `403 type_not_permitted`, as `GET /edges/{id}` beside it already refuses one (`keys-and-oauth.md` 1). `compliance/key-management.test.ts › the operator key is refused the data plane, reading as well as writing`. `correctness/edges/edges-list.test.ts › lists edges by type, excluding other types`, `› bounds a listing by updated_after with an excluded control`, `› paginates with a cursor and delivers every edge once`, `› refuses an unknown query key and an unknown edge id`, `sync/time-filters.test.ts › narrows an edge listing by modification time`.
7. `GET /items/{id}/edges` lists an item's outbound edges and `GET /items/{id}/backrefs` its inbound ones, both narrowed by `edge_type` and paginated; an unknown item answers `404 item_not_found` and a malformed id `400 invalid_id`. `correctness/edges/edges-crud.test.ts › edges CRUD`, `correctness/edges/edges-response.test.ts › per-type hydration caps a block and carries a next_cursor when over the limit`, `› answers 404 for an unknown item and 400 for a malformed id`, `correctness/edges/edges-backrefs.test.ts › GET /items/:id/backrefs returns inbound edges`, `› ?edge_type filter narrows to one type`, `› paginates via cursor across many inbound edges`, `› answers 404 for an unknown item and 400 for a malformed id`.
8. `GET /items/{id}` hydrates edges keyed by type, each block a page: at most 50 edges under `data`, and a `next_cursor` that `GET /items/{id}/edges?edge_type=<type>` continues, `null` when the block holds them all; a backrefs block continues at `GET /items/{id}/backrefs` the same way. `correctness/edges/edges-response.test.ts › GET /items/:id returns hydrated edges keyed by edge_type, each block a page`, `› per-type hydration caps a block and carries a next_cursor when over the limit`, `› continues a hydrated inbound block at the backrefs listing`.
9. `GET /items?edge[<type>]=<id>` narrows a listing to items with that outbound edge, combinable with `type`; the full form `filter=edge[<type>] eq "<id>"` returns the same set. `correctness/edges/edges-query.test.ts › edge[about]=<id> shorthand returns items with outbound about edge to id`, `› filter=edge[X] eq "Y" full form returns the same set`, `› combines edge filter with type to narrow results`.

## Updating and deleting

10. `PATCH /edges/{id}` merges `properties` over the ones it was not given, advances the version, and announces `edge.updated`; a stale `version` is refused. `correctness/edges/edges-crud.test.ts › updateEdge patches properties only`, `› updateEdge merges over the properties it was not given`, `compliance/events-contract.test.ts › announces edge.updated when an edge's properties change`, `sync/edge-version.test.ts › refuses an update naming a stale version and accepts the current one`. **It also moves one end of an edge whose other end holds one of its type**: `target_id` where each source holds one (`one-to-one`, `many-to-one`), `source_id` where each target holds one (`one-to-one`, `one-to-many`), so a child changes parent, a message its thread and a successor its predecessor in one write. The edge keeps its id and its properties, takes any the body names, moves its version on, and is announced as one `edge.updated` carrying it as it now stands, with no `edge.deleted` or `edge.created`: no reader, of a listing or of the stream, finds the end holding no edge or two. The edge as it would stand is judged as its create would be (14, 15, 19, 21), and refused with the same codes: `400 edge_constraint_violation` for a second edge at the new end or a type constraint, `400 edge_cycle`, `403 type_not_permitted` for a new source whose type the key may not write, and `404 item_not_found` for a target the key may not read, answered exactly as a missing one, for a new end that does not exist, and for an end that stays and is in the bin, which a create of the edge is refused for too. A stale `version` is refused `409 version_conflict` before anything the body names is judged, and an `Idempotency-Key` replays the first answer. A type holding more than one at the end that stays, `about` say, and a body moving both ends, are refused `400 validation_error`; a body that moves no end and names no `properties` is refused `400 missing_required_field`; and every refusal leaves the edge as it was. The event names no old end, because a consumer holds the edge by its id, and an old source named on the stream would be one a subscriber may not read. **Limit:** the stream holds an edge frame to read on its source's type as the edge now stands (23), so a subscriber that reads the old source's type and not the new one's is told nothing of the move, as it is told nothing of an item retyped out of its reach. `correctness/edges/edges-move.test.ts › moves a child to a new parent in one write, keeping the edge's id and properties`, `› moves a message to another thread, and a successor onto another predecessor`, `› never shows a reader the end with no edge while the edge moves`, `compliance/edge-move.test.ts › announces a move as one edge.updated, with nothing between`, `› refuses a move onto an end that already holds its one edge, and moves nothing`, `› refuses a move that would close a cycle, and moves nothing`, `› refuses a move onto a target its type's constraint refuses, and answers one the key cannot read exactly as a missing one`, `› refuses a new source that does not exist, or whose type the key cannot write`, `› refuses a move of an edge whose end that stays is in the bin, as its create is refused`, `› refuses a stale version with the edge as it stands, and moves nothing`, `› refuses a stale version before it judges the move`, `› refuses an update that moves no end and names no properties`, `› refuses to move an end of a type that holds many at the end that stays, or both ends at once`, `› answers a move repeated under one Idempotency-Key from its record`.
11. `DELETE /edges/{id}` removes the edge; later listings exclude it. `correctness/edges/edges-crud.test.ts › deleteEdge removes the edge; subsequent list excludes it`.
12. `POST /items` with `edges` creates the item and its edges in one write. `correctness/edges/edges-crud.test.ts › POST /items with edges creates item + edges atomically`.
13. `POST /edges/bulk` reports per-edge outcomes; `upsert` replaces properties on a duplicate triple, `create_only` reports `skipped` with reason `duplicate_edge`, `atomic` rolls the batch back on a refusal with `bulk_atomic_rollback` and no edge written, at the inner refusal's status, `404` for an end that is not there and `409` for an id another edge holds among them, as on the item door (`items.md` 31), and an unknown edge type lands as `errored` in non-atomic mode. `compliance/edges-bulk.test.ts › creates edges in bulk and returns per-edge outcomes`, `› upsert mode replaces properties in place on duplicate triples`, `› create_only surfaces duplicates as skipped with reason duplicate_edge`, `› atomic=true rolls back the whole batch on validation error`, `› atomic=true rolls back a batch naming an item that does not exist`, `› refuses a reused edge id here as the single door does, and says what differs`, `› atomic=false collects errors and continues`, `› unknown edge_type lands as errored in non-atomic mode`.

## Cardinality and cycles

14. `parent-of` allows one parent per child at any depth; `in-thread` is many-to-one; `supersedes` is one-to-one on both ends; many-to-many types accept any number; a refusal is `400 edge_constraint_violation`. An end that holds one edge of a type has it replaced by moving the edge's other end (10), judged without the edge being moved, rather than by a delete and a create, between which the end holds none. `correctness/edges/edges-move.test.ts › moves a child to a new parent in one write, keeping the edge's id and properties`, `› never shows a reader the end with no edge while the edge moves`, `compliance/edge-move.test.ts › refuses a move onto an end that already holds its one edge, and moves nothing`. `correctness/edges/edges-cardinality.test.ts › parent-of is one-parent-per-child: second parent rejected`, `› in-thread is many-to-one: source can only join one thread`, `› supersedes is one-to-one: rejects second outbound from same source`, `› supersedes is one-to-one: rejects second inbound to same target`, `› many-to-many edge types accept multiple edges`, `› parent-of deep nesting respects the one-parent-per-child rule at depth`. **A limit, accepted: every target-side cardinality check counts the edges the key cannot see.** Wherever a type lets a target hold one inbound edge, `parent-of`'s one parent, the target of `supersedes` and of any registered `one-to-one` or `one-to-many` type, a key writing that edge is refused `400 edge_constraint_violation` when the target already holds one from a source whose type the key may not read, though no door shows it that edge. The refusal can reveal that something hidden exists, never its id or type: its `details` name the edge type, the target the key named and the constraint, and nothing else. The one-parent rule stays whole. `compliance/edge-hidden-limits.test.ts › refuses a second parent the key cannot see, naming only the child`, `› refuses a successor the key cannot see on a one-to-one type, naming only the target`.
15. When a `parent-of` or `supersedes` edge would close a cycle, direct or deep and at any graph size, the server MUST refuse it with `400 edge_cycle` and leave the graph unchanged. A self-loop is refused `400 edge_cycle` on every edge type, cycle-prone or not, because one edge closes it. `correctness/edges/edges-cycle.test.ts › supersedes direct cycle: A→B then B→A rejected`, `› supersedes deep cycle: A→B→C then C→A rejected`, `› parent-of direct cycle: A→B then B→A rejected`, `› parent-of deep cycle: A→B→C then C→A rejected`, `› self-loop rejected: A→A on parent-of`, `› self-loop rejected: A→A on about`. **The cycle check considers every reachable edge, including earlier proposals in an atomic batch.** `packages/server/src/routes/edges-large-cycles.test.ts › rejects a parent-of cycle past 10,000 siblings while accepting an acyclic edge`, `› rejects a supersedes cycle deeper than 10,000 edges while accepting an acyclic edge`, `› rejects an atomic parent-of cycle formed by earlier proposals and writes neither edge`, `› rejects an atomic supersedes cycle formed by earlier proposals and writes neither edge`, `› terminates on a preexisting cycle that cannot reach the proposed source`. `A parent-of B` can be refused `400 edge_cycle` only because of an edge the key cannot see, one whose source is of a type it may not read. The refusal can reveal that something hidden exists, never its id or type: its `details` name the edge type and the two ends the key named, and nothing else. The acyclic graph stays whole. `compliance/edge-hidden-limits.test.ts › refuses an edge that closes a cycle only through an edge the key cannot see, naming only its own ends`.

## Cascade

16. Deleting a `parent-of` parent trashes its children; `supersedes`, `about`, `attached-to` and `references` orphan the other end; a custom edge type with `cascade_on_delete: cascade` cascades and one with `block` refuses the delete with `400 edge_constraint_violation` naming, in `details.blocking_edges` and in the count its message gives, the blocking edges whose edge type and both ends the key may read. A blocking edge failing any of those still refuses the delete and is left out of the list and the count, and where none is left the message gives no count, so the refusal can reveal that something hidden holds the row, never its id or type. `compliance/edge-hidden-limits.test.ts › refuses a delete held by a blocking edge it cannot see, naming no hidden id`. `correctness/edges/edges-cascade.test.ts › deleting a parent-of parent cascades to children`, `› supersedes defaults to orphan: deleting head leaves predecessor intact`, `› about defaults to orphan: deleting source leaves target intact`, `› attached-to defaults to orphan: deleting the host leaves the attachment intact`, `› references defaults to orphan: deleting the referenced target leaves the source intact`, `› custom edge-type with cascade_on_delete=cascade cascades on source delete`, `› custom edge-type with cascade_on_delete=block refuses source delete while edges exist`. The server records which rows a trash took this way, and restoring the row trashed brings them back (`items.md` 27); while each stays in the bin it carries `trashed_by_cascade`, and `trashed_with` naming the row trashed to a key that may read its type (`items.md` 26). `compliance/cascade-marks.test.ts › marks a row a cascade trashed with the row named, and no row trashed on its own`. **A limit, accepted: a cascade takes children the key cannot read or write.** A key deleting a row it may write trashes that row's `parent-of` children whatever their types, rows of types it may not read included, and nothing in the answer names them. `compliance/edge-hidden-limits.test.ts › trashes a hidden child with the parent the key deletes`.
17. An edge removed by cascade is announced `edge.deleted` like one removed by its own route, and says what removed it: each edge a purge takes, on the single door or a bulk purge, carries `purged_with` naming the purged item, and one removed by its own route carries none. `sync/deletions.test.ts › announces an edge removed by cascade, not only one removed by its own route`, `compliance/cascade-marks.test.ts › names the purged item on each edge its purge took, and on no edge deleted by its own door`, `› names the purged item on each edge a bulk purge took`.

## Edge types

18. `POST /edge-types` registers a custom type with a cardinality, optional endpoint type constraints and a cascade behavior, answering `201`; it needs `metadata.edge_types:write` (`403 forbidden`); an id colliding with a shipped type answers `409 conflict` and an `extends` field answers `400 validation_error` (`compliance/edge-types.test.ts › custom edge-type registration`); the type is then usable in `POST /edges`, and a shipped name always resolves to the shipped type. `compliance/edge-types.test.ts › registers a custom edge type and answers 201`, `› a key without metadata.edge_types:write cannot register an edge type`, `› rejects a custom type whose id collides with a core edge type`, `› registered edge type is usable in POST /edges`, `› core-first resolution: edge_type="about" always routes to core semantics`. **A registration may declare a `reverse_name`, and registration refuses a name another type already holds**, so every name a folder may read as an edge type belongs to one type among those registered under this rule. The reverse name takes the edge-type identifier grammar, refused `400 validation_error` otherwise, and it is listed and answered with the type. So is `written_at`, `source` or `target`, `source` where the registration names none; `target` without a reverse name is refused `400 validation_error`, since the target's file has no other name to write the edge under. An id another type holds as its reverse name, a reverse name another type holds as its id or its reverse name, and a reverse name that is the type's own id are each refused `409 conflict`. A folder reads a frontmatter key as the edge type it names, so a name two types held would say two things at once. **Limit:** registration refuses only what is registered after the name is held. A registered type holding a name a later build ships as a shipped type's id or reverse name keeps its registration, and the server logs the collision at boot and refuses nothing, so there one name belongs to two types. `compliance/edge-types.test.ts › registers an edge type with a reverse name and lists it`, `› refuses a reverse name another edge type already uses as a name`, `› refuses a reverse name that is not an edge type identifier`, `› registers an edge type written at its target, and refuses one with no name to write it under`. **A property's `type` is one of the field types a type's `fields` take**, and any other is refused `400 invalid_schema` with `details.errors` naming `property_schema.<name>.type`, the code a type's field of an unknown type gets. `compliance/edge-types.test.ts › refuses an edge property of an unknown type with the code a type's field gets`.
19. Endpoint type constraints are checked on every edge write and walk the parent chain, so a subtype satisfies a constraint naming its parent. `correctness/edges/edges-type-constraints.test.ts › source / target type constraints: matching types accepted`, `› non-matching source type rejected`, `› non-matching target type rejected`, `› inheritance-aware: constraint accepts inheriting child type`.
20. `GET /edge-types` lists the shipped types and every registered one with its cardinality, and **each says whether Marfa ships it** as `shipped`, `true` for a shipped type and `false` for a registered one, so a connector tells the two apart without a list of names; the `201` a registration answers carries it too, `false`. `compliance/edge-types.test.ts › says whether Marfa ships each edge type, on the list and on registration`. `DELETE /edge-types/{id}` removes a registered one, after which the listing omits it and a second delete answers `404 edge_type_not_found`, as does any unknown id. `compliance/edge-types.test.ts › lists the shipped edge types and a registered one`, `› deletes a registered edge type and answers 404 for it afterwards`, `› answers 404 when deleting an edge type that does not exist`. The delete takes `schema.write`, refusing a key without it `403 forbidden`. `compliance/edge-types.test.ts › refuses a delete to a key without schema.write, and declares the refusal`. **`schema.write` admits a key to the delete, and its edge map decides which edge types**, asked of the id and of any `reverse_name` the type declares, as registration asks them (26): a name the map leaves short of `write` is refused `403 edge_permission_denied` with `details.edge_type` naming it, `force=true` included, and the type stays registered. An id nothing registers still answers `404 edge_type_not_found` whatever the map. `compliance/edge-types.test.ts › deletes only the edge types whose id and reverse name the key's own edge map grants write on`. It consults the edges, in the shape its sibling `DELETE /types/{id}` has for items: `409 edge_type_in_use` with `details.edge_type` while any edge of the type is stored, and `?force=true` to delete the registration anyway. Forcing orphans rather than cascades — the edges stay, still naming a type the instance no longer holds — because deleting rows nobody asked to delete is the worse of the two surprises. A new code rather than `type_in_use`, matching the `edge_type_not_found` that already sits beside `type_not_found`. `compliance/edge-types.test.ts › refuses to delete an edge type while edges of it exist, and orphans them on force`, `› deletes an edge type no edge names, without force`. As on its sibling, the door looks the type up, asks for edges and deletes in one transaction. Without `force`, an edge written while a delete is in flight either lands first and the delete is refused `409 edge_type_in_use`, or lands after and is refused `404 edge_type_not_found`; with `force`, nothing is counted, and only the second half holds. Of two deletes in flight, the second answers `404 edge_type_not_found`. The server's own suite asserts it (`packages/server/src/routes/type-delete-atomic.test.ts`).

## Permissions

21. Writing an edge needs write on the source item's type and on the edge type, and the two halves answer differently: the source-type half is refused `403 type_not_permitted` where the key may read the source's type, and a source it may not read answers as a missing one (24), the edge-type half `403 edge_permission_denied` where the key lacks write on the edge type, each naming the grant it lacks in `details.grant` (`errors.md` 11), and on `PATCH` and `DELETE` an edge type it may not read at all answers as a missing edge (25). A key with `edge.about:write` cannot write `parent-of`; `edge.*:write` writes any type; `edge.about:read` lists but does not write; the gate holds when the source is trashed, on `PATCH` and `DELETE` too. `compliance/edge-permissions.test.ts › dual-gate: source-type write + edge-type write required`, `› a key holding every edge type creates any edge`, `› narrow scope: key with edge.about:write cannot create parent-of edges`, `› wildcard edge_permissions: edge.*:write creates any edge type`, `› trashed source: PATCH/DELETE edge still gated on source type`, `› edge read scope: key with edge.about:read can list but not write`. The target's type is asked only at read, and a target the key may not read answers as a missing one (24). So a key holding write on `core.note` and on `in-folder`, and read on `system.folder`, places a note in a folder, while every door that would write the folder row itself still refuses it `403 type_not_permitted` (`items.md` 16, 50); without that read the folder answers `404 item_not_found`. `compliance/edge-types.test.ts › writes an in-folder edge from a key holding the source's type, the edge type and read on system.folder, and writing nothing of it`.

22. **`GET /edges` answers only the edges the credential may read**, holding each row to the two permissions `GET /edges/{id}` asks for: read on the source item's type, and read on the edge type. A row failing either is left out of the page rather than refusing it, because a refusal would say a row exists. A page can therefore be shorter than `limit`, and empty with a `next_cursor` still to follow; the cursor comes from the whole listing, so paging still reaches the end of it, and a caller stops on `next_cursor: null` rather than on an empty page. A trashed source is read like any other, because a source read away is a source with no type to refuse. `compliance/edge-permissions.test.ts › drops an edge whose source is a type the credential cannot read`, `› drops an edge of an edge type the credential cannot read`, `› drops it still when the source is trashed, which is when a null source would read as no source at all`, `› pages to the end of the listing though whole pages are dropped`. **A limit, accepted: a readable edge names its target, readable or not.** An edge whose source and edge type the key may read is served whole on every door and frame that serves an edge (23), this one, `GET /edges/{id}`, `GET /items/{id}/edges`, every hydrated block, the edge lines of `GET /export` and the `edge.*` frames of `GET /events` among them, so its `target_id` can be the id of an item the key cannot read. The block refusal's `blocking_edges` is the exception (16): it lists no edge whose far end the key cannot read. `compliance/edge-hidden-limits.test.ts › names a hidden target's id on an edge the key may read`.

23. **Every plural door answers the same two questions, and so does the stream.** `GET /items/{id}/edges` and `GET /items/{id}/backrefs`, the edges and backrefs carried on an item read, the edges carried on an item listing and on `POST /items/bulk-get`, the edge lines of `GET /export`, and every `edge.*` frame on `GET /events` are each held to read on the edge type and read on the source item's type. The outbound doors already settled the source, because their anchor is every row's source; the inbound ones settled neither, because their anchor is the target while readability is the source item's. A row failing either is left out rather than refusing the answer, on the same terms as 22: the store's cursor is untouched, so a page or a block can be short while there is more to page for, and a hydrated block that empties is removed rather than left standing under an edge type's name. On the stream the withholding is per subscriber and applies to a replay from a cursor as it does to a live frame, and the source item's type is the one the event carries from when it was published (`events.md` 8 and 19), so the edges a purge takes reach only a subscriber that could read the purged item.

**A filter term naming an edge type is refused rather than dropped, on every door that takes one.** `GET /items?edge[<type>]=<id>`, `?backref[<type>]=<id>`, the same terms in the full `filter=` form, and `GET /search`'s `filter=`, all answer with the items on the other end of a relationship, so honoring one would say an edge of that kind joins two items the caller named and the page named. A term naming an edge type the credential may not read answers `403 edge_permission_denied`. A `backref` term counts only edges whose source the credential may read, as every door serving an edge does (23), on `GET /items`, `GET /search` and `POST /items/bulk-actions` alike: so one anchored on an item it may not read, trashed or not, matches exactly as one anchored on an id no row holds, and `backref[<type>] exists` matches no row through an edge it could not read. An `edge` term, whose far end is the target, matches every edge the credential may read, a target it may not read included, as a device holding those edges does (22). `compliance/unreadable-items.test.ts › a filter term anchored on an item it cannot read matches as one anchored on no item`, `› an outbound term naming an item it cannot read matches the readable edges to it`, `device/fidelity.test.ts › answers an edge term naming a target the key cannot read as the server does`. Refused and not dropped, because a dropped term would answer a different question under the same status, which is the unfiltered page an unknown parameter is refused to prevent. `POST /items/bulk-actions` refuses it the same way, before it matches anything. The doors ask through one function, because a listing and a search that disagreed about one term would be the same disclosure reached through the other. `compliance/edge-permissions.test.ts › refuses a filter term naming a relationship the credential may not read`. Outbound webhook delivery asks the same two questions of the credential that registered the subscription (`events.md` 23). `compliance/edge-permissions.test.ts › leaves an edge of an unreadable kind out of GET /items/{id}/edges`, `› leaves an edge with an unreadable source out of GET /items/{id}/backrefs`, `› narrows the edges carried on an item read and on a bulk read` (which covers the item listing and `POST /items/bulk-get` through the same hydration), `› pages a per-item door to the end though whole pages are dropped`, `compliance/export.test.ts › carries only the kinds of relationship the credential may read`, `compliance/edge-events.test.ts › withholds a live edge frame the credential could not read singly`, `› withholds the same frames on a replay from a cursor`.

24. **An edge write says nothing of an end the credential may not read.** On `POST /edges`, `POST /edges/bulk` and the inline `edges` of `POST /items` (a create or a natural-key upsert), `PATCH /items/{id}` and `POST /items/bulk`, a target whose type the key may not read is answered exactly as a missing one: `404 item_not_found` with the message `Edge target item not found: <id>` on a single write, and the same code and message where a bulk door reports its entries, inside `bulk_atomic_rollback` or as the entry's own error. The check runs before any that reads the target, so a target an endpoint type constraint would refuse answers the same, and the answer discloses neither the row's existence nor its type. It runs before the bulk door matches an existing edge, which would otherwise answer `updated` or `skipped` with that edge's id, and before `PATCH` reads the version, which would otherwise answer a stale write `409`. A readable target is written, and a readable target the constraint refuses answers `400 edge_constraint_violation` (19). `compliance/edge-permissions.test.ts › an edge write says nothing of a target the credential cannot read`, `› answers an unreadable target as a missing one on the bulk door, where an edge to it already exists`, `› answers an unreadable target as a missing one on a stale PATCH, before the version is read`. A source is answered the same way, `Edge source item not found: <id>`, on `POST /edges`, on `POST /edges/bulk`, where the entry is judged as a create even when an edge from that source already matches it, and on a `PATCH /edges/{id}` moving the source, before its write is asked (`keys-and-oauth.md` 20). `compliance/unreadable-items.test.ts › an item the key cannot read answers as a missing one`, `› PATCH /edges/{id} moving the source onto an item it cannot read`.

25. **An edge named by id says nothing of itself to a credential that may not read it.** `GET`, `PATCH` and `DELETE /edges/{id}`, on an edge whose edge type the key may not read, or whose source item is of a type it may not read, trashed or not, answer `404 edge_not_found` with the message an unknown id gets (5), because a listing leaves that edge out (22). An edge the key may read and not write refuses `PATCH` and `DELETE` `403`: `type_not_permitted` for the source's type, `edge_permission_denied` for the edge type (21). `compliance/unreadable-items.test.ts › an edge of a type it cannot read answers as a missing edge on every door naming it`. `compliance/unreadable-items.test.ts › an item the key cannot read answers as a missing one`, `compliance/edge-permissions.test.ts › trashed source: PATCH/DELETE edge still gated on source type`, `› drops it still when the source is trashed, which is when a null source would read as no source at all`.

26. **A key registers only the edge types its own edge map grants write on.** `metadata.edge_types:write` (18) admits a key to `POST /edge-types`; its edge map decides which names, and it is asked of the `id` and of any `reverse_name`, since a registration claims both. A name the map leaves short of `write` is refused `403 edge_permission_denied` with `details.edge_type` naming it, and nothing is registered. `compliance/edge-types.test.ts › registers only the edge type ids the key's own edge map grants write on`.
