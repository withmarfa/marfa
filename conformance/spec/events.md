# Events

`GET /events` is a server-sent event stream of every mutation, resumable by cursor, and outbound webhooks deliver the same events to a URL.

## The stream

1. A subscription with a bearer credential answers `200 text/event-stream`; without one, `401` in the standard envelope. `compliance/events-contract.test.ts › opens with a stream_cursor frame naming the log head`, `› refuses a subscription with no credential`, `compliance/unauthenticated.test.ts › answers 401 unauthorized on each of them`.
2. The first frame is `stream_cursor`, carrying no `id:` and a `cursor` equal to the id of the last event the log holds; a client resuming from it sees what a live subscriber would have. **Once the prologue is over the stream says so**: a `stream_live` frame, carrying no `id:` and a `cursor` at or past the announced head, follows the replay and the live frames held while it ran, and precedes every frame after them; a stream opened with no cursor sends it straight after its announcement. A frame the filter or the credential withholds is not written at all, so the frame that would show the announced head reached can be one a subscriber is never sent; the marker is what tells such a subscriber it has caught up, and its cursor, the furthest position the stream knows, is one it may resume from without being sent again what the replay covered. The cursor is `null` only where no position is known, a head read that outran its budget with nothing to replay. **A replay writes as it reads**: it gives the process a turn between its reads of the log, so what it has written reaches the wire and other requests are answered while it runs; frames published meanwhile are held for after it, and where they outrun the hold the replay reads on past them and sends them itself, ending short (`stream_incomplete`) only where one of them is a row it cannot read, whose live copy was its one carrier; and one that has written nothing for a second says it is still reading with a `: replaying` comment after its next read, so a subscriber that ends on silence is not told the replay finished while it reads rows it withholds (the server's own `routes/events.test.ts`). A stream that ends short, on `stream_incomplete`, `catchup_too_old` or `cursor_ahead`, never sends it. `compliance/events-contract.test.ts › opens with a stream_cursor frame naming the log head`, `sync/stream-contract.test.ts › announces a cursor a client can resume from`, `sync/stream-contract.test.ts › marks the end of the replay with a cursor a filtered reader can resume from`.
3. `Last-Event-ID` resumes from a cursor, and every retained event after it is replayed. **A cursor is an event id the log issued.** A `Last-Event-ID` that is not one written as the log writes it, a decimal number with no sign, spaces, leading zeros or other base and no larger than `9223372036854775807`, answers `400 validation_error` with `details.errors[].path` naming `Last-Event-ID`, rather than being read as no cursor; an empty one is no cursor, as an SSE client holding no id sends it. A cursor past the log's head is one the log never issued, which is what a client holds after the instance is restored behind it: the stream answers a terminal `cursor_ahead` frame carrying `requested` and `head` and no `id:`, and closes, rather than replaying from it and skipping every new event up to its number; the client re-reads state from the API, as for `catchup_too_old`. **A cursor is too old only when the event after it is no longer retained: the log's oldest retained id is greater than the cursor plus one.** Then the stream answers a terminal `catchup_too_old` frame carrying `min_retained_id` and `requested`, and closes; so does a replay whose next events the sweep retires while it reads, rather than replaying over the gap. A cursor of `0` against a log whose first event is `1` is a client exactly in step, because a cursor names the last event applied and not the first one wanted, and it is every device that hydrated an instance with an empty log. **Retention retires a prefix of the log: an event is retired only with every event before it, never while its own stamp is within the retention, and never the newest event.** A row is stamped before its insert waits for the log's writer, so stamps need not follow ids, and the sweep cuts by id below the oldest row still within the retention; a log once written keeps at least its newest event, so the oldest retained id is always there to check and is the one boundary a reader has to. A row stamped ahead of the clock, which a clock put back leaves, holds back every row above it until its stamp ages, since retiring around it would leave a hole. The server's own `storage/sqlite/event-log-store.test.ts` asserts the prefix over a log whose stamps are out of id order or ahead of the clock, and `routes/events.test.ts` the refusal of a cursor behind a log retired to its newest event and of a replay the sweep overtakes after its cursor was checked. The stale case cannot be arranged over the wire: a request can shorten the retention to an hour and run the sweep (`housekeeping.md` 3), but cannot make an event older than an hour, so it is asserted where a row can be retired, in the server's own `routes/events.test.ts`. **Ids are issued in commit order, and frames are delivered in that order, edge frames beside item frames.** An event's id is assigned by the insert that commits it, under the log's single writer, so no lower id reaches the log after a higher one, and the stream sends nothing ahead of a frame still waiting on the read that decides whether the subscriber may see it. A reader that closes and later resumes from the last id it received therefore sees every event after it exactly once. The one exception is a stored event whose payload the server can no longer read: it is not replayed, and a subscriber connected when it was published receives its live copy after the replay, behind higher ids, because that copy is the one carrier the event has left (`routes/events-replay-dedupe.test.ts`). The order across both kinds is asserted in the server's own `routes/events-live-order.test.ts`, where a purge announces a row's edges before the row, and `routes/events-delivery-hold.test.ts`, where frames queue behind a credential read still out (20), on the live path and in the prologue's hold. `sync/replay.test.ts › resolves a type filter through the same subtree the live stream does`, `sync/replay.test.ts › carries a bulk write, so a catch-up after an import is complete`, `compliance/catchup-too-old.test.ts › replays from a cursor of zero when the log begins at one`, `sync/resume.test.ts › a reader that closes at the head and resumes from its last id misses nothing and repeats nothing`, `compliance/events-contract.test.ts › refuses a cursor that is not a decimal event id`, `› refuses a cursor past the log's head with a terminal cursor_ahead frame`.
4. `type` narrows the stream to a type and its subtree, comma-separated up to ten; `*`, an entry outside the identifier grammar and more than ten entries answer `400 validation_error`; `edges=none` withholds edge events while item events still arrive, `edges=all` delivers them, and any other value answers `400`. `compliance/events-contract.test.ts › refuses a wildcard type filter, a type outside the grammar, an unknown edges value and more than ten types`, `› withholds edge events under edges=none and announces them under edges=all`, `sync/replay.test.ts › resolves a type filter through the same subtree the live stream does`, `sync/stream-contract.test.ts › delivers edge events to a stream filtered by item type`.
5. A write is announced after its transaction commits; a write that rolls back announces nothing. `sync/post-commit.test.ts › a write that rolls back announces nothing, while one that commits does`. **A change and its event are written together**: the event row is written inside the transaction that makes the change, on every door and job that writes an item, an edge, tags or extensions, so a change that commits is in the log and one that does not is not, and the log's ids follow the order the changes committed. A subscriber on the instance is told once the transaction commits. Whatever a door reads for its answer it reads inside that transaction too, so a failure anywhere before the answer undoes the change, and **a change that committed is never answered with a failure**: the idempotency layer releases its key on a `5xx`, and a retry of a change that had in fact committed would write it twice. Nothing a fixture can cause fails between a write and its answer, so the server's own suite injects it: every write door, its event refused by the log, writes nothing (`packages/server/src/routes/rollback-event-doors.test.ts`), and a write whose answer fails after its event was written is undone and written once by its retry (`packages/server/src/routes/committed-write-answer.test.ts`).
6. Writes continue while a subscription is open. `compliance/edge-events.test.ts › accepts writes while an event stream is open`.

## The vocabulary

7. Item events are `item.created`, `item.updated`, `item.deleted`, `item.restored`, `item.purged` and `item.state_changed`, each carrying `type` and `item`; a tag write and an extension write are both `metadata.changed` carrying `item` and `metadata`, whatever the namespace, and every frame carrying `metadata` carries only the extension namespaces the subscriber may read (`keys-and-oauth.md` 21). **A frame says what a cascade did.** The `item` of an `item.deleted`, or of an `item.purged` from the single door or a bulk purge, for a row a cascade trashed carries `trashed_by_cascade` and `trashed_with` (`items.md` 26), and an `item.restored` for a row another row's restore brought back carries `restored_with` beside `item`, naming that row (`items.md` 27); a frame for a row trashed or restored on its own, or a `system.*` row a cascade revokes, carries none of them. **A frame names another row only to a subscriber that may read its type**: `trashed_with` and `restored_with` are left out of the frame sent to any other, while `trashed_by_cascade` reaches every subscriber the frame reaches. The log stores one frame and each subscriber is answered from it when the frame is sent, so a replay from a cursor answers a subscriber exactly as the live frame did. `sync/identity.test.ts › keeps the id a client mints for an item, on the row and on the event`, `sync/deletions.test.ts › announces a purge, so a client offline across it learns the row is gone`, `compliance/events-contract.test.ts › announces item.restored when a trashed item comes back`, `› announces item.state_changed on a lifecycle transition`, `› announces metadata.changed on a tag write`, `› announces metadata.changed on an extension write under any namespace`, `› carries on a metadata.changed frame only the extension namespaces the subscriber may read`, `compliance/cascade-marks.test.ts › marks a row a cascade trashed with the row named, and no row trashed on its own`, `› names the row trashed only to a key that may read its type, and says a cascade took the row to any key that reads it`, `› names the row whose trash took it on the purge of a row a cascade trashed`, `› names the row whose trash took it on each row a bulk purge purges, only to a key that may read its type`, `› marks no row a cascade revokes rather than trashes`, `› names the row restored on each row its restore brings back, and not on the row itself`, `› names the row restored only to a key that may read its type`, `› names the row moved on each row a transition out of the bin brings back, only to a key that may read its type`, `› names the row moved on each row a bulk transition out of the bin brings back, only to a key that may read its type`.
8. Edge events are `edge.created`, `edge.updated` and `edge.deleted`, each carrying `type`, `edge` and `source_type`, the type of the edge's source item when the event was published, which is what decides who is told about it (19). An `edge.deleted` for an edge a purge took, on the single door or a bulk purge, also carries `purged_with` beside `edge`, naming the purged item (`edges.md` 17); an edge deleted any other way carries none, live or replayed. `compliance/edge-events.test.ts › SSE delivers edge.created and edge.deleted`, `› carries the source item's type on every edge frame`, `compliance/events-contract.test.ts › announces edge.updated when an edge's properties change`, `sync/identity.test.ts › keeps the id a client mints for an edge`, `compliance/cascade-marks.test.ts › names the purged item on each edge its purge took, and on no edge deleted by its own door`, `› names the purged item on each edge a bulk purge took`.
9. A bulk write reaches the log like a single write. `sync/replay.test.ts › carries a bulk write, so a catch-up after an import is complete`.
10. A repeated create under an id already used, and a repeated request under an `Idempotency-Key`, announce nothing the second time. `sync/acknowledged.test.ts › answers an item repeat with the stored row and announces nothing`, `› answers an edge repeat with the stored row and announces nothing`, `sync/idempotency.test.ts › answers a repeated create with the first result rather than a second row`.
11. `stream_incomplete` ends a stream that can no longer deliver what it opened with, carrying `reason` and the `cursor` of the last event it sent, and no `id:`: everything after that event is still in the log, so the recovery is to reconnect from it. It has five reasons. `credential_ended` (20) and `reader_behind` (21) are provoked over the wire and asserted there; `replay_failed`, `backlog_overflow` and `live_delivery_failed` are server-side failures nothing over the wire provokes, so they are unasserted (`coverage.md`). `stream_cursor`, `stream_live`, `catchup_too_old` and `cursor_ahead` are the stream's own frames beside it, and none of the five carries an `id:` but `catchup_too_old`, whose id is the oldest retained.

## Outbound webhooks

12. `POST /webhooks` with a `url` and `events` from the vocabulary above answers `201` with the subscription and its `secret` in plaintext, once; later reads redact the secret to its last characters. `compliance/webhooks.test.ts › registers a subscription and returns the secret once`.
13. A matching event is delivered to the URL as JSON with `event_type` and the payload, as the subscription's credential may read it (23), with every mark of statements 7 and 8 that credential may read where the frame carries it, `trashed_with` and `restored_with` included, an `X-Marfa-Event-Type` header, and an `X-Marfa-Signature` of the form `t=<unix seconds>,v1=<hex sha256>` where `v1` is the HMAC of `<t>.<raw body>` under the secret; the delivery is recorded at `GET /webhooks/{id}/deliveries` with its status and attempt, newest first, and the log pages by cursor like every list: a page the `limit` cut answers a `next_cursor`, and the walk reaches every attempt once. `compliance/webhooks.test.ts › delivers a matching event to the URL with a verifiable signature`, `› pages its delivery log by cursor, every attempt once`, `compliance/edge-events.test.ts › delivers edge.created and edge.deleted to a webhook with a valid signature`, `compliance/cascade-marks.test.ts › delivers the item.deleted of a row a cascade trashed with its mark, and the row trashed's own without one`.
14. An event outside the subscription is not delivered. `compliance/webhooks.test.ts › does not deliver an event outside the subscription`.
15. `events: ["*"]` is refused `400 validation_error`, with `details.errors[].path` naming the position of the offending entry rather than the body: `*` is not in the vocabulary either door publishes, and dispatch matches a subscribed name against an event's own literally, so a stored wildcard would be a subscription that could never fire. A named subscription on the same event is delivered to in the same run, which is what holds the refusal to the door rather than to dispatch. `PATCH /webhooks/{id}` refuses it on the same terms and leaves the stored list where it was. `compliance/webhooks.test.ts › refuses a wildcard subscription while a named one on the same event is delivered`, `› refuses a wildcard on the update door, leaving the stored events alone`.
16. `PATCH /webhooks/{id}` changes `url`, `events`, `type_filter` and `active` in place, each reading back; `DELETE` removes the subscription and every door answers `404 webhook_not_found` for it afterwards. `compliance/webhooks.test.ts › updates the url, events, type filter and active flag in place`, `› deletes a subscription and answers 404 for it afterwards`, `› answers 404 for an unknown subscription on every door`.
17. An event name outside the vocabulary, or a body without `url` or `events`, answers `400`; a key without `webhooks.manage` answers `403` on every door; no credential answers `401`. `compliance/webhooks.test.ts › refuses an event name outside the vocabulary`, `› refuses a body with no url or no events`, `› refuses a key without webhooks.manage`, `› refuses every door without a credential`.

**How long the delivery log is kept is not stated here, because no fixture can age a row.** A settled delivery leaves with the audit retention, a `/config` override of it included, and keeps no payload or address once settled, a delivery settled unsent included; one still retrying stays whatever its age. The server's own `webhooks/delivery-retention.test.ts` asserts both.

## Audit

18. Every write is recorded at `GET /audit` with the acting key, the action, the resource type and id, and details; the listing filters by `action`, `resource_type` and `resource_id`, bounds by `created_after` and `created_before` (both exclusive of the row's own instant, and both refused when they are not an instant), paginates by cursor, needs `audit.read`, refuses a query key it does not declare, and refuses no credential. `compliance/audit.test.ts › records a write with the acting key, the resource and the action`, `› filters by action and resource type with an excluded control`, `› bounds by created_after and created_before, both exclusive`, `› reads a bound at any precision, and refuses one that is not an instant`, `› paginates with a cursor and delivers every row once`, `› refuses an undeclared bound rather than answering the whole trail`, `› refuses a key without audit.read`, `› refuses a request with no credential`, `compliance/edge-events.test.ts › audit log records edge mutations with edge_id in resource_id`.

## Permissions

19. **A subscriber is told about an edge only where the single read would answer it.** Every `edge.created`, `edge.updated` and `edge.deleted` frame is held, per subscriber, to the two permissions `GET /edges/{id}` asks for: read on the edge type, and read on the source item's type (`edges.md` 23). `edges=none` is a subscriber's own parameter and narrows nothing else. A frame failing either is withheld rather than closing the stream, and a replay from a cursor withholds exactly what the live path does, because a stored frame is the same disclosure reached through a catch-up. **The source half is asked of the `source_type` the event carries** (8), not of a row read when the frame is sent: a purge announces each edge it took after the row has gone, and the type it carries still says who could read that row, so a subscriber that could not read the purged item is not told about its edges. A frame carrying no source type is withheld from every subscriber, since a source that cannot be classified cannot be shown readable. `compliance/edge-events.test.ts › withholds a live edge frame the credential could not read singly`, `› withholds the same frames on a replay from a cursor`, `› withholds a purged item's edges from a subscriber that could not read it, live and on a replay`.

20. **A stream answers to its credential as it stands, not as it stood when it connected.** The stream reads its credential again before it delivers each batch of frames, live or replayed, and at each heartbeat, every 30 seconds, and every frame in a batch was published before that read began. A key narrowed by `PATCH /keys/{id}` narrows the stream with it: a frame the key may no longer read is withheld from then on. A key revoked or deleted, a key past its `expires_at`, a sign-in's token revoked or past its expiry, and an app disconnected by revoking its grant each end the stream with a terminal `stream_incomplete` whose reason is `credential_ended`, and nothing written after the change reaches it; a reconnect with the same credential is refused `401`, and an app reconnects with the token it refreshed to. `compliance/stream-credential.test.ts › stops delivering a type the key is narrowed away from`, `› ends with credential_ended when the key is revoked, and sends nothing after`; the server's own `routes/events-live-credential.test.ts` covers expiry, a sign-in's token and the heartbeat, which a fixture cannot make pass without waiting on the clock.

## A reader that falls behind

21. **A stream holds at most 4 MiB of frames its reader has not taken, and the one frame that crosses that.** A live frame that finds that much still unread ends the stream with a terminal `stream_incomplete` whose reason is `reader_behind`, and its `cursor` names the last event sent, so the reader reconnects from it and the replay serves the rest. A replay, and the release of the frames held while the stream opened, are paced by the reader instead: each waits for room before every frame it sends, and ends the same way only when the reader has taken no frame for 30 seconds, so a reader taking frames slowly but steadily is waited for. A stream that has ended keeps what it queued for its reader, the terminal frame among it, for 30 seconds, and then lets the queue and the connection go. `compliance/stream-reader-behind.test.ts › is ended with reader_behind once it falls past the bound, and resumes from its cursor`; the server's own `routes/events-reader-behind.test.ts` holds the replay's pacing and the stalls, against a bound small enough to reach without megabytes.

## Whose subscription it is, and where it may send

22. **A subscription belongs to the credential that registered it.** Any credential holding `webhooks.manage` may register one, whatever it may read. Every door answers a subscription only to that credential: to another it is an id nobody holds, `404 webhook_not_found` on `GET`, `PATCH`, `DELETE` and the delivery log, and it is left out of `GET /webhooks`. A signed-in app's subscription belongs to its grant, the app and the person who consented to it, rather than to the token that registered it, so every token of that grant is the same credential and the subscription outlives the token: a refresh, a scope unticked on the consent screen, a replayed refresh token or the end of the browser session a token was issued under each ends tokens while the grant stands. `compliance/webhooks.test.ts › answers a subscription another credential registered as an unknown id on every door`, and the sign-in half in the server's own `routes/webhooks-ownership.test.ts` and `webhooks/grant-owner.test.ts`.
23. **A delivery carries what that credential may read when it is sent.** An item event is delivered only where the credential may read the item's type, and a mark naming another row only where it may read that row's type (7). A `metadata.changed` carries only the extension namespaces the credential may read, as every door answering extension data does (`keys-and-oauth.md` 21), so a signed-in app is sent none. An edge event is delivered only where `GET /edges/{id}` would answer the credential, read on the edge type and on the source item's type (19). The credential is read as it stands at each attempt, a signed-in app's as its grant's consented scopes stand, so one narrowed after the event narrows a pending retry, and an event it may no longer read is settled unsent. `compliance/webhooks.test.ts › delivers to a credential that reads part of what is stored only that part`, `› delivers only the extension namespaces the credential may read`, and the edge, mark and retry halves in the server's own `webhooks/delivery.test.ts`, the narrowed grant in `webhooks/grant-owner.test.ts`.
24. **A subscription is deleted with its credential, and a pending delivery stops with its subscription.** Revoking a key deletes its subscriptions, and revoking a signed-in app's grant, by any door or by retirement for inactivity, deletes the grant's, in the same write; so a person who reconnects the same app starts with none, and their pending retries are settled unsent. A key that expires, or that no longer holds `webhooks.manage`, delivers nothing more, retries already pending included. Deleting a subscription, pointing it at another URL or turning it off settles its pending deliveries unsent, so none goes to the old address. A delivery settled unsent is recorded with `succeeded: false` and the reason in `error`. `compliance/webhooks.test.ts › stops delivering once the credential that registered it is revoked`; a retry cannot be held pending over the wire, and a deleted subscription answers every caller as one never registered, so the pending half and the deletion are asserted in the server's own `webhooks/delivery.test.ts` and `webhooks/grant-owner.test.ts`.
25. **A webhook reaches only public addresses.** Its URL must be `http` or `https` and carry no credentials, or the create and update doors answer `400 validation_error`; a host written as an address that is not public, loopback, private, link-local, unique-local, carrier-grade NAT, unspecified or any other special range, an IPv4 address written as IPv6 judged as the IPv4 address it carries, is refused the same way. A name is resolved at each attempt, and the connection opens only when every address it resolves to is public, and to the address that was checked, so a second resolution cannot move it. A redirect is not followed: the delivery is settled failed with the redirect's status. A delivery refused an address is recorded with `error` saying the receiver's address is not public, and the receiver is never contacted; no recorded failure names the address or port tried. An operator whose receivers run on a private network allows them with `MARFA_WEBHOOK_ALLOW_PRIVATE_ADDRESSES=true`, which the run's own server sets because every other fixture's receiver is on loopback. `compliance/webhook-addresses.test.ts › refuses a subscription naming a loopback, private or link-local address`, `› sends nothing to a name that resolves to loopback, and records why`, `compliance/webhooks.test.ts › refuses a URL that is not http or https, or carries credentials`, and the redirect, the pinned address and every path that sends in the server's own `webhooks/outbound-http.test.ts` and `webhooks/delivery-census.test.ts`.
26. **A signing secret is at least 32 characters.** A shorter one, the empty string included, answers `400 validation_error`; one left out is generated. `compliance/webhooks.test.ts › refuses a secret shorter than 32 characters, the empty one included`.
