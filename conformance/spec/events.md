# Events

`GET /events` is a server-sent event stream of every mutation, resumable by cursor, and outbound webhooks deliver the same events to a URL.

The ordinary stream below remains available. A working copy uses the stricter copy stream in `read-views.md` 1 and 2, whose tuple and final marker certify the view it materializes.

## The stream

1. A subscription with a bearer credential answers `200 text/event-stream`; without one, `401` in the standard envelope. `compliance/events-contract.test.ts › opens with a stream_cursor frame naming the log head`, `› refuses a subscription with no credential`, `compliance/unauthenticated.test.ts › answers 401 unauthorized on each of them`.
2. The first frame is `stream_cursor`, carrying no `id:` and a `cursor` equal to the id of the last event the log holds; a client resuming from it sees what a live subscriber would have. **Once the prologue is over the stream says so**: a `stream_live` frame, carrying no `id:` and a `cursor` at or past the announced head, follows the replay and the live frames held while it ran, and precedes every frame after them; a stream opened with no cursor sends it straight after its announcement. A frame the filter or the credential withholds is not written at all, so the frame that would show the announced head reached can be one a subscriber is never sent; the marker is what tells such a subscriber it has caught up, and its cursor, the furthest position the stream knows, is one it may resume from without being sent again what the replay covered. The cursor is `null` only where no position is known, a head read that outran its budget with nothing to replay. **A replay writes as it reads**: it gives the process a turn between its reads of the log, so what it has written reaches the wire and other requests are answered while it runs; frames published meanwhile are held for after it, and where they outrun the hold the replay reads on past them and sends them itself, ending short (`stream_incomplete`) only where one of them is a row it cannot read, whose live copy was its one carrier; and one that has written nothing for a second says it is still reading with a `: replaying` comment after its next read, so a subscriber that ends on silence is not told the replay finished while it reads rows it withholds (the server's own `routes/events.test.ts`). A stream that ends short, on `stream_incomplete`, `catchup_too_old` or `cursor_ahead`, never sends it. `compliance/events-contract.test.ts › opens with a stream_cursor frame naming the log head`, `sync/stream-contract.test.ts › announces a cursor a client can resume from`, `sync/stream-contract.test.ts › marks the end of the replay with a cursor a filtered reader can resume from`.
3. `Last-Event-ID` resumes from a cursor, and every retained event after it is replayed. **A cursor is an event id the log issued.** A `Last-Event-ID` that is not one written as the log writes it, a decimal number with no sign, spaces, leading zeros or other base and no larger than `9223372036854775807`, answers `400 validation_error` with `details.errors[].path` naming `Last-Event-ID`, rather than being read as no cursor; an empty one is no cursor, as an SSE client holding no id sends it. A cursor past the log's head is one the log never issued, which is what a client holds after the instance is restored behind it: the stream answers a terminal `cursor_ahead` frame carrying `requested` and `head` and no `id:`, and closes, rather than replaying from it and skipping every new event up to its number; the client re-reads state from the API, as for `catchup_too_old`. **A cursor is too old only when the event after it is no longer retained: the log's oldest retained id is greater than the cursor plus one.** Then the stream answers a terminal `catchup_too_old` frame carrying `min_retained_id` and `requested`, and closes; so does a replay whose next events the sweep retires while it reads, rather than replaying over the gap. A cursor of `0` against a log whose first event is `1` is a client exactly in step, because a cursor names the last event applied and not the first one wanted, and it is every device that hydrated an instance with an empty log. **Retention retires a prefix of the log: an event is retired only with every event before it, never while its own stamp is within the retention, and never the newest event.** A row is stamped before its insert waits for the log's writer, so stamps need not follow ids, and the sweep cuts by id below the oldest row still within the retention; a log once written keeps at least its newest event, so the oldest retained id is always there to check and is the one boundary a reader has to. A row stamped ahead of the clock, which a clock put back leaves, holds back every row above it until its stamp ages, since retiring around it would leave a hole. The server's own `storage/sqlite/event-log-store.test.ts` asserts the prefix over a log whose stamps are out of id order or ahead of the clock, and `routes/events.test.ts` the refusal of a cursor behind a log retired to its newest event and of a replay the sweep overtakes after its cursor was checked. The stale case cannot be arranged over the wire: a request can shorten the retention to an hour and run the sweep (`housekeeping.md` 3), but cannot make an event older than an hour, so it is asserted where a row can be retired, in the server's own `routes/events.test.ts`. **Ids are issued in commit order, and frames are delivered in that order, edge frames beside item frames.** An event's id is assigned by the insert that commits it, under the log's single writer, so no lower id reaches the log after a higher one, and the stream sends nothing ahead of a frame still waiting on the read that decides whether the subscriber may see it. A reader that closes and later resumes from the last id it received therefore sees every event after it exactly once. The one exception is a stored event whose payload the server can no longer read: it is not replayed, and a subscriber connected when it was published receives its live copy after the replay, behind higher ids, because that copy is the one carrier the event has left (`routes/events-replay-dedupe.test.ts`). The order across both kinds is asserted in the server's own `routes/events-live-order.test.ts`, where a purge announces a row's edges before the row, and `routes/events-delivery-hold.test.ts`, where frames queue behind a credential read still out (20), on the live path and in the prologue's hold. `sync/replay.test.ts › resolves a type filter through the same subtree the live stream does`, `sync/replay.test.ts › carries a bulk write, so a catch-up after an import is complete`, `compliance/catchup-too-old.test.ts › replays from a cursor of zero when the log begins at one`, `sync/resume.test.ts › a reader that closes at the head and resumes from its last id misses nothing and repeats nothing`, `compliance/events-contract.test.ts › refuses a cursor that is not a decimal event id`, `› refuses a cursor past the log's head with a terminal cursor_ahead frame`.
4. `type` narrows the stream to a type and its subtree, comma-separated up to ten; `*`, an entry outside the identifier grammar and more than ten entries answer `400 validation_error`; `edges=none` withholds edge events while item events still arrive, `edges=all` delivers them, and any other value answers `400`. `compliance/events-contract.test.ts › refuses a wildcard type filter, a type outside the grammar, an unknown edges value and more than ten types`, `› withholds edge events under edges=none and announces them under edges=all`, `sync/replay.test.ts › resolves a type filter through the same subtree the live stream does`, `sync/stream-contract.test.ts › delivers edge events to a stream filtered by item type`.
5. A write is announced after its transaction commits; a write that rolls back announces nothing. `sync/post-commit.test.ts › a write that rolls back announces nothing, while one that commits does`. **A change and its event are written together**: the event row is written inside the transaction that makes the change, on every door that writes an item, an edge, tags or extensions and in the bulk-action job (the `trash-purge` housekeeping job announces nothing of what it removes), so a change that commits is in the log and one that does not is not, and the log's ids follow the order the changes committed. A subscriber on the instance is told once the transaction commits. Whatever a door reads for its answer it reads inside that transaction too, so a failure anywhere before the answer undoes the change, and **a change that committed is never answered with a failure**: a `5xx` tells the caller nothing was written, so it sends the change again, and a retry of a change that had in fact committed would write it twice. No idempotency key catches it: a door that takes one releases it on a `5xx`, and the bulk doors take none. Nothing a fixture can cause fails between a write and its answer, so the server's own suite injects it: every write door, its event refused by the log, writes nothing (`packages/server/src/routes/rollback-event-doors.test.ts`), and a write whose answer fails after its event was written is undone and written once by its retry (`packages/server/src/routes/committed-write-answer.test.ts`).
6. Writes continue while a subscription is open. `compliance/edge-events.test.ts › accepts writes while an event stream is open`.

## The vocabulary

7. Item events are `item.created`, `item.updated`, `item.deleted`, `item.restored`, `item.purged` and `item.state_changed`, each carrying `event_type` and `item`; a tag write and an extension write are both `metadata.changed` carrying `item` and `metadata`, whatever the namespace, and every frame carrying `metadata` carries only the extension namespaces the subscriber may read (`keys-and-oauth.md` 21). **A frame says what a cascade did.** The `item` of an `item.deleted`, or of an `item.purged` from the single door or a bulk purge, for a row a cascade trashed carries `trashed_by_cascade` and `trashed_with` (`items.md` 26), and an `item.restored` for a row another row's restore brought back carries `restored_with` beside `item`, naming that row (`items.md` 27); a frame for a row trashed or restored on its own, or a `system.*` row a cascade revokes, carries none of them. **A frame names another row only to a subscriber that may read its type**: `trashed_with` and `restored_with` are left out of the frame sent to any other, while `trashed_by_cascade` reaches every subscriber the frame reaches. The log stores one frame and each subscriber is answered from it when the frame is sent, so a replay from a cursor answers a subscriber exactly as the live frame did. `sync/identity.test.ts › keeps the id a client mints for an item, on the row and on the event`, `sync/deletions.test.ts › announces a purge, so a client offline across it learns the row is gone`, `compliance/events-contract.test.ts › announces item.restored when a trashed item comes back`, `› announces item.state_changed on a lifecycle transition`, `› announces metadata.changed on a tag write`, `› announces metadata.changed on an extension write under any namespace`, `› carries on a metadata.changed frame only the extension namespaces the subscriber may read`, `compliance/cascade-marks.test.ts › marks a row a cascade trashed with the row named, and no row trashed on its own`, `› names the row trashed only to a key that may read its type, and says a cascade took the row to any key that reads it`, `› names the row whose trash took it on the purge of a row a cascade trashed`, `› names the row whose trash took it on each row a bulk purge purges, only to a key that may read its type`, `› marks no row a cascade revokes rather than trashes`, `› names the row restored on each row its restore brings back, and not on the row itself`, `› names the row restored only to a key that may read its type`, `› names the row moved on each row a transition out of the bin brings back, only to a key that may read its type`, `› names the row moved on each row a bulk transition out of the bin brings back, only to a key that may read its type`.
8. Edge events are `edge.created`, `edge.updated` and `edge.deleted`, each carrying `event_type`, `edge` and `source_type`, the type of the edge's source item when the event was published, which is what decides who is told about it (19). An `edge.deleted` for an edge a purge took, on the single door or a bulk purge, also carries `purged_with` beside `edge`, naming the purged item (`edges.md` 17); an edge deleted any other way carries none, live or replayed. `compliance/edge-events.test.ts › SSE delivers edge.created and edge.deleted`, `› carries the source item's type on every edge frame`, `compliance/events-contract.test.ts › announces edge.updated when an edge's properties change`, `sync/identity.test.ts › keeps the id a client mints for an edge`, `compliance/cascade-marks.test.ts › names the purged item on each edge its purge took, and on no edge deleted by its own door`, `› names the purged item on each edge a bulk purge took`.
9. A bulk write reaches the log like a single write. `sync/replay.test.ts › carries a bulk write, so a catch-up after an import is complete`.
10. A repeated create under an id already used, and a repeated request under an `Idempotency-Key`, announce nothing the second time. `sync/acknowledged.test.ts › answers an item repeat with the stored row and announces nothing`, `› answers an edge repeat with the stored row and announces nothing`, `sync/idempotency.test.ts › answers a repeated create with the first result rather than a second row`.
11. `stream_incomplete` ends a stream that can no longer deliver what it opened with, carrying `reason` and the `cursor` of the last event it sent, and no `id:`: everything after that event is still in the log, so the recovery is to reconnect from it. It has six reasons. `credential_ended` (20) and `reader_behind` (21) are provoked over the wire and asserted there, and `server_stopping` (`instance.md` 17) by stopping the server, which `compliance/stream-shutdown.test.ts` does to a server of its own; `replay_failed`, `backlog_overflow` and `live_delivery_failed` are server-side failures nothing over the wire provokes, so they are unasserted (`coverage.md`). `stream_cursor`, `stream_live`, `catchup_too_old` and `cursor_ahead` are the stream's own frames beside it, and none of the five carries an `id:` but `catchup_too_old`, whose id is the oldest retained.

## Outbound webhooks

12. `POST /webhooks` with a `url` and `events` from the vocabulary above answers `201` with the subscription and its `secret` in plaintext, once; later reads redact the secret to its last characters. `compliance/webhooks.test.ts › registers a subscription and returns the secret once`.
13. A matching event is delivered to the URL as JSON with mandatory `event_type`, `event_id` (the originating committed event-log ID as a canonical decimal string), `delivery_id` (the stable queued delivery ID), and a fresh per-attempt ISO `delivered_at`, plus the payload, as the subscription's credential may read it (23), with every mark of statements 7 and 8 that credential may read where the frame carries it, `trashed_with` and `restored_with` included, an `X-Marfa-Event-Type` header, and an `X-Marfa-Signature` of the form `t=<unix seconds>,v1=<hex sha256>` where `v1` is the HMAC of `<t>.<raw body>` under the secret; the delivery is recorded at `GET /webhooks/{id}/deliveries` with `status` (`pending`, `success`, `dead_letter` or `canceled`), its last accepted HTTP `status_code` and `error`, and cumulative accepted-outcome ordinal `attempt`. A permanent refusal records the observed status/count and reason; success clears an earlier error, and `succeeded` derives from the same lifecycle status. The body IDs survive retry and process restart and the event ID equals the stream cursor. Rows are newest first, and the log pages by cursor like every list: a page the `limit` cut answers a `next_cursor`, and the walk reaches every delivery once. `compliance/webhooks.test.ts › delivers a matching event to the URL with a verifiable signature`, `› pages its delivery log by cursor, every delivery once`, `compliance/edge-events.test.ts › delivers edge.created and edge.deleted to a webhook with a valid signature`, `compliance/cascade-marks.test.ts › delivers the item.deleted of a row a cascade trashed with its mark, and the row trashed's own without one`.
14. An event outside the subscription is not delivered. `compliance/webhooks.test.ts › does not deliver an event outside the subscription`.
15. `events: ["*"]` is refused `400 validation_error`, with `details.errors[].path` naming the position of the offending entry rather than the body: `*` is not in the vocabulary either door publishes, and dispatch matches a subscribed name against an event's own literally, so a stored wildcard would be a subscription that could never fire. A named subscription on the same event is delivered to in the same run, which is what holds the refusal to the door rather than to dispatch. `PATCH /webhooks/{id}` refuses it on the same terms and leaves the stored list where it was. `compliance/webhooks.test.ts › refuses a wildcard subscription while a named one on the same event is delivered`, `› refuses a wildcard on the update door, leaving the stored events alone`.
16. `type_filter` is one trimmed item subtree pattern using the stream's dotted-descendant and declared-inheritance rule. Qualified wildcards and syntactically valid unregistered identifiers are accepted; global `*`, malformed identifiers and comma-separated alternatives answer `400 validation_error` with `details.errors[].path` naming `type_filter`. Blank or whitespace means no filter; null clears it on update. A refused update preserves stored configuration. Edge events are independent of this item filter and remain subject to their event-selection and credential/edge reach checks (23), including filtered edge-only subscriptions. `PATCH /webhooks/{id}` changes `url`, `events`, `type_filter` and `active` in place, each reading back; `DELETE` removes the subscription and every door answers `404 webhook_not_found` for it afterwards. `compliance/webhooks.test.ts › normalizes one item filter and preserves it after refused updates`, `› updates the url, events, type filter and active flag in place`, and the subtype/edge reach controls in `webhooks/follow-up.test.ts`, `› deletes a subscription and answers 404 for it afterwards`, `› answers 404 for an unknown subscription on every door`.
17. An event name outside the vocabulary, or a body without `url` or `events`, answers `400`; a key without `webhooks.manage` answers `403` on every door; no credential answers `401`. `compliance/webhooks.test.ts › refuses an event name outside the vocabulary`, `› refuses a body with no url or no events`, `› refuses a key without webhooks.manage`, `› refuses every door without a credential`.

**Delivery history follows the effective audit retention, including its `/config` override.** A dead-letter delivery keeps its replay frame and original address while within the effective audit retention measured from its original `created_at`, so its owner can explicitly redeliver it. Success and cancellation discard the frame and address. A pending delivery still retrying stays whatever its age; reopening a failed row never restarts its retention clock. Aging is checked in the server's own `webhooks/delivery-retention.test.ts` because a public fixture cannot age a row.

## Audit

18. The server MUST record every write at `GET /audit` with the acting key, action, resource type and ID, and details, subject to the operational exemptions below.

    When a domain change commits, the server MUST commit its audit record in the same database unit.

    When a credential change commits, the server MUST commit its audit record in the same database unit (`keys-and-oauth.md` 47).

    The server MUST exclude credential values, passwords, verification identifiers, authorization codes, private signing keys, and session cookie values from audit metadata.

    When the server returns success for a domain change, its audit record MUST be readable.

    If audit insertion fails, the server MUST roll back the represented database unit and its events.

    When an atomic bulk page commits, the server MUST record one aggregate audit entry.

    When a best-effort page commits an entry, the server MUST record an audit entry containing the page's shared `details.operation_id` and the entry's input `details.index`.

    When a best-effort entry is an acknowledged duplicate, skipped or refused, the server MUST NOT record a mutation for that entry.

    When the server records an atomic page summary, it MUST include the skipped count.

    When an asynchronous bulk job is enqueued, the server MUST record the enqueue.

    When cancellation changes an asynchronous bulk job's status, the server MUST record the cancellation.

    When an asynchronous bulk job commits a resource-changing chunk, the server MUST record the chunk.

    When blob or archive work requires external bytes, the server MUST stage those bytes before opening the database unit that records them.

    When an archive restore commits, the server MUST commit an audit record for each type registration, each edge-type registration and each batch of blob rows in the same database unit as the restore's own record.

    If an archive restore does not commit, the server MUST NOT retain any of those audit records.

    When automated enrichment, retention or blob work changes a resource, the server MUST record a system audit entry without an acting key.

    The domain audit requirement excludes connector heartbeats, run reports, holds, checkpoints and agreements; inbound receipt bookkeeping; delivery attempts; and internal scheduler, authentication-use and telemetry bookkeeping. Schema seeding, structural generation and stable instance identity initialization are startup bookkeeping.

    When an authorized export is accepted, the server MUST persist a standalone `export.run` observation before opening the stream.

    If the export observation cannot be persisted, the server MUST refuse the export before opening the stream.

    Rationale: Earlier best-effort entries remain committed when a later entry fails. An archive restore's preparation commits with its rows (`search-and-filters.md` 64 and 67), so a refused restore leaves no preparation behind. The export observation represents an extraction attempt and does not certify completion of streaming.

    Native tests: `routes/audit-atomicity.test.ts`, `routes/bulk-audit.test.ts`, `housekeeping/external-audit.test.ts` and `storage/audited-transaction.test.ts` exercise refused audit insertion, rollback, success, no-op and uncertain commit controls. The external audit suite exercises both export formats with successful and refused audit insertion.

    The listing filters by `action`, `resource_type` and `resource_id`, bounds by `created_after` and `created_before` (both exclusive of the row's own instant, and both refused when they are not an instant), paginates by cursor, needs `audit.read`, refuses a query key it does not declare, and refuses no credential. `compliance/audit.test.ts › records a write with the acting key, the resource and the action`, `› exposes each committed best-effort entry immediately with one operation context`, `› filters by action and resource type with an excluded control`, `› bounds by created_after and created_before, both exclusive`, `› reads a bound at any precision, and refuses one that is not an instant`, `› paginates with a cursor and delivers every row once`, `› refuses an undeclared bound rather than answering the whole trail`, `› refuses a key without audit.read`, `› refuses a request with no credential`, `compliance/edge-events.test.ts › audit log records edge mutations with edge_id in resource_id`.

## Permissions

19. **A subscriber is told about an edge only where the single read would answer it.** Every `edge.created`, `edge.updated` and `edge.deleted` frame is held, per subscriber, to the two permissions `GET /edges/{id}` asks for: read on the edge type, and read on the source item's type (`edges.md` 23). `edges=none` is a subscriber's own parameter and narrows nothing else. A frame failing either is withheld rather than closing the stream, and a replay from a cursor withholds exactly what the live path does, because a stored frame is the same disclosure reached through a catch-up. **The source half is asked of the `source_type` the event carries** (8), not of a row read when the frame is sent: a purge announces each edge it took after the row has gone, and the type it carries still says who could read that row, so a subscriber that could not read the purged item is not told about its edges. A frame carrying no source type is withheld from every subscriber, since a source that cannot be classified cannot be shown readable. `compliance/edge-events.test.ts › withholds a live edge frame the credential could not read singly`, `› withholds the same frames on a replay from a cursor`, `› withholds a purged item's edges from a subscriber that could not read it, live and on a replay`.

20. **A stream answers to its credential as it stands, not as it stood when it connected.** The stream reads its credential again before it delivers each batch of frames, live or replayed, and at each heartbeat, every 30 seconds, and every frame in a batch was published before that read began. A key narrowed by `PATCH /keys/{id}` narrows the stream with it: a frame the key may no longer read is withheld from then on. A key revoked or deleted, a key past its `expires_at`, a sign-in's token revoked or past its expiry, and an app disconnected by revoking its grant each end the stream with a terminal `stream_incomplete` whose reason is `credential_ended`, and nothing written after the change reaches it; a reconnect with the same credential is refused `401`, and an app reconnects with the token it refreshed to. `compliance/stream-credential.test.ts › stops delivering a type the key is narrowed away from`, `› ends with credential_ended when the key is revoked, and sends nothing after`; the server's own `routes/events-live-credential.test.ts` covers expiry, a sign-in's token and the heartbeat, which a fixture cannot make pass without waiting on the clock.

## A reader that falls behind

21. **A stream holds at most 4 MiB of frames its reader has not taken, and the one frame that crosses that.** A live frame that finds that much still unread ends the stream with a terminal `stream_incomplete` whose reason is `reader_behind`, and its `cursor` names the last event sent, so the reader reconnects from it and the replay serves the rest. A replay, and the release of the frames held while the stream opened, are paced by the reader instead: each waits for room before every frame it sends, and ends the same way only when the reader has taken no frame for 30 seconds, so a reader taking frames slowly but steadily is waited for. A stream that has ended keeps what it queued for its reader, the terminal frame among it, for 30 seconds, and then lets the queue and the connection go. `compliance/stream-reader-behind.test.ts › is ended with reader_behind once it falls past the bound, and resumes from its cursor`; the server's own `routes/events-reader-behind.test.ts` holds the replay's pacing and the stalls, against a bound small enough to reach without megabytes.

## Whose subscription it is, and where it may send

22. **A subscription belongs to the credential that registered it.** Any credential holding `webhooks.manage` may register one, whatever it may read. Every door answers a subscription only to that credential: to another it is an id nobody holds, `404 webhook_not_found` on `GET`, `PATCH`, `DELETE` and the delivery log, and it is left out of `GET /webhooks`. A signed-in app's subscription belongs to its grant, the app and the person who consented to it, rather than to the token that registered it, so every token of that grant is the same credential and the subscription outlives the token: a refresh, a scope unticked on the consent screen, a replayed refresh token or the end of the browser session a token was issued under each ends tokens while the grant stands. `compliance/webhooks.test.ts › answers a subscription another credential registered as an unknown id on every door`, and the sign-in half in the server's own `routes/webhooks-ownership.test.ts` and `webhooks/grant-owner.test.ts`.
23. **A delivery carries what that credential may read when it is sent.** An item event is delivered only where the credential may read the item's type, and a mark naming another row only where it may read that row's type (7). A `metadata.changed` carries only the extension namespaces the credential may read, as every door answering extension data does (`keys-and-oauth.md` 21), so a signed-in app is sent none. An edge event is delivered only where `GET /edges/{id}` would answer the credential, read on the edge type and on the source item's type (19). The credential is read as it stands at each attempt, a signed-in app's as its grant's consented scopes stand, so one narrowed after the event narrows a pending retry, and an event it may no longer read is settled unsent. `compliance/webhooks.test.ts › delivers to a credential that reads part of what is stored only that part`, `› delivers only the extension namespaces the credential may read`, and the edge, mark and retry halves in the server's own `webhooks/delivery.test.ts`, the narrowed grant in `webhooks/grant-owner.test.ts`.
24. **A subscription is deleted with its credential, and a pending delivery stops with its subscription.** Revoking a key deletes its subscriptions, and revoking a signed-in app's grant, by any door or by retirement for inactivity, deletes the grant's, in the same write; so a person who reconnects the same app starts with none, and their pending retries are settled unsent. A key that expires, or that no longer holds `webhooks.manage`, delivers nothing more, retries already pending included. Deleting a subscription, pointing it at another URL or turning it off settles its pending deliveries unsent, so none goes to the old address. A delivery settled unsent is recorded with `status: canceled`, `succeeded: false` and the reason in `error`, preserving its last accepted HTTP status/count rather than inventing another attempt. `compliance/webhooks.test.ts › stops delivering once the credential that registered it is revoked`; a retry cannot be held pending over the wire, and a deleted subscription answers every caller as one never registered, so the pending half and the deletion are asserted in the server's own `webhooks/delivery.test.ts` and `webhooks/grant-owner.test.ts`.
25. **A webhook reaches only public addresses.** Its URL must be `http` or `https` and carry no credentials, or the create and update doors answer `400 validation_error`; a host written as an address that is not public, loopback, private, link-local, unique-local, carrier-grade NAT, unspecified or any other special range, an IPv4 address written as IPv6 judged as the IPv4 address it carries, is refused the same way. A name is resolved at each attempt, and the connection opens only when every address it resolves to is public, and to the address that was checked, so a second resolution cannot move it. A redirect is not followed: the delivery is settled failed with the redirect's status. A delivery refused an address is recorded with `error` saying the receiver's address is not public, and the receiver is never contacted; no recorded failure names the address or port tried. An operator whose receivers run on a private network allows them with `MARFA_WEBHOOK_ALLOW_PRIVATE_ADDRESSES=true`, which the run's own server sets because every other fixture's receiver is on loopback. `compliance/webhook-addresses.test.ts › refuses a subscription naming a loopback, private or link-local address`, `› sends nothing to a name that resolves to loopback, and records why`, `compliance/webhooks.test.ts › refuses a URL that is not http or https, or carries credentials`, and the redirect, the pinned address and every path that sends in the server's own `webhooks/outbound-http.test.ts` and `webhooks/delivery-census.test.ts`.
26. **A signing secret is at least 32 characters.** A shorter one, the empty string included, answers `400 validation_error`; one left out is generated. `compliance/webhooks.test.ts › refuses a secret shorter than 32 characters, the empty one included`.

27. **Outbound scheduling resumes from a durable partial event position.** Every considered subscription's queue row or skip commits with the exact position through that event's ordered subscriptions. The full event checkpoint advances only once fan-out is complete. A scheduling failure, process crash or lost commit response therefore cannot skip unfinished work or create a second set of committed queue rows. A run fetches at most 128 consecutive event payloads and examines at most 50 subscriptions in aggregate, including relevant configuration and reach skips, inserting at most 50 deliveries. Ordered storage selection excludes valid subscriptions born at or after the considered event, while including invalid or ahead-of-head births for visible failure. The row limit bounds projected results, not SQLite internal scan work. Completed events may advance together within these budgets; partial fan-out resumes on the next ordinary job tick. An exactly full subscription page remains in progress until the next bounded read proves exhaustion. Scheduling only queues durable deliveries and wakes the existing tracked attempt job after commit; it does not await receiver I/O, so a held receiver cannot delay later scheduling batches or the listening socket during startup. At most 50 due deliveries are attempted concurrently by one tracked run; a saturated batch wakes the same job to drain remaining due work. Wakes during a run survive its settlement, and an idle wake consumed by a subsequent claim does not request another run. Shutdown waits for tracked attempts. HTTP attempts retain their existing retry and cancellation rules; receiver delivery is not exactly once. `packages/server/src/webhooks/scheduling-independent.test.ts › queues beyond a held attempt batch and preserves a wake during the active poll`, `packages/server/src/storage/sqlite/housekeeping-store.test.ts › keeps a wake after %s despite an earlier idle snapshot`, `› consumes an idle wake in a subsequent %s`. `webhooks/cursor.test.ts` holds rollback, lost response, concurrent connections and skip-only pages; `webhooks/cursor-crash.test.ts` kills owned server processes before scheduling and during partial fan-out, then proves recovery after reopening their databases.
28. **A subscription starts after the event-log head at its creation.** It receives no earlier events merely because scheduling lagged. Unexamined subscriptions use current configuration and current owner standing and read reach; committed skips and deliveries are not revisited. Deleting a subscription does not invalidate the saved exclusive immutable-ID position. A subscription created between pages is excluded by its birth watermark. The event's logged `enable_fanout` remains authoritative, including no-fanout restore events, which drain without deliveries. The internal checkpoint and birth watermark are omitted from public subscription JSON. `webhooks/cursor.test.ts` holds birth, deletion, configuration changes and no-fanout progress.
29. **Recovery is limited to retained history.** Event retention is unchanged. A checkpoint ahead of the local log, a missing checkpoint on a populated instance, inconsistent event history or a retention gap fails the `webhook-schedule` housekeeping job visibly without resetting or advancing its position. This includes a partially scheduled event retired before its remaining subscriptions are considered; already queued deliveries retain their attempt lifecycle. A scheduling transaction separately targets 8 MiB of scanned event payload and 8 MiB of copied queued payload. It stops before considering the next event or inserting the next delivery that would exceed its target, while allowing one accepted oversized first event and first delivery to progress. These are work targets, not absolute memory caps: a pass measures one complete candidate payload at a time, parsing and HTTP can allocate more, and a configured-valid oversized payload is allowed. `webhooks/cursor.test.ts` holds unchanged failed position, partial retention loss, payload budget and the oversized exception through ordinary accepted writes.

30. **Webhook retries preserve accepted outcomes and can be explicitly reopened.** A cycle has eight attempts, with seven scheduled waits of 1, 5, 25, 125, 625, 3125 and 15625 seconds, totaling 19531 seconds. A valid `Retry-After` is a minimum against the ordinary backoff, capped at five minutes; shorter hints cannot shorten the ordinary schedule. The ordinary retry poll cadence remains 30 seconds; committed scheduling and saturated batches may wake it sooner, but only due rows with eligible claims are attempted. Poll cadence, attempt duration and process downtime can delay dispatch. Redirects and permanent 4xx responses other than 408 and 429 give up immediately. A fresh claim token fences every accepted outcome and per-attempt cancellation: an old in-flight completion cannot change another claim or a reopened cycle. The delivery's `attempt` is a cumulative accepted-outcome ordinal, not a census of concurrent or lost HTTP sends. `webhooks/retry.test.ts` checks the schedule with a controlled clock and stale outcomes with explicitly shortened claim timestamps.

31. **Only the subscription owner can queue a retained failed delivery again.** `POST /webhooks/{id}/deliveries/{delivery_id}/redeliver` takes no body and returns the same delivery projection with `202` and `status: pending`, preserving identity and the last accepted outcome until the next accepted completion. It atomically checks the current owner, active subscription, live credential and retained frame, uses the current address and signing secret, and allocates a fresh eight-attempt cycle. Missing or foreign subscriptions or deliveries answer `404 webhook_not_found`; a nonfailed, expired or unavailable frame answers `409 conflict`. Concurrent duplicate requests queue one transition. When explicit redelivery is accepted, the server MUST commit the transition and its `webhook.delivery.redeliver` audit record together. When recording that transition, the server MUST identify the delivery as `resource_id` and the subscription as `details.webhook_id`. If redelivery is refused or duplicated, the server MUST NOT add an audit record. If audit insertion fails, the server MUST leave the failed delivery unchanged. A failed frame stays until the original effective audit retention expires; reopening never restarts retention. Success and cancellation discard replay frames. Per-attempt live credential and read-reach checks still apply. `webhooks/retry.test.ts` holds ownership, grant, retention, malformed frame, concurrent reopening and narrowed reach controls; `compliance/webhooks.test.ts › redelivers a retained failed row to the current address with stable identity` proves actual signed receiver delivery.

32. **An answered outbound request releases its response without losing the answer.** Webhook and heartbeat responses are canceled before completion, including non-2xx responses. If cancellation fails, an owned abort releases the response; the observed HTTP status remains authoritative and cleanup failure is logged separately using safe facts. `webhooks/response-cleanup.test.ts` uses owned finite and streaming HTTP receivers, including a controlled cancellation failure, and proves their release for 2xx and non-2xx responses.

## Working-copy certification

33. **A copy stream announces and certifies its view with no-id tuple markers.** Exactly `GET /events?edges=all&copy=1` selects it. Bootstrap sends no resume headers; resume pairs one canonical `Last-Event-ID` with one opaque `X-Marfa-Read-View`. Its `stream_cursor` and `stream_live` bodies each contain exactly string `event_type`, `cursor`, `instance_id` and `read_view`; live follows completed replay and held release, at or past the announced head, resume cursor and last delivered event. Copy grammar refuses empty, malformed, duplicate or unpaired proofs and alternate query grammar before the stream starts, while ordinary stream rules remain unchanged. `read-views.md` 1 and 2 states the full grammar. `compliance/read-views.test.ts › bootstraps and resumes with one instance, cursor and opaque read view`, `› rejects every alternate copy grammar before starting a stream`.
34. **A copy stream carries required item-set classification beside every item or metadata frame.** `listed` is a JSON boolean under the effective source filter, before local type or tier slicing; direct source-excluded ID reads may still succeed with `listed:false`. Edge frames retain their existing shape. Ordinary content and metadata writes retain the view. `read-views.md` 3, 6 and 9 states the projection and snapshot rules. `compliance/read-views.test.ts › classifies source-excluded direct items and neighbors without admitting them to a listed page`, `› keeps the read view across content, metadata and write-only authority changes`, `› ends an open copy stream with a no-id detail-free terminal after a structural change`.
35. **A changed copy view ends delivery before the changed data can be adopted.** Before SSE starts it answers `409 read_view_changed` in the exact standard envelope with no certificate. After SSE starts it sends exactly one no-id `read_view_changed` frame with `{"event_type":"read_view_changed"}`, then closes without another frame, cursor, live certificate or policy detail. This terminal is separate from environmental `stream_incomplete` and its existing `credential_ended` reason. `read-views.md` 8 and 9. `compliance/read-views.test.ts › refuses stale HTTP and resume proofs before resource lookup after retype or read narrowing`, `› ends an open copy stream with a no-id detail-free terminal after a structural change`.

36. **A live stream never sends an event at or below an id it has already sent or replayed.** Live events reach a stream in id order, so one at or below that id is a repeat: an archive restore tells subscribers its events after its commit (`search-and-filters.md` 72), by which time a stream opened since may have replayed them from the log. A client resuming by `Last-Event-ID` therefore sees each event once. `packages/server/src/routes/archive-restore-bounds.test.ts › sends a stream opened while the events are read back each event once`, `› sends a copy stream resumed while the events are read back each event once`.
