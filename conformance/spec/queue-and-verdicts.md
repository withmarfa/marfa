# The queue and its verdicts

A device does not write to the server directly. It writes to its working copy, queues the write, and drains the queue when it can. Every queued write is answered with one verdict from a closed set, and the verdict says what became of the write and what the device may do next.

`device.md` states the working copy the queue writes into. The server behavior a verdict is read from is `versions.md`, `items.md` and `errors.md`.

## The queue

1. The queue is persisted and ordered. A write survives the process that made it, and a drain sends writes in the order they were queued; a write to a row or an edge waits for an answer to the write ahead of it to the same one, across a failure too (42). `device/queue.test.ts › sends queued writes in the order they were queued`, `› keeps the queue across a restart`, `› sends a delete of a row only once the edits of it ahead are answered`.
2. **Every write carries the version it read.** It is required on an update: an update queued without one is refused before it is sent, because a version-less update is a write that overwrites whatever it finds. The copy projects item-update nulls as the server does (`items/update-null-merge` and `items/update-null-replace`): an optional null leaves its field untouched under a merge, so it clears nothing, and a null is absent under a replace, which is how an edit clears a property (45). The queued request retains the caller's values for server validation. A delete captures the version and the complete content the working copy holds, and sends that version as its precondition. An earlier accepted create or edit from this device may advance an unsent delete only when its answer confirms that content; an answer carrying unseen content cannot authorize its deletion. A new create confirms the server-owned fields of its local draft. Once a delete has been sent, its version and idempotency key never change, even if its answer was lost. It is optional on a create, and a create that carries one is conditional on it where its `(source, source_id)` resolves a live row: there the server answers it exactly as it answers an update. A repeated `id`, and a natural key resolving a trashed row, are acknowledged rather than written, so neither has a precondition to fail. `device/queue.test.ts › refuses an update queued with no version`, `› sends a create with the version it was based on`, `device/versioned-deletes-live.test.ts › guards a queued delete through %s`, `› replays a lost delete answer without deleting a restored newer item`, `device/null-properties-live.test.ts › leaves a property a merging null names, as the server does`.
3. Every queued write carries an idempotency key, minted when the write is queued and never changed. A retry re-sends the same key, so a write whose answer the device never saw is answered from the server's record rather than written a second time. `device/queue.test.ts › retries under the key it was queued with, and is answered from the record rather than written twice`.
4. **A write waits for the write it depends on.** An update, a delete or an edge write naming a row whose create the server has not taken is held rather than sent, because the server has no such row and would refuse it. A create is not taken while it is unanswered or blocked, because a blocked write is waiting still (35): a write to its row sent in the meantime is refused `item_not_found`, and the copy then forgets the row it was queued against. `device/queue.test.ts › holds a write whose create has not been answered`, `device/classification.test.ts › blocks a create naming a source its key does not claim, and sends it once the key does`.
5. A device sends `conflict=auto` on every update. It resolves nothing itself (`device/edit-sends-named`); the flag is how the server is asked to resolve within its own transaction rather than refusing and leaving two writes where one is atomic. `device/queue.test.ts › sends every update with the server asked to resolve`.
6. A drain reports the verdict of every write it answered, sent or refused unsent — its id, its kind, the row or edge it names and, for a refusal, the refusal read into its parts (48) — unless an answer on another contract or a renewal failure ends it, which it reports as an error instead while the queue holds the verdicts it reached (`device/contract-drain-ends`); and the queue reports what it still holds with each row's verdict and reason. It is answerable before a hydration, because a queue is a record of what a caller asked for rather than a view on the copy, and the moment a caller most needs it is the moment the server cannot be reached. A row the server has not answered carries no verdict, which is the absence of one rather than a seventh. **Its counts say what the server answered**: the writes the server answered this pass, whatever it answered; the writes it held for a write ahead (24); and the writes it could not deliver, the one an environmental failure met and every write left unsent behind it that is not held (17), and an upload whose bytes could not be opened (`device/upload-bytes-unopened`), with why in words where the server could not take them; the writes it gave a verdict without sending, refused for a write they waited on (16) or for bytes no longer held, or settled by another write's answer (39, 40); and the writes whose request could not be made, each counted (19) and waiting for the next drain. Every write a pass comes to is in one of the five, but those a refused credential parks (20), which the drain counts in saying why it stopped. A write that went out and met no answer is never counted as answered: a drain that reported it as sent would read the same whether the server took it or could not be reached, so an app could not tell offline from saved. `device/queue.test.ts › reports a verdict for every write it sent`, `› reports an empty queue on a store that has never been written to`, `device/verdicts.test.ts › refused: reads the server's code, message, fields and missing grant into the refusal`, `device/classification.test.ts › counts only the writes the server answered, and says why the rest were not delivered`, `› counts the writes it settled without sending apart from those the server answered`, `device/folders.test.ts › folder rebase accounts for every unmade request`, `› folder rebase accounts for writes refused in its later pass`. The CLI preserves this report on stdout and exits 3 for an unavailable pass or undelivered writes, 5 for a credential-stopped pass (taking precedence), and 0 otherwise. A completed pass with refused writes has a distinct plain-text refusal count. Report outcomes print no additional error envelope. A direct renewal error instead prints its typed error on stderr with empty stdout; it invents no verdict for the current write and preserves earlier answers, the current request and idempotency key, and refusal counts. A local signed-out state or unavailable credential store carries no server status. Plain queue output describes only unresolved dependencies as waiting; stored dependency history stays unchanged. `device/cli-outcomes.test.ts › keeps the complete $label drain report with exit $exit`, `› preserves answered writes before an interrupted later write`, `› reports completed refusals separately and keeps exit zero`, `device/queue.test.ts › says in words which writes hold a queued write`.

## The verdicts

7. Every queued write carries exactly one of six verdicts, and the set is closed: `accepted`, `merged`, `conflicted`, `refused`, `blocked`, `dead`. An answer a device cannot classify is a defect in the device, not a seventh verdict. `device/verdicts.test.ts › answers every write with one of the six verdicts`, `device/queue.test.ts › reads the answer its own door gives, not an item's`.
8. **The three verdicts a `2xx` can carry are told apart by one field.** A successful answer either reports a resolution or does not, and a resolution either names a conflicted copy or does not; those two questions decide between `accepted`, `merged` and `conflicted`, and a device reads them rather than comparing the row it got against the row it imagined. Comparing rows cannot work: every answer carries fields the server stamps and the device never sent. `device/verdicts.test.ts › tells the three successful verdicts apart by the resolution the answer carries`.
9. **`accepted`** — a `2xx` reporting no resolution. The server took the write as sent. The receipt settles the verdict and records the version the write produced. The working copy adopts only a fresh certified read of the row, including the version and fields the server now holds (`device/read-back-keeps-verdict`). A natural-key upsert and a repeat answered from the server's record are both `accepted`: the server took the write, and the receipt does not prove present read access or listing membership. The fresh read replaces the baseline except where the copy holds the row, or for an edge's write the edge, at a later version than the fresh read, or at the same version stamped later than that read (`device/server-row-order`). A catch-up can bring that later version before a repeat's answer arrives, and adopting the older one would take the copy back under the writes since and base the next edit on a version the row has left; the copy keeps the later version, and the edits behind the write still move onto the answer (42). `device/verdicts.test.ts › accepted: adopts the row the server returned`, `› accepted: takes an upsert and a replayed repeat as accepted`, `device/queue.test.ts › keeps the later row a catch-up brought over an older answer replayed after it`, `› keeps the later edge a catch-up brought over an older edge answer replayed after it`.
10. **`merged`** — a `2xx` reporting a resolution that names no conflicted copy. The server applied the write over changes made since, property by property, and the row it returned carries both. The device records the merged verdict and does not send again; a fresh certified read supplies its current baseline, as for an accepted write (9). `device/verdicts.test.ts › merged: adopts the row a resolution returned`.
11. **`conflicted`** — a `2xx` reporting a resolution that names a conflicted copy. The type's policy for a colliding property is to keep both, so the server kept its own value on the row and wrote the losing one to a sibling of the same type tagged `conflicted-copy`. The verdict names the sibling; the working copy obtains a fresh certified baseline for the written row and holds the sibling when a certified read or event places it in the slice. The answer carries only the row written to, so the sibling reaches the working copy with a later event from the stream, not with the answer: a caller reads it once the copy has caught up past that event. `device/verdicts.test.ts › conflicted: names the sibling the server wrote`, `device/verdicts.test.ts › conflicted: the sibling reaches the copy with a later event, not with the answer`. **The sibling's `derived-from` edge to the original (`versions/copy-link`) is held with it**, as every edge from a row the copy holds is (`device/slice-held`), whether or not the copy holds the original: from the event after the sibling's on a catch-up, and with the sibling on a hydration, and it stays when the store is opened again. So a caller finds the original from the copy, and the copies from the original, by reading edges from either end (`device/edges-to`), after a restart as before it. `device/verdicts.test.ts › holds the link with the sibling after the verdict's catch-up, and after the store is reopened`, `› holds the link a catch-up brings where the copy does not hold the original`, `› holds the link a hydration reads with the sibling, where the copy does not hold the original`.
12. **`refused`** — the server refused the write for a reason no retry changes. The verdict carries the server's code verbatim, and the refusal read into its parts (48). It is terminal: the write is not sent again, and the working copy is reconciled back to what the server holds. **The original refusal is recorded before reconciliation.** Until a fresh certified read succeeds, the existing projection stays intact and the read-back remains owed. After checking the captured read view and local generation in the same transaction, the copy removes the settled write's overlay, retains a newer existing baseline over an older response, and overlays work still waiting. Every drain retries pending receipt reconciliation before new writes, without resending the settled request. A certified event or read may settle baseline debt, but cannot discard pending identity adoption or receipt reconciliation. A network failure, `5xx` or `429` retains that debt and the original verdict, body, key and refusal count (`device/read-back-keeps-verdict`). **A refusal the drain made rather than the server is the one exception** — a write held for a dependency that was itself refused or died carries the same verdict without ever having been sent, and a caller may release it (27). `device/verdicts.test.ts › refused: carries the server's code and is not sent again`, `› refused: preserves the local row until a fresh read succeeds at the next drain`, `› refused: keeps the row the copy holds where the read-back answers an older one`, `device/classification.test.ts › will not release a write the server itself refused, dependency or not`.
13. **`blocked`** — the write has stopped until something outside the queue changes. It carries one reason from the closed set in the next section. It is not a failure and not counted toward the ceiling; the drain passes over it and the queue reports it. `device/verdicts.test.ts › blocked: is passed over by a drain and reported with its reason`.
14. **`dead`** — a failure a retry could have cleared was answered the same way until the ceiling was reached. Not sent again until the row is released, but still laid over the copy (35). `device/verdicts.test.ts › dead: is terminal once the ceiling is reached`.
15. A verdict is reported, never acted on. A device meeting `conflicted`, `blocked` or `refused` does not write a resolution of its own; it reports the verdict, the server's envelope and the row it holds, and stops (`device/conflict-blocked`). `device/verdicts.test.ts › reports a conflict rather than resolving it`.
16. A refused create refuses the writes that were waiting on it, and their reason names the write that was refused. Nothing that depended on a row the server never accepted is sent. A create refused because its natural key resolves a row the server holds is the one exception (39): that row exists, so what waited on the create goes to it. `device/verdicts.test.ts › refuses the writes that were waiting on a create the server refused`, `device/queue.test.ts › refuses a create whose natural key names a row, and moves the copy onto that row`.

## Which failures retry, and which do not

The split is the whole of the classification, and it is closed. A device that retries the wrong class either loops on a refusal it will always get or strands a good write behind a network that came back.

17. **An environmental failure retries without limit and is never counted.** A dropped connection, a refused connection, a read that timed out, any `5xx`, a `429`, and any refusal naming no contract are statements about the environment rather than about the write, and every one of them clears without anybody doing anything. Counting them would strand a valid write behind an outage and then need a person to release it. **It ends the pass at once.** The write it met and every write behind it stay queued, unsent this pass and uncounted, for the next drain, a write held for one ahead (24) still reported as held, and the drain says why it could not deliver them (6), passing on the `Retry-After` of a `429`, whether a write or a read met it. A read the drain makes meets the same rule: one a refusal is reconciled against (12), whether owed from an earlier drain or made for this one, and the read of the row a create landed on (39). Gone on to the next write, a drain against a server that cannot be reached would wait out a connection timeout for every write in the queue, and a server that asked for a wait would be asked again at once by every write behind the one it answered. `device/classification.test.ts › retries an environmental failure past the ceiling without counting it`, `› retries a 5xx and a 429 without counting them`, `› ends the pass at the first write the server cannot take, leaving the rest untried and uncounted`, `› ends the pass at a read the server cannot answer, sending nothing after it`, `› passes on the wait a read reconciling a refusal was asked for (contract %s)`, `device/contract.test.ts › takes a refusal that names no contract as the network's, ending the pass uncounted`.
18. **A contract failure does not retry.** A `400`, a `403` and a `404` are `refused` on the first answer, because the same request sent again is the same request. A create's `403` naming a source its key does not claim (40), and a `403` naming a missing grant (51), are about the credential and block instead. **The refusal is the server's only where it names the server's contract** (`device/unnamed-not-server-word` and `device/command-unnamed-refusal`): one naming none is taken as from something in front of it, a proxy, a tunnel or an access gateway, which says nothing of the write or the key, and it is environmental (17), whatever its status, a `401` among them, which then blocks nothing (20). The drain says so naming the status, and that a refusal repeating so while the server otherwise answers is one losing the contract header on the way. Refused on a proxy's word, a write the server never saw would be ended for good; counted, a proxy restarting under a watch that drains each second would take every queued write to `dead` within seconds. `device/classification.test.ts › refuses a contract failure on the first answer`, `› blocks a create naming a source its key does not claim, and sends it once the key does`, `device/contract.test.ts › takes a refusal that names no contract as the network's, ending the pass uncounted`.
19. **A failure that is neither retries, and is counted.** An unparseable write receipt, a recoverable local-store error before a verdict is durably recorded where the store can record the failed attempt, and a key the server reports as still in flight are failures a further attempt might clear. Full storage ends the pass with its typed error without spending this count. A failure after a durable verdict, including a fresh read or its proof, retains that verdict and pending reconciliation without counting another refusal (`device/read-back-keeps-verdict`). This is the class the ceiling exists for, and it is the only one: without it `dead` is a verdict nothing reaches. A recoverable local-store failure before a durable verdict counts against the write that drew it and the pass goes on when the counter can be saved: ended there, the write would be retried uncounted forever and every write behind it would wait on it. `device/classification.test.ts › retries an answer it cannot read, and counts it`, `› retries a key the server reports in flight, and counts it`, `› counts a write whose answer the copy cannot take, and goes on to the next`.
20. **A `401` naming the server's contract blocks the whole queue with the reason `credential_refused`.** It is the one refusal that looks environmental and is not: it clears only when a person replaces the credential. Every queued write carries the same credential, so every one of them parks together and the drain stops rather than working through a queue none of which can succeed. `device/classification.test.ts › blocks the whole queue on a refused credential, and stops the drain`.
21. **`422 idempotency_key_reused` blocks that write with the reason `key_spent`**, on the first refusal. The key has been answered for a different body, so it is the key that is spent rather than the write; retrying would spend the ceiling on refusals that are all the same refusal and then park the row under a reason naming the wrong cause. Re-sending the same key cannot clear it. `device/classification.test.ts › blocks a spent key on the first refusal rather than spending the ceiling`.
22. **`409 ancestor_unavailable` blocks that write with the reason `ancestor_unavailable`.** The server no longer holds a snapshot of the version the write names, so the same write re-sent is refused identically however often anyone sends it. The envelope carries the version the server does hold, and settling means rebasing on it — which is a new write, not this one. A create carrying a natural key is the exception (39): its envelope names the row the key resolved, and the device moves onto that row rather than holding a write nobody can send. `device/classification.test.ts › blocks a write whose base version the server no longer holds`, `device/queue.test.ts › refuses a create whose natural key names a row, and moves the copy onto that row`.
23. **`409 version_conflict` blocks a write with the reason `conflict_unresolved`.** A delete whose row has changed is blocked this way, keeping the newer row intact; it never retries without its version. The server as specified resolves an update requesting automatic resolution inside its own transaction (`versions/auto-resolved` and `versions/auto-type-move`), except one that also moves the type, which it refuses by design; this is what a device does when it meets either: it cannot resolve the conflict itself (`device/conflict-blocked`) and re-sending is the same request, so it reports and stops. A create carrying a natural key is refused and moves onto the row instead (39). `device/classification.test.ts › blocks a conflict the server declined to resolve`, `device/queue.test.ts › blocks a move that collides with a write it did not read, keeping it`.
24. A write held for a dependency, or behind the write ahead of it to the same row or edge (42), carries the reason `awaiting_dependency`, and it is released by that write being answered rather than by anything a caller does. The queue names what holds it: the writes it depends on in `depends_on`, and the write ahead of it in `follows`, which the binary's plain output names too. The queue stores it, and the binary reports it, as `blocked` with this reason; **the typed view a binding hands an app presents it as waiting, with no verdict**, since nothing outside the queue has to change for it to go and an app showing each verdict would show an ordinary wait as a stop. `device/classification.test.ts › releases a held write when its dependency is answered`, `device/queue.test.ts › sends a delete of a row only once the edits of it ahead are answered`, `› says in words which writes hold a queued write`.
25. **The ceiling is five refusals, counted as refusals and not as attempts.** A device that could not ask has not been refused, so a week offline does not exhaust it. It is a number this contract fixes; it is not configuration. `device/classification.test.ts › counts refusals rather than attempts, so a long outage does not exhaust the ceiling`, `› reaches the ceiling on the fifth refusal`.
26. The blocked reasons are a closed set: `credential_refused`, `key_spent`, `ancestor_unavailable`, `conflict_unresolved`, `awaiting_dependency`. `device/classification.test.ts › reports one of the five blocked reasons and no other`.
27. **A `blocked` or `dead` row is released by the caller, one row or one reason at a time, and a released row is sent again under a fresh idempotency key.** A row the drain refused because what it waits for was refused or died is released the same way, because it never went out; a row the _server_ refused is not, whatever it waits on, because it did. **What separates them is whether the row was sent**, which nothing a caller reads reports: the queue carries a verdict and a reason, not that fact, so a caller releases and is told whether it took. Re-sending under the spent key would be answered from the server's record, which is the same refusal that blocked it; a fresh key is what makes releasing mean anything. A row whose reason clears on its own — `awaiting_dependency`, and `credential_refused` once the credential is replaced or, for a create naming a source, once its key claims that source (40), or once the missing grant is restored (51) — needs no release. A reason names blocked rows only, so a release by reason never takes a dead one, which carries no reason and is released by its id. A release lays every write it releases back over the copy in the same transaction, including unsent dependents released with it, before any request is sent. A row refused because a write it waited for was withdrawn is never released, since what it waited for is gone (46). `device/classification.test.ts › sends a released row again under a fresh key`, `› releases by reason the rows blocked for it, and never a dead one`, `› blocks a create naming a source its key does not claim, and sends it once the key does`.

## Offline, reconnect and re-hydration

28. A device that cannot reach the server queues writes and reports them as queued. Nothing is lost and nothing is retried in a loop that a caller has to stop: a drain that cannot reach the server ends at the first write (17). `device/queue.test.ts › queues writes while the server is unreachable`.
29. On reconnect the queue drains in order, and a write queued before the outage is answered before one queued during it. `device/queue.test.ts › drains in order on reconnect`.
30. **A re-hydration leaves the queue intact.** A copy that expires, whether its cursor aged out, its server was restored behind it or another instance answers at its origin, clears the working copy and pulls the slice again (`device/expire-aged-cursor` and `device/expire-log-behind`), and a queue cleared with it would silently drop writes a caller had been told were queued. `device/queue.test.ts › keeps the queue through a re-hydration`, `device/catch-up.test.ts › hydrates again when the server's log ends behind its cursor, keeping the queue`, `device/queue.test.ts › sends nothing to another instance at the same address, keeping the queue`.
31. A row the device wrote and has not yet had answered is visible to a local read, and is reconciled to the server's row when the verdict arrives. `device/queue.test.ts › shows an unanswered local write to a local read`.

## What a queue holds

32. **The kinds of write a queue holds are a closed set**: create, update, delete, restore and transition an item; create, update and delete an edge; replace and merge an item's metadata; add a tag and remove a tag; write and delete an extension namespace; upload a blob. A purge is not among them (`device/purge-unqueued`), and neither is a bulk door or a bulk action: those are the server's way of doing many things in one request, not a thing a device holds a write for. `device/queue.test.ts › holds one kind per write, from the closed set`.
33. **An edge, a tag, a metadata write and an extension are their own writes**, each queued and answered on its own. None of them is part of an item's fields, so none of them collides with an edit to those fields: a title changed on one device and a tag added on another both land. `device/queue.test.ts › queues an edge, a tag and an extension as writes of their own`.
34. **A write carries whole property values and a verdict answers about whole properties.** A device does not merge inside a property, and it does not assume the server will: whether a body is ever merged line by line is not settled, and a device that assumed it were would send a property it had already half-resolved. `device/verdicts.test.ts › answers about whole fields, never about part of one`.

## Writes that wait on writes

35. **Nothing the device applies erases a write still waiting.** A write waits until it is answered, and a blocked or dead one is waiting still, because a release sends it again (27). A row takes the server's values from an answer the drain adopts, an event a catch-up applies or a page a hydration pulls, and each waiting write to that row is laid back over them, whole properties in the order they were queued, so a local read goes on answering those writes (31) until their own verdicts settle the row; a create still waiting is held again once a hydration has cleared the copy (30), and its supplied values remain laid over a row the server already holds while the create has no accepted answer, an edge's only where the copy holds its source or holds its type whole (`device/edge-source-left-unheld`). A copy that adopted the answer to a create over the edit queued after it would show the edit as undone while the queue still sends it, and a tag or a delete answered later would never come back, because their answers carry no row to adopt. `device/waiting-projections.test.ts › keeps a %s edit visible after a newer server row arrives`, `› shows an unsent dependent edit as soon as its dead create is released`, `› keeps a dead create visible through hydration`, `› keeps a dead edge edit over a newer edge event`, `› keeps a dead edge create over an existing server edge`, `device/waiting-projections-live.test.ts › keeps a dead %s visible over real later changes and on release`, `device/queue.test.ts › keeps the writes it has not had answered through the answer to an earlier one`, `› keeps a waiting write through the reconcile of a refused one`, `› keeps a waiting edge edit through the answer to the edge's create`, `› keeps the writes it has not had answered through a re-hydration`, `› keeps a blocked write through a re-hydration`, `› holds no waiting edge whose source a re-hydration left outside the slice, nor its answer`, `device/catch-up.test.ts › applies an event beneath a write it has not had answered`, `› applies an edge event beneath an edge edit it has not had answered`, `› applies an event beneath a blocked write, which a release sends again`, `› applies an event on a held stream beneath a write it has not had answered`, `› applies an edge event on a held stream beneath an edge edit it has not had answered`.
36. **A write based on a row or an edge this device created is sent based on the version that create was answered with.** A delete requires the complete-content confirmation in 2; an acknowledged create is not proof that a local draft ever read the existing row, and a delete without a confirmed server version is refused unsent. The local copy of an unanswered create is at 0, which the server never mints (`versions/create-claim-none`), so an edit queued against it is based on 0; sent as it stands it names a snapshot no server holds and is blocked `ancestor_unavailable` (22), although everything it was based on was this device's own create. The version is read from the answer to the create it waited on: where the server took that create as an upsert onto a row it already held, the copy has moved onto that row (38), and the write is sent on the version the create was answered with, which is this device's own write. **Two answers are exceptions.** A create carrying a version and answered as an upsert more than one version past it was merged over another device's write, silently where nothing collided (`versions/create-stale-merges`), and a write made from the copy of the create never read that write. It is sent on the answer only where the answer holds, for every property it changed, what the copy held when it was made, as for an edit behind an edit (42): there it changes what the person changed and the other device's write stands. Otherwise, sent on the answer, it would be taken over that write, so it is sent on the version the create was based on, which this device read, and the server merges or conflicts on it against that version as the type's policy says: a body edited after such a create, where the other device changed a property the edit changed, comes back `conflicted`, the create's body kept on the row and the edit's set aside in a copy, while the other device's write stands. And a create the server acknowledges as a repeat of one it had already taken is answered with the row or edge as it stands, whoever has written it since (`items/create-repeat`, `edges/id-repeat`), so a write behind it is sent on 1, the version that create made, and the server merges it against that version; an edge, which is not merged, refuses the write as stale wherever it has moved past 1, and the write is blocked `conflict_unresolved`. Nothing else moves onto a create's answer: a write based on a version the server issued is sent on that version, or on the one an earlier edit of the same row was answered with (42). `device/queue.test.ts › sends an edit of its own unanswered create based on the version that create was answered with`, `› sends an edit of its own create on the version the create was based on where the server applied it over another device's write`, `› sends an edit of its own create on the answer where the server applied it over another device's write that left what the edit changed alone`, `› sends an edit of its own create on the version that create made where the server answers a repeat of it`, `› sends an edit of its own unanswered edge based on the version that edge was answered with`, `› moves the copy onto the row a create lands on, with every write waiting on it`.

## Uploads

37. **An upload is accepted only where the server's answer names the bytes by the hash they were queued under.** Any other answer to it is one the device cannot read (19): accepting it would report the bytes landed under a name the server does not hold them by, and the file item waiting on the upload would then name nothing. `device/queue.test.ts › counts an upload whose answer names other bytes`.

## What the real server cannot be made to produce

## A create that lands on a row the server holds

38. **A create carrying a natural key is sent without the id the device minted, and the copy moves onto the row the answer names.** The server resolves such a create by its key (`items/natural-key-upsert` and `items/natural-key-new`): onto a row it already holds, answered `200` with that row, or into a new row whose id it mints, answered `201`. It refuses a body `id` that is not the row the key resolves, so a minted id sent with a key another device's create already landed under is a create refused on every device but the first. The minted id names the local row until a fresh certified read permits adoption in a transaction guarded by the captured read view. Then the local identity and unsent dependent requests move to the server row. Already-sent dependent requests retain their original addressed IDs, body, base and idempotency key. A failed read leaves the accepted receipt recorded and adoption pending; the next drain retries the read without resending the create. Left alone, each would address an id the server never held, and the copy would hold one item twice. A create with no natural key is sent with the id the device minted, and the server keeps it (`items/create-client-id`). `device/queue.test.ts › sends a create carrying a natural key without the id it minted, and holds the row the answer names`, `› moves the copy onto the row a create lands on, with every write waiting on it`.

39. **A create carrying a natural key that the server refuses `409` because the key resolves a row it holds is `refused`, and the copy moves onto that row.** The refusal is `version_conflict` where the row has moved on since the version the create read and the server still holds that version, and `ancestor_unavailable` where it does not: where the create said it read no row, which a create carrying version 0 says (`versions/create-claim-none`), or where the version it read has since been thinned. Either envelope names the row in `current.id` (`versions/create-names-row`). It is refused with the server's code rather than blocked (22, 23), because the row it would have made exists and the same create sent again meets the same refusal: there is nothing for a release to send. The copy is reconciled onto that row rather than back to nothing (12): the minted row goes, and unsent additive dependent requests that named it name the server's row instead, as for a create answered `200` (38). After a `version_conflict` the copy adopts the fresh certified current baseline, retaining an already-held newer baseline over an older response. **After an `ancestor_unavailable` the version read, if any, is one the server no longer holds, which is as good as never read**: the copy holds the row as the server does, read again by id, and a write made from it next is based on that version and replaces content this device never read as the last writer. Nothing here protects that content, and the device does not claim to; kept as the base instead, a thinned version would have every edit of the row refused the same way. **What waited on the create goes to that row only where it adds to it**: a tag added, an edge made to or from it. A write that replaces, removes or moves the state of the row, an update, a delete, a restore or a transition, a metadata write, a tag removed, an extension written or deleted, is refused without being sent. Each was made against the row this device created, and sent to the server's row it would do to another device's item, one this device never read, what was meant for this one; an update names a version of a row the server never made besides. Where a certified read says the target is absent, adoption remains pending: the original refused verdict, local identity and dependent work are retained. Environmental read failure likewise preserves the receipt and debt; later drains retry the read without resending the settled create. A server-attributed terminal `401` during this read expires the working copy, without changing the original receipt. Only unsent dependent requests are remapped; requests already sent retain their original identity and payload. A key that may not read the row never meets these envelopes: the server refuses its create `403 type_not_permitted` without naming the row (`items/natural-key-unreadable`), which is refused like any other `403` (18). ## An edit made against an earlier read

43. **An update may say that the version it names is one read before the version the copy holds, and it is then sent on that version, for the server to merge.** An editor holding a row while the copy takes in another device's write has what its person read, not what the copy has caught up to. ## A write that can never be sent

46. **A write blocked `ancestor_unavailable` or `conflict_unresolved` can be withdrawn by its id, and no other row can.** Sent again, under any key, such a write is refused the same way (22, 23), so a release spends a request to be told the same thing, while the write stays laid over its row as a write still waiting (35) and the copy goes on showing what the server will never take, whatever lands after it. ## Drains that overlap

## A grant that returns

51. **A `403` naming a missing grant in `details.grant` blocks the write as `credential_refused`.** The grant has the kind, name and level stated in 48; a missing or malformed grant leaves the ordinary refusal rule in force (18). A type, edge, metadata or extension write refused for its key's grants keeps its content and the row the copy shows, including a create and the writes that wait for it. The drain carries on with unrelated writes, and reports the missing grant alongside the blocked verdict. **The next drain tries the write again under its original idempotency key**, so restoring the grant allows it to land without a release. A refusal of a replay may follow a write that already committed: the device neither assumes it was unwritten nor mints another key for the retry. Later writes to the same subject stay unsent with their original base until that receipt is available (42). A folder sends a held edit or create again when the grant returns, retaining the file and the refusal while it waits. A permanent fence carrying no missing grant remains terminal, since restoring a grant cannot open it. `device/grant-recovery.test.ts › keeps an edit blocked for $kind $level until its grant returns`, `› keeps a grant-blocked create and its edit until the grant returns`, `› holds a later edit while an earlier receipt lacks a grant after catch-up to %s`, `› keeps a permanent fence terminal when its details are %j`, `device/grant-recovery-live.test.ts › sends a real %s after its key's grant is restored`, `› keeps a folder's edit and create and sends both when its grant returns`.

## Local item field validation

52. When a caller queues an item create or update, the device MUST check declared fields against its held type catalog before changing the working copy or queue. The check MUST resolve inherited fields with the nearest declaration taking precedence. The check MUST enforce required fields, field kinds, enum membership, UTF-16 string length limits, array length limits, NUL rejection on bounded strings, URL, email, date, datetime and thumbnail rules as `types.md` defines them. The check MUST accept optional nulls, undeclared properties, annotation-only formats and arbitrary array element values where the server's field validator accepts them. When the check refuses a field, the device MUST return its existing validation classification with `invalid_properties` and a deterministic message naming the field and reason. When the held catalog does not contain the item's type, the device MUST refuse its item field write as an unknown type. **Reason:** A local row shown as queued must not contain a field value the held type already proves invalid. A server-only strict-mode setting can still refuse an undeclared property. **Tests:** `device/property-validation.test.ts › refuses missing and invalid fields atomically and accepts their boundary neighbours`, `device/property-validation-live.test.ts › matches a real server's field decisions and keeps queued writes across a catalog change`; core `local_fields_distinguish_an_absent_type_from_a_known_empty_type`, `field_formats_accept_the_servers_boundary_neighbours`, `default_caps_and_thumbnail_caps_refuse_one_past_the_accepted_limit`, `enums_with_no_values_use_string_rules_and_populated_enums_use_only_membership`.

53. When a create has no natural key, the device MUST check all properties of the new row. When an update names the held version, including version zero on an unanswered create without a natural key, the device MUST check the result of its merge, replace or retype against the destination type. When a natural-key create resolves a held row of the same type and has no version or names that row's held version, the device MUST check the known merged properties. When an edit or natural-key create names an earlier version, the device MUST check supplied field values without judging missing required fields in the server's unresolved result. When a natural-key create has no known target, or an update or repeated create targets its unanswered version-zero placeholder, the device MUST check supplied field values without requiring fields an unseen target may already hold. **Reason:** Only the server holds the ancestor, unseen upsert targets and conflict policy needed to resolve stale writes. Permissions, strict-mode configuration, uniqueness and recurrence also remain server-owned. **Tests:** `device/property-validation.test.ts › judges current merge, replace, retype and version zero while leaving stale results to the server`, `› checks known upserts and supplied values on unresolved or stale targets`; core `local_fields_judge_current_whole_edits_but_only_stale_supplied_values`, `local_fields_judge_a_known_upsert_and_defer_an_unknown_targets_missing_fields`, `local_fields_keep_unanswered_keyed_placeholders_unresolved`; `device/property-validation.test.ts › keeps repeated creates and edits to an unanswered keyed placeholder unresolved`.

54. ## A placement a folder gives way from

55. When a folder gives way to another machine's placement (`folders.md` 19), the device MUST take the folder's own `in-folder` writes to that edge out of the queue, a create refused as a duplicate among them, without a caller's withdraw or discard.
    **Reason:** What is withdrawn is every write of the folder's to that `in-folder` edge not yet accepted: the create refused as a duplicate or the move refused as stale, and any later move of the same edge still queued behind it, whose path is lost with it. The refused create carries only a path the folder chose, from the item's title or where its file sat; the item and the file both stay, and the pull moves the file to the placement the server holds. Kept until discarded, the create would leave a refusal to discard for nearly every item two machines both pulled, since each writes the item's placement.
    **Tests:** `device/folders.test.ts › follows the placement another Mac made first, and leaves no refusal behind`, `› follows another Mac's move of the same file, giving its own way`.

## A restore of a row the copy does not hold

56. When a caller restores a row the copy does not hold, a device MUST queue the restore by the row's id.
    **Reason:** A row read from the bin (`device/bin-read`) is not held, and nor is one the slice never took, yet the person restoring it is restoring a row the server holds. Queued, the restore waits out a network as any write does and goes after a restart.
    **Tests:** `device/bin-live.test.ts › restores a row read from the bin that the copy does not hold`.

57. When a device queues a restore of a row the copy does not hold, the device MUST NOT enter the row on the restore alone.
    **Reason:** A row entered before the answer would be one the copy holds no read of and cannot keep current, and a refusal would leave nothing to put it back to. The row enters as any row does: by the answer's read or its `item.restored` event where the slice or a pin takes it, or by an event or a hydration while the restore waits, with the restore laid over it (35).
    **Tests:** `device/bin-live.test.ts › restores a row read from the bin that the copy does not hold`.

58. When a restore of a row the copy does not hold already waits, the device MUST refuse another restore of it `invalid`, queueing nothing.
    **Reason:** The bin goes on listing the row until the restore is answered, so a person can ask twice, and the second restore would come back a refusal for a row that was restored.
    **Tests:** `device/bin-live.test.ts › restores a row read from the bin that the copy does not hold`.

## A null a write carries

59. When a create carries a null for a field its type declares and does not require, the device MUST hold the new row without that field.
    **Reason:** The server makes the row without it (`items/create-null-optional`), and a copy showing the null would show a field the server never holds. `attachments` and `links`, which every type takes, count as declared. In a create that makes a new row, a null on a property the type does not declare is held as the server holds it, as a value.
    **Tests:** `device/null-properties-live.test.ts › leaves out a create's null on a declared optional field, as the server does`, core `catalog::tests::a_create_holds_its_nulls_as_the_server_does`.

## An edit that moves an edge's end

60. When a caller edits an edge naming a new source or a new target, the device MUST queue the move as one update of the edge, carrying the one end it moves and no end the copy already holds, the properties the edit names and the version the copy holds, and MUST NOT queue a delete and a create in its place.
    **Reason:** The server moves one end of an edge whose other end holds one of its type in one write, judged without the edge being moved (`edges/move-target`, `edges/move-source` and `edges/move-cardinality`). A delete and a create are two writes with two verdicts: offline, the delete can be accepted and the create refused, for a cycle or a new end the server does not hold, and the end that stays is left with no edge, a child with no parent. Queued as one update, the move waits on the edge's own create (4) and on the write ahead of it to the same edge (42) as any edge edit does, goes after a restart, and a refusal leaves the edge where the server holds it (12). A new end the copy does not hold is sent: the server judges it. An end named as the copy holds it moves nothing and is left out, because the server judges a named end against the edge it holds, which a move still waiting ahead may not leave where the copy shows it: sent, it would ask again for a move the server may refuse, or read as a move of both ends.
    **Tests:** `device/edge-move.test.ts › sends a move as one update of the edge, on the version the copy holds`, `device/edge-move-live.test.ts › re-parents a note offline in one write a real server takes, never leaving it without a parent`, `› puts the edge back at its old parent when the server refuses the move for a cycle`, core `tests::an_edge_move_naming_the_end_that_stays_as_it_is_moves_the_other_one`.

61. While a move of an edge waits, the device MUST show the edge at its new end, read from either end, over whatever puts the server's edge back, a catch-up or the answer to a write ahead of it (35).
    **Reason:** A local read would otherwise show the old parent still drawing a child the person has moved, as 44 says of an item's move. The answer to the move, or its refusal read back, is what the edge then holds. A move of a source changes the server's read view once it lands (`read-views/view-moves-edge-source`), so the drain that has it answered records the verdict and expires the copy, as an answered retype does, and the next hydration holds the edge where the server does; a move of a target leaves the read view as it was, and the copy reads the moved edge back.
    **Tests:** `device/edge-move.test.ts › shows a waiting move at its new end from both ends, over the answer to the edit ahead of it`, `device/edge-move-live.test.ts › re-parents a note offline in one write a real server takes, never leaving it without a parent`, `device/catch-up.test.ts › lays its own waiting move of an edge's target over the server's change to the edge`, `› keeps an edge whose source moved outside the slice while a move of its own waits`.

62. When a move names as its new end a row of this device's own create that the server has not taken, the device MUST hold the move until that create is answered, and MUST send it naming the row the create was answered with.
    **Reason:** The server holds no such row and would refuse the move `404 item_not_found` (4). A create carrying a natural key lands on the row its key resolves (38, 39), whose id is not the one the device minted; a move still naming the minted id would be refused for a row the server never made. 63. IF an edge edit moves both ends, or moves an end of a type whose end that stays may hold more than one edge of it where the catalog the device holds names that type, THEN the device MUST refuse it `validation`, carrying the server's `validation_error`, and MUST queue nothing.
    **Reason:** The server refuses either body `400 validation_error` whatever its rows hold (`edges/move-many` and `edges/move-both-ends`), so the copy can tell without asking.
