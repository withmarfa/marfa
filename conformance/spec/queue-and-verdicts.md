# The queue and its verdicts

A device does not write to the server directly. It writes to its working copy, queues the write, and drains the queue when it can. Every queued write is answered with one verdict from a closed set, and the verdict says what became of the write and what the device may do next.

`device.md` states the working copy the queue writes into. The server behavior a verdict is read from is `versions.md`, `items.md` and `errors.md`.

## The queue

1. The queue is persisted and ordered. A write survives the process that made it, and a drain sends writes in the order they were queued; a write to a row or an edge waits for an answer to the write ahead of it to the same one, across a failure too (42). `device/queue.test.ts › sends queued writes in the order they were queued`, `› keeps the queue across a restart`, `› sends a delete of a row only once the edits of it ahead are answered`.
2. **Every write carries the version it read.** It is required on an update: an update queued without one is refused before it is sent, because a version-less update is a write that overwrites whatever it finds. It is optional on a create, and a create that carries one is conditional on it where its `(source, source_id)` resolves a live row: there the server answers it exactly as it answers an update. A repeated `id`, and a natural key resolving a trashed row, are acknowledged rather than written, so neither has a precondition to fail. `device/queue.test.ts › refuses an update queued with no version`, `› sends a create with the version it was based on`.
3. Every queued write carries an idempotency key, minted when the write is queued and never changed. A retry re-sends the same key, so a write whose answer the device never saw is answered from the server's record rather than written a second time. `device/queue.test.ts › retries under the key it was queued with, and is answered from the record rather than written twice`.
4. **A write waits for the write it depends on.** An update, a delete or an edge write naming a row whose create the server has not taken is held rather than sent, because the server has no such row and would refuse it. A create is not taken while it is unanswered or blocked, because a blocked write is waiting still (35): a write to its row sent in the meantime is refused `item_not_found`, and the copy then forgets the row it was queued against. `device/queue.test.ts › holds a write whose create has not been answered`, `device/classification.test.ts › blocks a create naming a source its key does not claim, and sends it once the key does`.
5. A device sends `conflict=auto` on every update. It resolves nothing itself (`device.md` 19); the flag is how the server is asked to resolve within its own transaction rather than refusing and leaving two writes where one is atomic. `device/queue.test.ts › sends every update with the server asked to resolve`.
6. A drain reports the verdict of every write it sent, unless an answer on another contract ends it, which it reports as a refusal instead while the queue holds the verdicts it reached (`device.md` 42); and the queue reports what it still holds with each row's verdict and reason. It is answerable before a hydration, because a queue is a record of what a caller asked for rather than a view on the copy, and the moment a caller most needs it is the moment the server cannot be reached. A row the server has not answered carries no verdict, which is the absence of one rather than a seventh. `device/queue.test.ts › reports a verdict for every write it sent`, `› reports an empty queue on a store that has never been written to`.

## The verdicts

7. Every queued write carries exactly one of six verdicts, and the set is closed: `accepted`, `merged`, `conflicted`, `refused`, `blocked`, `dead`. An answer a device cannot classify is a defect in the device, not a seventh verdict. `device/verdicts.test.ts › answers every write with one of the six verdicts`, `device/queue.test.ts › reads the answer its own door gives, not an item's`.
8. **The three verdicts a `2xx` can carry are told apart by one field.** A successful answer either reports a resolution or does not, and a resolution either names a conflicted copy or does not; those two questions decide between `accepted`, `merged` and `conflicted`, and a device reads them rather than comparing the row it got against the row it imagined. Comparing rows cannot work: every answer carries fields the server stamps and the device never sent. `device/verdicts.test.ts › tells the three successful verdicts apart by the resolution the answer carries`.
9. **`accepted`** — a `2xx` reporting no resolution. The server took the write as sent. The working copy adopts the returned row, including the version and the fields the server stamps. A natural-key upsert and a repeat answered from the server's record are both `accepted`: the server took the write, and the row it returned is the truth whatever the device held, except where the copy holds the row, or for an edge's write the edge, at a later version than the answer. A catch-up can bring that later version before a repeat's answer arrives, and adopting the older one would take the copy back under the writes since and base the next edit on a version the row has left; the copy keeps the later version, and the edits behind the write still move onto the answer (42). `device/verdicts.test.ts › accepted: adopts the row the server returned`, `› accepted: takes an upsert and a replayed repeat as accepted`, `device/queue.test.ts › keeps the later row a catch-up brought over an older answer replayed after it`, `› keeps the later edge a catch-up brought over an older edge answer replayed after it`.
10. **`merged`** — a `2xx` reporting a resolution that names no conflicted copy. The server applied the write over changes made since, property by property, and the row it returned carries both. The device adopts that row whole and does not send again; the difference is the merge, not a failure to apply. `device/verdicts.test.ts › merged: adopts the row a resolution returned`.
11. **`conflicted`** — a `2xx` reporting a resolution that names a conflicted copy. The type's policy for a colliding property is to keep both, so the server kept its own value on the row and wrote the losing one to a sibling of the same type tagged `conflicted-copy`. The verdict names the sibling; the working copy adopts the returned row and holds the sibling as an ordinary item of the slice. `device/verdicts.test.ts › conflicted: names the sibling the server wrote`.
12. **`refused`** — the server refused the write for a reason no retry changes. The verdict carries the server's code verbatim. It is terminal: the write is not sent again, and the working copy is reconciled back to what the server holds. **A refusal the drain made rather than the server is the one exception** — a write held for a dependency that was itself refused or died carries the same verdict without ever having been sent, and a caller may release it (27). `device/verdicts.test.ts › refused: carries the server's code and is not sent again`, `device/classification.test.ts › will not release a write the server itself refused, dependency or not`.
13. **`blocked`** — the write has stopped until something outside the queue changes. It carries one reason from the closed set in the next section. It is not a failure and not counted toward the ceiling; the drain passes over it and the queue reports it. `device/verdicts.test.ts › blocked: is passed over by a drain and reported with its reason`.
14. **`dead`** — a failure a retry could have cleared was answered the same way until the ceiling was reached. Terminal until the row is released. `device/verdicts.test.ts › dead: is terminal once the ceiling is reached`.
15. A verdict is reported, never acted on. A device meeting `conflicted`, `blocked` or `refused` does not write a resolution of its own; it reports the verdict, the server's envelope and the row it holds, and stops (`device.md` 21). `device/verdicts.test.ts › reports a conflict rather than resolving it`.
16. A refused create refuses the writes that were waiting on it, and their reason names the write that was refused. Nothing that depended on a row the server never accepted is sent. A create refused because its natural key resolves a row the server holds is the one exception (39): that row exists, so what waited on the create goes to it. `device/verdicts.test.ts › refuses the writes that were waiting on a create the server refused`, `device/queue.test.ts › refuses a create whose natural key names a row, and moves the copy onto that row`.

## Which failures retry, and which do not

The split is the whole of the classification, and it is closed. A device that retries the wrong class either loops on a refusal it will always get or strands a good write behind a network that came back.

17. **An environmental failure retries without limit and is never counted.** A dropped connection, a refused connection, a read that timed out, any `5xx` and a `429` are statements about the environment rather than about the write, and every one of them clears without anybody doing anything. Counting them would strand a valid write behind an outage and then need a person to release it. `device/classification.test.ts › retries an environmental failure past the ceiling without counting it`, `› retries a 5xx and a 429 without counting them`.
18. **A contract failure does not retry.** A `400`, a `403` and a `404` are `refused` on the first answer, because the same request sent again is the same request. A create's `403` naming a source its key does not claim is the one exception (40). `device/classification.test.ts › refuses a contract failure on the first answer`, `› blocks a create naming a source its key does not claim, and sends it once the key does`.
19. **A failure that is neither retries, and is counted.** An answer the device cannot read, a local store that refused the write after the server had accepted it, and a key the server reports as still in flight are all failures a further attempt might clear and none of them clears on its own. This is the class the ceiling exists for, and it is the only one: without it `dead` is a verdict nothing reaches. `device/classification.test.ts › retries an answer it cannot read, and counts it`, `› retries a key the server reports in flight, and counts it`.
20. **A `401` blocks the whole queue with the reason `credential_refused`.** It is the one refusal that looks environmental and is not: it clears only when a person replaces the credential. Every queued write carries the same credential, so every one of them parks together and the drain stops rather than working through a queue none of which can succeed. `device/classification.test.ts › blocks the whole queue on a refused credential, and stops the drain`.
21. **`422 idempotency_key_reused` blocks that write with the reason `key_spent`**, on the first refusal. The key has been answered for a different body, so it is the key that is spent rather than the write; retrying would spend the ceiling on refusals that are all the same refusal and then park the row under a reason naming the wrong cause. Re-sending the same key cannot clear it. `device/classification.test.ts › blocks a spent key on the first refusal rather than spending the ceiling`.
22. **`409 ancestor_unavailable` blocks that write with the reason `ancestor_unavailable`.** The server no longer holds a snapshot of the version the write names, so the same write re-sent is refused identically however often anyone sends it. The envelope carries the version the server does hold, and settling means rebasing on it — which is a new write, not this one. A create carrying a natural key is the exception (39): its envelope names the row the key resolved, and the device moves onto that row rather than holding a write nobody can send. `device/classification.test.ts › blocks a write whose base version the server no longer holds`, `device/queue.test.ts › refuses a create whose natural key names a row, and moves the copy onto that row`.
23. **`409 version_conflict` answered to a write that asked the server to resolve blocks that write with the reason `conflict_unresolved`.** The server as specified resolves such a write inside its own transaction (`versions.md` 13), so this is what a device does when it meets a server that did not: it cannot resolve the conflict itself (`device.md` 21) and re-sending is the same request, so it reports and stops. A create carrying a natural key is refused and moves onto the row instead (39). `device/classification.test.ts › blocks a conflict the server declined to resolve`, `device/folders.test.ts › does not overwrite newer server content from a stale folder`.
24. A write held for a dependency, or behind the write ahead of it to the same row or edge (42), carries the reason `awaiting_dependency`, and it is released by that write being answered rather than by anything a caller does. The queue names what holds it: the writes it depends on in `depends_on`, and the write ahead of it in `follows`, which the binary's plain output names too. `device/classification.test.ts › releases a held write when its dependency is answered`, `device/queue.test.ts › sends a delete of a row only once the edits of it ahead are answered`, `› says in words which writes hold a queued write`.
25. **The ceiling is five refusals, counted as refusals and not as attempts.** A device that could not ask has not been refused, so a week offline does not exhaust it. It is a number this contract fixes; it is not configuration. `device/classification.test.ts › counts refusals rather than attempts, so a long outage does not exhaust the ceiling`, `› reaches the ceiling on the fifth refusal`.
26. The blocked reasons are a closed set: `credential_refused`, `key_spent`, `ancestor_unavailable`, `conflict_unresolved`, `awaiting_dependency`. `device/classification.test.ts › reports one of the five blocked reasons and no other`.
27. **A `blocked` or `dead` row is released by the caller, one row or one reason at a time, and a released row is sent again under a fresh idempotency key.** A row the drain refused because what it waits for was refused or died is released the same way, because it never went out; a row the _server_ refused is not, whatever it waits on, because it did. **What separates them is whether the row was sent**, which nothing a caller reads reports: the queue carries a verdict and a reason, not that fact, so a caller releases and is told whether it took. Re-sending under the spent key would be answered from the server's record, which is the same refusal that blocked it; a fresh key is what makes releasing mean anything. A row whose reason clears on its own — `awaiting_dependency`, and `credential_refused` once the credential is replaced or, for a create naming a source, once its key claims that source (40) — needs no release. A reason names blocked rows only, so a release by reason never takes a dead one, which carries no reason and is released by its id. `device/classification.test.ts › sends a released row again under a fresh key`, `› releases by reason the rows blocked for it, and never a dead one`, `› blocks a create naming a source its key does not claim, and sends it once the key does`.

## Offline, reconnect and re-hydration

28. A device that cannot reach the server queues writes and reports them as queued. Nothing is lost and nothing is retried in a loop that a caller has to stop. `device/queue.test.ts › queues writes while the server is unreachable`.
29. On reconnect the queue drains in order, and a write queued before the outage is answered before one queued during it. `device/queue.test.ts › drains in order on reconnect`.
30. **A re-hydration leaves the queue intact.** An aged-out cursor clears the working copy and pulls the slice again (`device.md` 16), and a queue cleared with it would silently drop writes a caller had been told were queued. `device/queue.test.ts › keeps the queue through a re-hydration`.
31. A row the device wrote and has not yet had answered is visible to a local read, and is reconciled to the server's row when the verdict arrives. `device/queue.test.ts › shows an unanswered local write to a local read`.

## What a queue holds

32. **The kinds of write a queue holds are a closed set**: create, update, delete, restore and transition an item; create, update and delete an edge; replace and merge an item's metadata; add a tag and remove a tag; write and delete an extension namespace; upload a blob. A purge is not among them (`device.md` 25), and neither is a bulk door or a bulk action: those are the server's way of doing many things in one request, not a thing a device holds a write for. `device/queue.test.ts › holds one kind per write, from the closed set`.
33. **An edge, a tag, a metadata write and an extension are their own writes**, each queued and answered on its own. None of them is part of an item's fields, so none of them collides with an edit to those fields: a title changed on one device and a tag added on another both land. `device/queue.test.ts › queues an edge, a tag and an extension as writes of their own`.
34. **A write carries whole property values and a verdict answers about whole properties.** A device does not merge inside a property, and it does not assume the server will: whether a body is ever merged line by line is not settled, and a device that assumed it were would send a property it had already half-resolved. `device/verdicts.test.ts › answers about whole fields, never about part of one`.

## Writes that wait on writes

35. **Nothing the device applies erases a write still waiting.** A write waits until it is answered, and a blocked one is waiting still, because a release sends it again (27). A row takes the server's values from an answer the drain adopts, an event a catch-up applies or a page a hydration pulls, and each waiting write to that row is laid back over them, whole properties in the order they were queued, so a local read goes on answering those writes (31) until their own verdicts settle the row; a create still waiting is held again once a hydration has cleared the copy (30). A copy that adopted the answer to a create over the edit queued after it would show the edit as undone while the queue still sends it, and a tag or a delete answered later would never come back, because their answers carry no row to adopt. `device/queue.test.ts › keeps the writes it has not had answered through the answer to an earlier one`, `› keeps a waiting write through the reconcile of a refused one`, `› keeps a waiting edge edit through the answer to the edge's create`, `› keeps the writes it has not had answered through a re-hydration`, `› keeps a blocked write through a re-hydration`, `device/catch-up.test.ts › applies an event beneath a write it has not had answered`, `› applies an edge event beneath an edge edit it has not had answered`, `› applies an event beneath a blocked write, which a release sends again`, `› applies an event on a held stream beneath a write it has not had answered`, `› applies an edge event on a held stream beneath an edge edit it has not had answered`.
36. **A write based on a row or an edge this device created is sent based on the version that create was answered with.** The local copy of an unanswered create is at 0, which the server never mints (`versions.md` 18), so an edit queued against it is based on 0; sent as it stands it names a snapshot no server holds and is blocked `ancestor_unavailable` (22), although everything it was based on was this device's own create. The version is read from the answer to the create it waited on: where the server took that create as an upsert onto a row it already held, the copy has moved onto that row (38), and the write is sent on the version the create was answered with, which is this device's own write. **Two answers are exceptions.** A create carrying a version and answered as an upsert more than one version past it was merged over another device's write, silently where nothing collided (`versions.md` 10, 11), and a write made from the copy of the create never read that write. It is sent on the answer only where the answer holds, for every property it changed, what the copy held when it was made, as for an edit behind an edit (42): there it changes what the person changed and the other device's write stands. Otherwise, sent on the answer, it would be taken over that write, so it is sent on the version the create was based on, which this device read, and the server merges or conflicts on it against that version as the type's policy says: a body edited after such a create, where the other device changed a property the edit changed, comes back `conflicted`, the create's body kept on the row and the edit's set aside in a copy, while the other device's write stands. And a create the server acknowledges as a repeat of one it had already taken is answered with the row or edge as it stands, whoever has written it since (`items.md` 3, `edges.md` 3), so a write behind it is sent on 1, the version that create made, and the server merges it against that version; an edge, which is not merged, refuses the write as stale wherever it has moved past 1, and the write is blocked `conflict_unresolved`. Nothing else moves onto a create's answer: a write based on a version the server issued is sent on that version, or on the one an earlier edit of the same row was answered with (42). `device/queue.test.ts › sends an edit of its own unanswered create based on the version that create was answered with`, `› sends an edit of its own create on the version the create was based on where the server applied it over another device's write`, `› sends an edit of its own create on the version that create made where the server answers a repeat of it`, `› sends an edit of its own unanswered edge based on the version that edge was answered with`, `› moves the copy onto the row a create lands on, with every write waiting on it`, `device/folders.test.ts › sends a file saved three times before a push on the answers ahead of each save, its create merged over another machine's write that left the file alone`.

## Uploads

37. **An upload is accepted only where the server's answer names the bytes by the hash they were queued under.** Any other answer to it is one the device cannot read (19): accepting it would report the bytes landed under a name the server does not hold them by, and the file item waiting on the upload would then name nothing. `device/queue.test.ts › counts an upload whose answer names other bytes`.

## What the real server cannot be made to produce

The list and the reason for each entry are in `device.md`; `device/fidelity.test.ts` checks every answer the real server can produce against the scripted server's.

## A create that lands on a row the server holds

38. **A create carrying a natural key is sent without the id the device minted, and the copy moves onto the row the answer names.** The server resolves such a create by its key (`items.md` 5): onto a row it already holds, answered `200` with that row, or into a new row whose id it mints, answered `201`. It refuses a body `id` that is not the row the key resolves, so a minted id sent with a key another device's create already landed under is a create refused on every device but the first. The minted id names the copy's row until the answer comes; then the minted row goes, and every write still waiting on it, every edge and every file bound to it name the server's row instead, and so does the drain's report of the create. Left alone, each would address an id the server never held, and the copy would hold one item twice. A create with no natural key is sent with the id the device minted, and the server keeps it (`items.md` 2). `device/queue.test.ts › sends a create carrying a natural key without the id it minted, and holds the row the answer names`, `› moves the copy onto the row a create lands on, with every write waiting on it`, `device/folders.test.ts › binds one file to one item across two separately enrolled devices`.

39. **A create carrying a natural key that the server refuses `409` because the key resolves a row it holds is `refused`, and the copy moves onto that row.** The refusal is `version_conflict` where the row has moved on since the version the create read and the server still holds that version, and `ancestor_unavailable` where it does not: where the create said it read no row, which a create carrying version 0 says (`versions.md` 18), or where the version it read has since been thinned. Either envelope names the row in `current.id` (`versions.md` 10). It is refused with the server's code rather than blocked (22, 23), because the row it would have made exists and the same create sent again meets the same refusal: there is nothing for a release to send. The copy is reconciled onto that row rather than back to nothing (12): the minted row goes, and every edge, file and waiting write that named it names the server's row instead, as for a create answered `200` (38). After a `version_conflict` the copy keeps the row as it read it where it holds it, and a folder's next edit of the file is based on the version the create was based on, whatever the copy has caught up to since, so the server merges it against what was read. **After an `ancestor_unavailable` the version read, if any, is one the server no longer holds, which is as good as never read**: the copy holds the row as the server does, read again by id, and a write made from it next is based on that version and replaces content this device never read as the last writer (`folders.md` 13). Nothing here protects that content, and the device does not claim to; kept as the base instead, a thinned version would have every edit of the file refused the same way. **What waited on the create goes to that row only where it adds to it**: a tag added, an edge made to or from it. A write that replaces, removes or moves the state of the row, an update, a delete, a restore or a transition, a metadata write, a tag removed, an extension written or deleted, is refused without being sent. Each was made against the row this device created, and sent to the server's row it would do to another device's item, one this device never read, what was meant for this one; an update names a version of a row the server never made besides. Where that row cannot be read because it is gone or out of this credential's reach since the refusal, there is nothing to move onto, and the create stops as 22 and 23 say. A read that fails for a reason that clears on its own, a dropped connection, a `5xx` or a `429`, leaves the create unanswered and uncounted (17), and the next drain, which the server answers the same way, reads again; a `401` there blocks the whole queue (20). A key that may not read the row never meets these envelopes: the server refuses its create `403 type_not_permitted` without naming the row (`items.md` 5), which is refused like any other `403` (18), and a folder's file then holds bytes bound to a row the copy lost (`folders.md` 30). Left blocked where the row is there, the copy holds one item twice, an edit to the minted row is refused `item_not_found`, and the file bound to it has nowhere left to go. `device/queue.test.ts › refuses a create whose natural key names a row, and moves the copy onto that row`, `› refuses the writes behind a landed create that would take from the row, and sends those that add`, `› blocks a create whose natural key names a row it cannot read`, `› reads the row a create landed on again after a failure that clears on its own`, `› blocks the whole queue when the read of a landed row meets a refused credential`, `› holds a write still waiting behind a landed create on the row it landed on`, `device/folders.test.ts › keeps a file whose key names a row it may not read to itself, and says so`, `device/folders.test.ts › binds one file to one item when two folders hold it before either pushes`, `› does not overwrite newer server content from a stale folder`, `› sends a stale folder's edit over a row whose read version is thinned, and says so`.

## A source the credential's key does not claim

40. **A create refused `403 forbidden` because its key does not claim the source it names is `blocked` with the reason `credential_refused`, and so is every unanswered create naming that source.** The refusal names that source in `details.source` and nothing else (`items.md` 4), and a device reads it as this refusal only where `details` holds exactly that; a refusal from a source allow-list names the type and the list as well (`types.md` 18) and is refused like any other `403` (18), as is any other refusal naming a source beside something more. It is about the credential rather than the write, as a `401` is (20), but about one source: a write naming none, or another, carries on in the same drain. Nothing is reconciled, so the row the copy holds for each create and every write waiting on one stay as they are (4). The drain reports the source, because `credential_refused` alone reads as a key that no longer works. The reason clears on its own (27), so the first drain a caller asks for after the key claims the source sends them. **A folder left watching asks less often**: it drains every second, and a claim is granted by a person, so it asks about a source it found unclaimed again only once a minute has passed since, while a `push` or a drain a caller asks for asks at once; each asking spends one create per such source, and the watcher says the source is unclaimed once, when the set of unclaimed sources changes, rather than on every pass. Refused instead, each create's row would be forgotten while the file it came from stayed bound to it, and a claim granted afterwards would send nothing. `device/classification.test.ts › blocks a create naming a source its key does not claim, and sends it once the key does`, `device/folders.test.ts › tells a folder whose key does not claim its source, and sends its files once it does`, `› asks about an unclaimed source again only now and then while watching`, `› says in words which source its key does not claim, and once while watching`.

## A create onto a row in the bin

41. **A create carrying a natural key that the server acknowledges without writing, because the key resolves a row somebody trashed, is `refused` with the reason `trashed`, and the row it was queued as is forgotten.** The server answers such a create `200` with the row in the bin and `acknowledged: true` (`versions.md` 10), and writes nothing: what the create carried reached no row. Taken as `accepted`, the copy would move onto a row in the bin and a folder would bind the file to it, record what the file holds as agreed, and call it unchanged from then on, so the person's writing would be dropped with nothing saying so. Refused, the file stays bound to a row the copy no longer holds and is reported (`folders.md` 30). A create carrying a natural key names no id of its own (38), so an acknowledgment of one is never this device's own earlier create answered again. `device/folders.test.ts › refuses a create onto a row somebody trashed, and keeps the file as lost`.

## An edit behind an edit of the same row

42. **An edit of a row or an edge queued behind this device's own earlier edit of it is sent on the version that earlier edit was answered with, where the server took the earlier edit, `accepted` or `merged`, and applied it to the version the later one is based on.** An edit is queued against the version the copy holds, and an edit waiting in the queue is laid over the copy without moving that version (35), so edits made one after another before a drain are all based on the version the first one was. Sent as it stands, the second names a version the first has moved the row past, and the server merges it against the first as though another device had written it: a property both changed collides, and a note edited twice offline comes back `conflicted`, the first edit's text kept on the row and the second's set aside in a copy beside it (`versions.md` 13). So when the server answers an earlier edit `accepted` or `merged` at version N, a later edit of the same row, not yet sent and based on an earlier version than N, is sent on N where N holds, for every property it changed, what the copy held when it was made, which N does wherever the earlier edit was applied to the version the later one read. A property it carries at the value it read is no change of its own: it is not checked, and it is dropped from the edit when the edit moves, so a move never asserts a value the person did not change over another device's write. An edge is never merged, so a later edit of it based on N − 1 is sent on N. A chain moves one answer at a time: the third edit moves onto the second's answer once the second lands, and an edit of this device's own create moves onto the create's answer first (36). The row at N is then exactly what the later edit was made against, the version it read with the earlier edit laid over it. **A write to a row or an edge waits for the answer to the write ahead of it to the same one.** The queue records that write when it queues this one, where it is still to be written, and orders by it and nothing else: where it went out and had no answer, or is itself held, this one is held with the reason `awaiting_dependency` (24), whatever it depends on, and goes in a drain that has the answer; any answer releases it, a refusal and a block included, and none is passed on to it. A write the drain would refuse for a dependency is held in its place first, so the writes behind it do not step past the one ahead. A create carrying the natural key of a row the copy holds is a write to that row, since the server lands it there (38): it is ordered behind the row's last write still to go, and a write to the row queued after it is ordered behind it; and where a create lands on a row this device holds (38, 39), the writes moved onto that row are ordered behind the row's own writes still to go, in the order all of them were queued. Sent beside an edit that had no answer, an edit would go on the version both were queued against, and a body that has gone out under its key is never moved afterwards (3); a delete would put the row in the bin before the edits ahead of it reached it. A write to an edge depends on nothing but the edge's create (4), so it is ordered as a write to a row is. **Nothing moves onto an answer that holds anything else, and an edit made against an earlier edit that did not land as made goes on that edit's base.** A `conflicted` edit left the server's value on the row where it collided; a `refused` one, or one the server blocked, did not land; and a `dead` one is not known to have. Sent on such an answer's version, a later edit would be taken over content this device never read. A later edit made while an earlier edit of the same row or edge was waiting was made, for every property the earlier one carries, against that edit's value and not the server's, since the copy lays the earlier edit over the row (35). So where it shares a property with the earlier one and was based on a later version, one a catch-up brought, it is sent on the earlier edit's base, the properties it carries unchanged dropped: on its own base the server would take the earlier edit's value it carries as newer than whatever the row holds, and apply it without a word, and on the earlier base the server merges or conflicts on it. A later edit that shares no property with the earlier one read the server for everything it carries and is sent as it stands, as is one based on the same version as the earlier one. **An edit the server applied past its own base moves the edits behind it only where the other write left them alone.** Answered at N having been applied past its base, the earlier edit was merged over another device's write, silently where nothing collided (`versions.md` 11), and a later edit based on an earlier version never read that write. It is sent on N where N holds, for every property it changed, what the copy held when it was made, the version it was based on being the one the copy held; on N it changes what the person changed and nothing else, the other device's write stands, and edits of a body made offline land one after another whatever another device did to the title, a title a folder's file carries unchanged included. The same holds at each answer after it, so a third edit reaches the second's answer. Where that write touched a property the later edit changed, the later edit goes as it would behind an edit that did not land, and the server merges or conflicts on it. For the same reason the version is the one the earlier edit was answered with, not the one the server holds by the time the later edit goes, so a change another device makes between the two sends is merged or conflicted as that version says.
