# Folders

A folder is a device surface: a directory on a machine that holds, as files, what a saved search matches. It is a working copy and a queue like any other device (`device.md`, `queue-and-verdicts.md`) with a filesystem as its face, and every statement in those chapters holds here too.

## What a folder is

1. **A folder is a directory on a machine bound to a `system.folder` item, and the item holds its settings**: the search (2), the defaults (3), the include and ignore lists, the per-type first placement (18) and the removal threshold (`items.md` 49). **Each machine chooses only the directory.** `folders add <dir> --folder <id>` binds it, reading the settings from the server as it does, and is refused for an id naming an item that is not a `system.folder`, or a folder that is revoked, which has no settings to follow. **The settings are written out as one editable file, `.marfa/folder.yaml`**: a YAML map carrying the `system.folder`'s id and the version it was written from beside the settings, and the folder's only record of them on the machine. A catch-up or a pull that moves the row rewrites the file, unless the person changed it since it was written: that is their edit, and it is sent first. `folders push`, and a watch (25), send an edit as `PATCH /folders/{id}` (`items.md` 51) based on the version the file's own `version` line names (a file with no such line, or one naming no version the server mints, is based on the version last written), as a Markdown file's edit is (22), so the door merges it with a change made elsewhere meanwhile: a file current with the settings sends the settings it changed, and one older than them, an editor saving an old buffer over a rewrite say, sends every setting it names, for the door to merge against what it was written from. What the door answers is the folder's settings from then on. **An edit the door refuses, one naming a search or defaults this folder cannot follow (2, 3), a file that does not parse, or one naming another folder keeps the settings in force and flags the file**: the push, the watch and the pull say why, in words and in JSON, and the same refused text is not sent again. Only the door's own answers about the edit (`400`, `403`, `404`, `409` or `422`) are a refusal: a failing server, a rate limit or a spent key reports the edit as not sent yet, and it goes again at the next pass. Where the door refused it for a conflict, the reason says to delete the file, which writes the settings in force back into it, and edit it again. An edit changing no setting, a comment or a reformatting, sends nothing, and the file is written again from the settings. A setting taken out of a current file is refused the same way, because the door replaces a setting and never removes one: the reason says to write it empty, `[]` for a list or `{}` for a map. The folder's copy pins its `system.folder` (`device.md` 1), so a catch-up keeps it current, and every pass reads the settings from that row: a change made on any device reaches every folder bound to the item at its next pass, and one that asks for another slice, other types, another tier or a `beneath` it did not walk, is met with a fresh hydration at the next push; a watch already running takes that one only at the next push or when it starts again. **A key without read on `system.folder` cannot follow its settings**, and `folders add` is refused naming `system.folder:read`. A `.marfa/folder.json`, where a folder kept its settings before, is refused, saying to make a `system.folder` and add the folder again: settings kept on one machine are settings no other machine sees change. Adding a folder again under the same id writes the file afresh, and an edit of it not yet sent is lost. `device/folders.test.ts › reads its settings from the system.folder it is bound to`, `› takes settings changed on another device`, `› hydrates again where its changed settings ask for another slice`, `› refuses to follow settings its key cannot read, naming the permission`, `› refuses a folder whose settings are kept on this machine, and says to add it again`, `› writes its settings out as one file in .marfa/`, `› sends an edit to its settings file through the folder door`, `› keeps its settings in force and flags the file when an edit is refused`, `› rewrites its settings file when the settings change elsewhere`, `› does not write its settings file over the person's edit, and sends the edit`, `› bases an edit of its settings file on the version written in it`, `› refuses to follow an item that is not a live folder`, `› rewrites a settings file whose edit changes no setting`, `› sends a settings edit the folder door could not take for now at the next push`.
2. **The search decides what the folder holds, on every pass.** It takes the listing grammar's conditions: a type with its subtree, the tier, the state, and in its `filter` tags, `properties.<name>` and an edge to an item; and it adds `beneath` an item, which holds that item and everything it reaches along `parent-of` at any depth, as far as the key can read. It is answered from the copy as a local list answers the same conditions (`device.md` 24 and 36), with `parent-of` held whole where the search names `beneath` (`device.md` 1). A search naming no type holds every type the key reads, `system.*` aside. **Its default state is active and archived**, unlike a list's default of active (`device.md` 31): an archived item keeps its file, with `state: archived` in its frontmatter (7). **A condition the core does not implement is refused**, a `backref`, a member of the search, the defaults or the removal threshold it does not know, or a state other than active and archived, none among them, when the folder is added and at any pass that meets it, never ignored: an ignored condition holds everything it would have narrowed. `device/folders.test.ts › holds exactly what its search matches`, `› holds archived items unless its search narrows state`, `› refuses a search condition it does not implement`, `› takes every type, and any default type, where its search names no type`, `› keeps an archived item's file with its state in the frontmatter`.
3. **The defaults fill what a new file leaves blank, and never touch an edit.** A new document becomes the type its `type` line names (7), or else the defaults' type, or else the search's first type that is not a file type, or else `core.note`, at the tier its `tier` line names or else the defaults' or else the search's, with the defaults' properties where its frontmatter carries none of that name and the defaults' tags where it has no `tags` line. It takes the defaults' edges too, a `.txt` file and a file item as well as a Markdown file: each runs from the new item to the item named, except `parent-of`, which runs from the item named to the new one, as a child's file writes it, so a new file in a folder that searches `beneath` a project lands beneath it. A file item's type is its bytes', so of the defaults it takes the tier, the tags and the edges. An edit of a file already bound sends what the file holds and nothing from the defaults: a default filled in over an edit would put back a value somebody removed. **Defaults whose type or tier the search does not hold are refused**, as a condition is (2): every new file would otherwise fall outside its own folder. `device/folders.test.ts › fills a new file's blanks from its defaults, never an edit's`, `› reads type, tags, tier and state as the item's own`, `› makes a new document the search's first type that is not a file type`, `› refuses defaults its search would not hold`.
4. A machine holds several folders, each bound to its own settings, and they are independent: one folder's state, journal and queue are its own. `device/folders.test.ts › keeps each folder's state and queue to itself`.
5. A folder in a container is the same thing: add it, hydrate, work in files, push, discard the container. The settings are the `system.folder`'s, so nothing about a folder depends on the directory outliving the work. `device/folders.test.ts › hydrates into an empty directory and pushes without holding anything else`.

## Files and items

6. A file in the folder is an item on the server and an item the search matches is a file in the folder. `device/folders.test.ts › makes a file an item and an item a file`.
7. **One file is one item, and its frontmatter names that item's fields.** `type` (the type's full name), `tier`, `tags` and `state` (`active` or `archived`) are the item's own fields, read and written as such; `marfa_id` and `marfa_version` name the item and the version the file was written from (12, 22); a line named for an edge type or a reverse name is an edge (`edges.md` 2), never a property, and a folder reserves the shipped edge types' names and reads none of them yet; every other line is a property, one the type does not declare included, since nothing a file carries is dropped on the way in (`device.md` 23). **The body and the title follow the type's `display_hints`**: the file's body is the property `body_field` names and a new file's name goes to the one `title_field` names, so `core.event`'s body is its `description`, with `body` and `title` for a type naming neither. A type declaring a property under one of the names a file reads as something else is reported in the pull's `uncarried`: no file can carry it, so no line is written for it and an edit leaves it on the item. **A line taken out clears a property only in a file carrying a `marfa_version` line**: such a file is sent as its item's whole properties (`items.md` 22), based on that version (22), and in it no `tags` line is no tags and no `state` line is active. A file with no version line merges its lines over the item's, as before, and leaves an own field it names no line for as it is: whatever wrote it may not have kept every line. **An own-field line is read against what the pull wrote at the version the file's line names**, so an old buffer sends only what its person changed in it, and never moves back a type or a tag another machine changed since. A `tier` other than `feed` or `library`, a `state` other than `active` or `archived`, or `tags` that are not a list of tags, one tag or empty, makes the frontmatter unreadable (10). A pull writes `type` and `tier` always, `tags` where the item has any, and `state` only where it is archived, first and in that order, then the properties in the order the item holds them: an absent `type` or `tier` would have to mean a setting, and a change of the settings would then move every file, where tags and a state have an empty value of their own. **The folder does not reorder a file's properties.** What the server does with the order it is sent is the server's, and no statement anywhere says; the rule here is that the folder adds no reordering of its own. `device/folders.test.ts › carries frontmatter to properties and the body to the body`, `› writes a person's frontmatter back in the order they wrote it`, `› reads type, tags, tier and state as the item's own`, `› takes body and title from the type's display hints`, `› reports a type that declares a property no file can carry, and keeps it`, `› clears a property whose line was taken out of a versioned file`, `› merges an edit from a file with no version line`, `› sends only what an old buffer's own lines changed, not what another machine changed since`, `› keeps an archived item's file with its state in the frontmatter`.
8. **Frontmatter is only what a file opens with and delimits as frontmatter.** A body that opens with a horizontal rule is a body, and so is a fence pair holding a list or a line of text, which Markdown reads as a list or a heading between rules. Reading it as frontmatter loses the first paragraph and then writes the loss back to the server, which is silent data loss in both directions. A fence pair holding YAML that does not parse as fields is frontmatter that cannot be read (10). `device/folders.test.ts › treats a body opening with a horizontal rule as a body`.
9. **Changing `type:` retypes the item**, through the server's retype (`queue-and-verdicts.md` 44), in one edit with the file's properties, and the body goes to the body field of the type the item enters. A type this copy's catalog does not hold, or a file type, whose items are bytes, is refused before anything is queued. **A refused retype leaves the file as the person wrote it, flagged with the reason**, the server's code and message where the server refused it, and so does any other edit, tag or state of the file the server refuses (`queue-and-verdicts.md` 12): the pull does not write the item over the file and reports it in `flagged`, and the same bytes are not sent again. The next change the person makes is sent as any edit is, and an edit of the item from the file answered after the refusal lets the file go. Written over, the person's retype would be gone with nothing to say why. `device/folders.test.ts › retypes an item whose frontmatter changes its type`, `› flags a refused retype and keeps the file`.
10. **Frontmatter that does not parse is held, not sent, and the file is flagged `unreadable`.** That is a fence pair (8) whose YAML does not parse, one keyed by something that is not text, or one holding an own field no item can hold (7). Nothing is queued for the file and the pull does not write over it: a bound file keeps its item, and a move while it is unreadable moves the binding, so no delete is journaled for it; a new one is not created. The scan reports it in `flagged` with the reason, and so does every pull while its binding holds it. Once it parses it is sent as any edit is. Read as a body, the frontmatter would reach the server as text, and a versioned file's item would lose every property its lines named. `device/folders.test.ts › holds a file whose frontmatter does not parse`.
11. Links in the body become edges, and the edges of an item appear as links. An edge the folder cannot express as a link is kept on the item rather than dropped. `device/folders.test.ts › carries links to edges and edges to links`.

## Identity

12. **A Markdown file is the item its `marfa_id` names.** A Markdown file is one named `.md` or `.markdown`, compared without regard to case, and it is the only kind of file that carries frontmatter. Where the line is missing, the folder's own binding on this machine decides, by the file's identity (16) and then by its path, so a file an editor saved without the line, or one moved or swapped with another, keeps its item. A file with neither is new: its create carries an id the device mints, which the server keeps (`items.md` 2), and no natural key and no version: a file's path is where it sits, its placement (18), and never which item it is. A move changes only the placement, and sends no edit of the item. Once the create lands, a pull writes `marfa_id` into the file, but only while the file still holds the bytes the scan read: a create not yet answered leaves the file as the person wrote it, and a file changed since its scan is not written into, and the next scan meets the change and the binding keeps the item. Written before the create landed, a refused create would leave the file naming nothing; written over a later save, the person's newest words would go. The line names the item rather than being a property of it, so it is never sent, and a save that only drops it sends nothing. A file carrying the id of an item the copy holds, a checkout say, is that item's file before anything binds it: what it changes is sent, and a file already in step sends nothing. `device/folders.test.ts › creates a file under the device's id and writes the id back once it lands`, `› keeps the item when a save drops the id line`, `› does not write back into a file changed since its scan`, `› follows a rename by the id the file carries, and sends no edit of the item for it`, `› does not write a new file's body onto the item whose name it took`, `› keeps a binding for every file after a swap that also edits both`, `› keeps its id line out of what it sends the server`, `› sends nothing for a save that only drops the id line`, `› sends a checked-out file's edits to the item its id names, and nothing for one in step`, `› reads the id of a Markdown file whatever the case of its extension`.
13. **A whole-file rewrite at the same path is the same item**, whether an agent wrote the file anew or an editor saved it atomically by renaming a new file over the old, and whether the bytes are new or the same ones. New bytes are an edit of that item and the same bytes send nothing, and either way the folder's record of the file moves to the new one, so the file is followed wherever it goes next. `device/folders.test.ts › keeps an agent's whole-file rewrite the same item`, `› keeps an unchanged rewrite the same item`.
14. **A copy within a folder is a new item.** Of the files in a folder claiming one id, by carrying it or by the binding naming them for it, the one the binding names keeps it, by identity and then by path; failing that, the one born earlier keeps it, and then the first in path order. Every other file carrying that id is a copy: it becomes a new item under an id the device mints, which is written into it once its create lands (12), and until then its own binding, at its path and identity, keeps it that item's file whatever its line still says. A binding naming a file at the path over a copy carrying the id is what keeps an item whose editor saved it without the line; the same order reads a move by copy and delete, with a new file left at the old name before any scan, as that new file keeping the item. Kept under one id, two files would be one item edited from two places, each save overwriting the other. `device/folders.test.ts › makes a copy a new item with a fresh id`, `› keeps the id with the file its binding names`, `› keeps the id with the older of two unbound files that carry it`, `› keeps the id with the original an editor saved without its line, over a copy carrying it`, `› keeps a copy its own item once the original goes, before its id line is rewritten`.
15. **An id naming no item this folder's copy holds as a document is no id**, nor is one naming a `system.*` row, the folder's own settings among them, and the binding decides as it does for a file with none (12), so a file bound to nothing gets a fresh id in place of the one it carried. The copy is what a folder asks, because it can always ask it and a device offline cannot ask the server; an id naming an item outside the copy, one the server trashed, or one somebody typed, is one this folder cannot write to. A file item's id is never taken from a document, because a file item's file is its bytes. The create goes under its minted id like any other, and an id the server already holds is the server's to answer (`items.md` 3). Taken at its word, a typed id would bind the file to whatever it names. `device/folders.test.ts › gives a fresh id to a file whose id names nothing`, `› reads no id from a .txt file or from a document naming a file item`, `› reads no id from a file naming the folder's own settings`.
16. **A file that cannot carry frontmatter keeps the folder's own record of it.** That is a file item and a `.txt` file, which the folder reads and writes as a body alone. It is the same file across a rename when its device, inode and birth time match; a zero birth time yields no identity, and an identity two files share yields none. **No identity means a new item, never a guess.** Identity is resolved over the files the folder pushes, so a file it never touches cannot take one away. A save that gives the same bytes a new inode moves the record with it, so a rename after it is still followed rather than making a second item and journaling the first. `device/folders.test.ts › follows a rename by device, inode and birth time`, `› treats a file with no usable identity as new rather than guessing`, `› resolves identity over the files it holds, not every file in the tree`, `› follows the rename of a file saved again with the same bytes`, `› reads a .txt file that opens with a --- block as a body`.
17. **The initial scan and the live watcher use one identity rule.** The same bytes arriving while the folder is running and the same bytes present when it starts must reach the same kind of item; two rules turn one file into two items depending on when it appeared. `device/folders.test.ts › binds the same file to the same item whether it was present at start or arrived while running`.

## Where a file sits

18. **Where a file sits comes from its item's `in-folder` edge to the folder's `system.folder`** (`edges.md` 2), whose `path` names the file from the folder's root. The copy holds it as an edge drawn by a row it holds, a member or a bound file's pinned row (`device.md` 1), so every pass knows it without holding `in-folder` whole. Only an `in-folder` edge is a placement: another edge to the folder's row is not read, remembered or given way as one. A pull writes the file there on every machine bound to the folder, and moves a file of its own there when the edge's path changes, as a move made on another machine changes it, writing the new file before it takes the old one away. An item with no such edge keeps the path of the file it has here; failing that, a new item from elsewhere goes by its title under the settings' first placement for its type, the most specific key naming the type or an ancestor of it (`items.md` 49), or else at the root. The folder then writes the edge with that path, and a file made in the folder, or a checked-out one carrying the id of an item the folder has no file for (12), gets its edge with the path where it sits. **A rename or a move inside the folder sends only the edge's new `path`**, as an edge update, and no edit of the item. **The server holds one placement of an item in a folder**, and refuses a second `400 edge_constraint_violation` with `constraint: "duplicate"`. So where another machine placed the item first, or moved it first, and the server refuses this machine's placement as that duplicate or its move as stale (`409 version_conflict`, `versions.md` 16), **the folder gives way**: it withdraws its own placement writes, takes the edge the server holds, and the pull follows it; the push or the watch counts it `gave_way`, and no refusal is left in the queue. **Two items are never given one path.** The one whose placement the server made first keeps it, by the edge's time and then its id, and an item with no placement ranks after every one with; the rest go beside it, at the first free number counted from the name without any number it already carries, `Name (2).md` and then `Name (3).md`, never `Name (2) (2).md`, where free is a name no file on disk holds and no other item here is placed at, or the item's own file; their edges move there, and the pull counts them `beside`. Every machine ranks from what the server holds, so machines taking turns settle on one layout and then write nothing more; until each has heard of the others' moves, more than one may write the same move for one item, and the later ones give way; a file wanting a path whose file moves away in the same pull is written once it has. **A path the folder does not write**, one with a dot-led name the walk never reads back (24), one with a `..` in it, which the server takes where it stays inside the folder, or one leading out of the folder through a symlink (27), is counted `outside`; **a path that would make the item another kind of file**, a document at a name that is not a document's or a file item at a name whose extension names a MIME type other than its own, is counted `unsuited`. Neither is written, and the edge is left as it says: the next edit of a document written as bytes, or of a picture written as Markdown, would send it as that other kind. **A path the filesystem refuses**, a name under a file or one longer than a name can be, is counted `unwritten`: the file stays where it was, and the pull and the watch go on with every other file. **A placement the server refuses for any other reason**, a key without `edge.in-folder:write` say, **is not sent again** for that item at that path while the key's id and its `in-folder` grant, as `GET /keys/current` names them (`keys-and-oauth.md` 35), and the folder's settings stay as they were; a key that cannot be read, offline say, is taken as unchanged, and a file moved after its refusal is tried where it now sits. The file stays where it is, and the pull counts the placements it holds back as `unplaced`, which a watch says once. `folders add` is refused naming `edge.in-folder:write` where the key cannot write it, as the server resolves the grant, and leaves nothing it made; a credential that is not a key is not asked. **Placement never decides membership**: the search alone does (2), so an edge to this folder gives no file to an item the search does not hold, and an item it holds with no edge still gets one. The edge is never written in a file, in its frontmatter or as a link in its body. Placed by each machine's own paths, two machines holding one item would lay the folder out each its own way, and a move on one would never reach the other. **Limits:** two items whose placements are swapped on another machine each wait on the other's file, and both stay where they are, counted `unwritten`; a move leaves the directories it emptied behind; the first pull of a folder writes one edge for each file; names are compared exactly, case and Unicode form included; and a folder added again over an old directory places its checked-out files where they sit, which can undo a move made on another machine meanwhile. `device/folders.test.ts › places an item where its in-folder edge says, on every Mac`, `› places a new item from elsewhere under its type's first placement`, `› sends only ## Writing

19. **Echo suppression has no gap.** A write the folder made to its own files never comes back as a change. Every write the folder makes is either announced to the watcher before it happens or lands under a path the watcher does not watch. `device/folders.test.ts › does not read its own writes back as changes`.
20. Deletes are journaled and deferred: a file that disappears is recorded, and the delete is sent after the grace that separates a delete from the first half of a rename. `device/folders.test.ts › defers a delete past the rename grace`, `device/folders.test.ts › takes the old path out of the journal when the file comes back under a new name`, `› takes a file out of the journal when it comes back under its own name`.
21. **A delete made while the folder was not running is recovered when it starts.** A tracked file that is absent at startup is journaled the same way one that vanished while watching is. `device/folders.test.ts › journals a delete that happened while it was not running`.
22. **An edit from a Markdown file is based on the version its `marfa_version` line names.** A pull writes the line beside `marfa_id` (12), naming the version it wrote the file from, so an edit made in a file the copy has since moved past, an editor saving an old buffer over a newer pull say, is sent said to be read at that version (`queue-and-verdicts.md` 43) and the server merges it against what the file was written from (`versions.md` 11): a property only the file changed lands, and one only another device changed stands. A file with no line, or one naming no version earlier than the one the copy holds, edits on the version the copy holds, and so does the next edit from a line no newer than one an earlier edit already went on, since it was made against that edit, even once a pull has rewritten the line. A save that changes only the line sends nothing. Like the id, the line is never sent. **Where the server no longer holds that version** (`queue-and-verdicts.md` 22), the edit goes again as a merge on the version the copy holds, the first edit of a row in each pass, and the push or the watch counts it and says so: nothing can then be merged against what the file was written from, so what the file carries goes over whatever changed since, and as a merge, since nothing tells a line taken out from a property another device added. On the version the copy holds, an old buffer's every value would go over another device's write without a word. `device/folders.test.ts › bases a stale file's edit on the version written in it`, `› keeps a line an edit spent spent after the pull rewrites it`, `› sends over a thinned version as a merge, and says so`, `› says in words that an edit went over a thinned version`, `› says while watching that an edit went over a thinned version`, `› stops at one resend where the server no longer holds the version the copy holds either`, `› keeps a line spent where a pull writes the file over the edit that spent it`, `› sends nothing for a save that changes only the version line`.
23. **The version line is rewritten only where a pull writes the file anyway, or where the file's own edit has landed and the file is unchanged since its scan.** A file that differs from its item's render in the line alone, because another device changed something no file carries such as the item's own time, is left as it is: a write wakes every editor holding the file, for a change it cannot show. Left behind the file's own edit, the line would base the next edit on the version before it, and the server would merge that against the file's own earlier edit as though another device had written it. A pull that writes a file while its own edit still waits leaves the line to be rewritten once that edit lands. `device/folders.test.ts › does not rewrite a file for its version line alone`, `› rewrites the line once its own edit lands, where a pull wrote the file while that edit waited`, `› writes the line into a file saved without one, once its edit lands`.

## What a folder does not watch

24. A dot-led directory is excluded, at any depth. `device/folders.test.ts › excludes a dot-led directory at any depth`.
25. `.marfa/` inside the folder is the folder's own state — its settings file, its mapping, its journal, its queue — and is never pushed. **It is never watched, with one exception: the settings file, `.marfa/folder.yaml` (1)**, whose edit a watch sends at its next pass; nothing else under `.marfa/` is read as a file. `device/folders.test.ts › keeps its own state in .marfa and never pushes it`, `› sends an edit to its settings file through the folder door`.
26. A file of a type the search does not hold is not pushed, and an item the search does not match does not become a file. `device/folders.test.ts › leaves a file outside its search alone`.

## What a folder will not write

27. **A folder writes only inside itself.** Every component of the path is a plain name: no `..`, no separator leading out, and no symlink anywhere on the way. A path that fails this is reported and not written. A link pointing out of the folder loses the file, and one pointing back in is worse — the write lands on another item's file and truncates it — and the folder's own walk descends neither. The check reads the path and the write resolves it again, so this is a rule the folder keeps rather than one it enforces against something trying to break it. `device/folders.test.ts › refuses to write a file outside the folder`.
28. **A link the file used to carry and no longer does takes its edge with it**, where that edge is the folder's own kind. An edge the folder has never written into the file is not a link anybody removed — it arrived from somewhere else and no pull has rendered it yet, and a scan always runs before a pull — so it stays. So does an edge of a kind the folder could not have made. And a body carrying a link that resolves to nothing stands the whole removal down, because a link that names nothing and a link that has gone are the same absence. `device/folders.test.ts › takes the edge with a link the body no longer names`, `› keeps an edge the file never carried, whoever made it`, `› keeps an edge of a kind it could not have made`, `device/folders.test.ts › removes no edge at all when a link in the body names nothing`, `› remembers a link it stood down over, so a later removal still lands`.
29. **A pull does not write over a file the folder did not write.** `folders pull` runs no scan of its own, so a file that appeared since the last one is a file nothing has queued: writing an item over it loses what is there with no queue row and no line in the report. It is reported and left alone, unless it is byte for byte what the item renders to — which only that item's own file can be, because a render carries the item's id — and then the mapping takes it back. Otherwise the next scan pushes the file as a **new** item, and where it and the item that wanted the path are both placed there, 16 decides which keeps the path and writes the other beside it. `device/folders.test.ts › does not write over a file it never wrote`, `› takes back a file of its own the mapping had lost`.
30. **A link resolves against every file the scan holds, not only the ones it held before it started.** Two files that arrive together and name each other are one edge each way, whichever order the walk returns them in. Resolving as the walk goes makes the edge in one direction and drops the other for good, because the next scan finds both files unchanged and asks nothing. `device/folders.test.ts › makes an edge between two files that arrive together`.
31. **An item that starts to match the search becomes a file at the next pass**, whatever it starts to match by: a tag, a property, a state, an edge, or a `parent-of` that puts it beneath the item the search names. The copy learns the change from the stream (38, `device.md` 14), and the pull asks the search again rather than remembering what it matched. `device/folders.test.ts › adds an item that starts to match`.
32. **An item that stops matching the search keeps its file, unless it was trashed or left by state.** The file of an item trashed, or of one whose state the search no longer holds, is taken away where the bytes are what the folder last wrote, and a restore brings it back at the next pass: kept, it would be bound and unmaintained, and the next scan would push it back as an edit to an item in the bin. The file and its binding go; the journal is not touched and nothing is queued, because the folder is not being told the item was deleted, it is being told the folder no longer holds it. A file the person has changed since the folder wrote it stays, with its binding, and the pull reports it. **Any other departure leaves the file where it is, bound and flagged `unmatched` in the pull's report**, whether the item left by a tag, a property, an edge, `beneath`, its type or its tier: what it left by says nothing of whether the file is still wanted. **A bound file's row is pinned (`device.md` 1)**, so the copy keeps it current however the item left, a hydration for a narrower search included, and the file's edits still reach its item; the pin goes with the binding, a path another item takes included. **The pull keeps such a file current as it keeps a member's**, under the same rules (22, 23, 29), so its next edit is based on a line naming what the file shows; it never writes a new file for an item outside the search. A file whose item the copy no longer holds at all is the scan's to report (36). `device/folders.test.ts › removes a trashed item's file and brings it back on restore`, `› removes the file of an item that leaves by state`, `› keeps a file whose item no longer matches, flagged`, `› keeps the file of an item a narrowed search leaves out, flagged, and sends its edits to it`, `› keeps the file of an item retyped out of its search elsewhere, flagged, and sends its edits to it`, `› keeps an unmatched file current, so its second edit keeps another device's change`, `› lets go of the pin of an item whose file's path another item takes`, `› keeps a file the person changed after its item left, and says so`, `› keeps a file the folder never wrote whose create was refused, inside one push`.
33. **A link the person took out is not written back where the folder could not have made its edge.** An edge of another kind renders as a link like any other (11), and 26 keeps the edge when the link goes, so without this the person removes the line and the next pull writes it again, forever. The folder records, per file, the targets whose rendered link the person took out, and renders no link for them; naming the link again by hand lifts the record. The edge itself stays. `device/folders.test.ts › does not write back a link the person took out for an edge it could not have made`.

## Files that are not documents

34. **A file that is not a document becomes a file item where the folder's search holds a file type**, created under an id the device mints as a note is (12) and typed by its MIME type, and it is left alone where the search holds none (26) or where it is empty. Its bytes go up as an upload the create waits on (`device.md` 38). New bytes are a new upload and an update naming them, and a move alone moves its placement (18), with an update carrying the new name as the title where the old name was the item's title, and nothing more where it was not, since somebody else set that title. A folder that pushed only documents would keep a photo dropped beside the notes on one machine for good. `device/folders.test.ts › pushes a file that is not a document as a file item, its bytes uploaded first`, `› keeps a title somebody set when the file moves`, `› sends an edited file item named like a document as bytes`.

35. **A pull writes a file item's bytes as its file, fetched when the pull asks for them**, and a file already holding them needs no fetch. Where they cannot be had for a reason about that file, it writes nothing and binds nothing, reports the file absent, keeps a file an earlier pull wrote, and the next pull asks again; a refused credential refuses every file alike and ends the pull instead. A pull that failed on one file's bytes would stop every other file reaching the disk, and one that wrote an empty or placeholder file would have the next scan push it back as the item's new bytes. `device/folders.test.ts › writes a file item's bytes as its file, and reports them absent where it cannot fetch them`, `› keeps the file of an item whose new bytes cannot be had`, `› ends a pull whose credential is refused, rather than counting each file absent`, `› writes an item carrying a blob_ref outside the file types as a document`.

## A file whose row the copy has lost

36. **A file bound to a row the copy no longer holds is bound to nothing.** A refused create's reconcile forgets its row (`queue-and-verdicts.md` 12), and a row the server trashes or purges leaves the copy too. Neither takes a file the person wrote away: a pull removes only a file whose bytes are the folder's own (29), so the file the person has been writing in stays. Once the person acts on the file, its bytes changed or the file moved, the next scan queues it as a new item under an id the device mints, like any file (12), and reports it as queued again. Queuing it takes the file's old binding away only where it is still this row's: in a scan where a live file has already moved onto the old name, the binding there is the live file's. Left where it was with its bytes unchanged, it is reported and nothing is sent, because the server has already answered those bytes, and a folder left watching would otherwise send them again on every pass. A scan that stopped on such a file instead would stop every file after it in the walk, and every push after that. `device/folders.test.ts › queues a file whose row the copy lost again once it changes, and says so`, `› keeps a file the folder never wrote whose create was refused, inside one push`, `› keeps a live file's binding when it takes a lost file's old name`, `› keeps a live file's binding when it takes a lost file's old name, across a push`, `› queues a file whose row the copy lost again once it moves`, `› says in words when a file is bound to an item that is gone, once while watching`.

## A save set aside against its own

37. **A save the server sets aside in a conflicted copy against this device's own earlier save stays in its file.** A save made while the folder's earlier save of the same file was waiting is made against that save, and where it goes on the earlier save's base (`queue-and-verdicts.md` 42) it can collide with it: the row keeps the earlier save's value and the newer one goes to a copy. The pull does not write the row's older save over the file holding the newest; the file is marked as holding bytes the row does not, read at the version the row is then at, and the next scan sends what it holds as an edit said to be read at that version (`queue-and-verdicts.md` 43), which the server takes where nothing has moved since. Written over, the person's newest text would leave their file for a copy they never asked for. `device/folders.test.ts › keeps a file whose newest save conflicted with its own earlier one, and sends it again`.

## Keeping up with the server

38. **A folder takes in what the server recorded since its copy's cursor, without a hydration.** `folders push` catches up after its drain and before its pull, and `folders watch` holds the event stream open beside its passes, so another device's change reaches the copy and the pass after it writes the change out. A cursor the log has aged past is met with a fresh hydration (`device.md` 16). **A copy that cannot answer is hydrated first**, whether it never hydrated, its hydration was cut short or its cursor aged out (`device.md` 4): a push after one whose hydration failed hydrates and goes on, and a watch whose hydration met the network or a failing server tries it again after a wait that doubles from a second to thirty, or the longer wait a rate limit names. **A catch-up that cannot reach the server does not stop a push's pull**: the push reports the failure and writes out the copy it holds, and where the failure left a copy that cannot answer, it reports the pull as not run and the next push hydrates first. Any other failure fails the push, and ends the watch saying the server's changes stopped reaching the folder. A folder that only ever pushed and pulled would write out what it held at its last hydration for good, and one that stopped on a failed hydration would stay stopped. `device/folders.test.ts › takes another device's change at the next push, without a hydration`, `› takes another device's change while watching, without a hydration`, `› hydrates again at a push whose cursor the log has aged past`, `› hydrates again while watching when the log ages past its cursor`, `› keeps watching through a hydration that failed, and tries it again`, `› waits out a rate limit's Retry-After before hydrating again while watching`, `› ends the watch and says so when its hydration meets an answer no retry changes`, `› hydrates at the next push after one whose hydration failed`, `› pulls at a push that cannot reach the server, and says the catch-up failed`.
