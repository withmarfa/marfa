# Folders

A folder is a device surface: a directory on a machine that holds a slice as files. It is a working copy and a queue like any other device (`device.md`, `queue-and-verdicts.md`) with a filesystem as its face, and every statement in those chapters holds here too.

## What a folder is

1. A folder is a view on a slice — a type list, tags or a filter — with defaults for what a new file becomes: its type, its tier and any properties the type requires that a file cannot carry. `device/folders.test.ts › is a view on a slice with defaults for a new file`.
2. A machine holds several folders, each a different slice, and they are independent: one folder's state, journal and queue are its own. `device/folders.test.ts › keeps each folder's state and queue to itself`.
3. A folder in a container is the same thing: hydrate, work in files, push, discard the container. Nothing about a folder depends on the directory outliving the work. `device/folders.test.ts › hydrates into an empty directory and pushes without holding anything else`.

## Files and items

4. A file in the folder is an item on the server and an item in the slice is a file in the folder. `device/folders.test.ts › makes a file an item and an item a file`.
5. Frontmatter becomes properties and the body is the body. A property the type does not declare travels as a property; nothing a file carries is dropped on the way in (`device.md` 23), and **the folder does not reorder a file's own fields**. What the server does with the order it is sent is the server's, and no statement anywhere says; the rule here is that the folder adds no reordering of its own. `device/folders.test.ts › carries frontmatter to properties and the body to the body`, `› writes a person's frontmatter back in the order they wrote it`.
6. **Frontmatter is only what a file opens with and delimits as frontmatter.** A body that opens with a horizontal rule is a body. Reading it as frontmatter loses the first paragraph and then writes the loss back to the server, which is silent data loss in both directions. `device/folders.test.ts › treats a body opening with a horizontal rule as a body`.
7. Links in the body become edges, and the edges of an item appear as links. An edge the folder cannot express as a link is kept on the item rather than dropped. `device/folders.test.ts › carries links to edges and edges to links`.

## Identity

8. **A Markdown file is the item its `marfa_id` names.** A Markdown file is one named `.md` or `.markdown`, compared without regard to case, and it is the only kind of file that carries frontmatter. Where the line is missing, the folder's own binding on this machine decides, by the file's identity (12) and then by its path, so a file an editor saved without the line, or one moved or swapped with another, keeps its item. A file with neither is new: its create carries an id the device mints, which the server keeps (`items.md` 2), and no natural key and no version, because nothing the server holds names a file's path. A move sends nothing for the same reason, and a pull leaves the file where it is. Once the create lands, a pull writes `marfa_id` into the file, but only while the file still holds the bytes the scan read: a create not yet answered leaves the file as the person wrote it, and a file changed since its scan is not written into, and the next scan meets the change and the binding keeps the item. Written before the create landed, a refused create would leave the file naming nothing; written over a later save, the person's newest words would go. The line names the item rather than being a property of it, so it is never sent. `device/folders.test.ts › creates a file under the device's id and writes the id back once it lands`, `› keeps the item when a save drops the id line`, `› does not write back into a file changed since its scan`, `› follows a rename by the id the file carries, and sends nothing for it`, `› does not write a new file's body onto the item whose name it took`, `› keeps a binding for every file after a swap that also edits both`, `› keeps its id line out of what it sends the server`.
9. **A whole-file rewrite at the same path is the same item**, whether an agent wrote the file anew or an editor saved it atomically by renaming a new file over the old, and whether the bytes are new or the same ones. New bytes are an edit of that item and the same bytes send nothing, and either way the folder's record of the file moves to the new one, so the file is followed wherever it goes next. `device/folders.test.ts › keeps an agent's whole-file rewrite the same item`, `› keeps an unchanged rewrite the same item`.
10. **A copy within a folder is a new item.** Of the files in a folder claiming one id, by carrying it or by the binding naming them for it, the one the binding names keeps it, by identity and then by path; failing that, the one born earlier keeps it, and then the first in path order. Every other file carrying that id is a copy: it becomes a new item under an id the device mints, which is written into it once its create lands (8). Kept under one id, two files would be one item edited from two places, each save overwriting the other. `device/folders.test.ts › makes a copy a new item with a fresh id`, `› keeps the id with the file its binding names`.
11. **An id naming no item this folder's copy holds as a document is no id**, and the binding decides as it does for a file with none (8), so a file bound to nothing gets a fresh id in place of the one it carried. The copy is what a folder asks, because it can always ask it and a device offline cannot ask the server; an id naming an item outside the copy, one the server trashed, or one somebody typed, is one this folder cannot write to. A file item's id is never taken from a document, because a file item's file is its bytes. The create goes under its minted id like any other, and an id the server already holds is the server's to answer (`items.md` 3). Taken at its word, a typed id would bind the file to whatever it names. `device/folders.test.ts › gives a fresh id to a file whose id names nothing`.
12. **A file that cannot carry frontmatter keeps the folder's own record of it.** That is a file item and a `.txt` file, which the folder reads and writes as a body alone. It is the same file across a rename when its device, inode and birth time match; a zero birth time yields no identity, and an identity two files share yields none. **No identity means a new item, never a guess.** Identity is resolved over the files the folder pushes, so a file it never touches cannot take one away. A save that gives the same bytes a new inode moves the record with it, so a rename after it is still followed rather than making a second item and journaling the first. `device/folders.test.ts › follows a rename by device, inode and birth time`, `› treats a file with no usable identity as new rather than guessing`, `› resolves identity over the files it holds, not every file in the tree`, `› follows the rename of a file saved again with the same bytes`.
13. **The initial scan and the live watcher use one identity rule.** The same bytes arriving while the folder is running and the same bytes present when it starts must reach the same kind of item; two rules turn one file into two items depending on when it appeared. `device/folders.test.ts › binds the same file to the same item whether it was present at start or arrived while running`.

## Writing

14. **Echo suppression has no gap.** A write the folder made to its own files never comes back as a change. Every write the folder makes is either announced to the watcher before it happens or lands under a path the watcher does not watch. `device/folders.test.ts › does not read its own writes back as changes`.
15. Deletes are journaled and deferred: a file that disappears is recorded, and the delete is sent after the grace that separates a delete from the first half of a rename. `device/folders.test.ts › defers a delete past the rename grace`, `device/folders.test.ts › takes the old path out of the journal when the file comes back under a new name`, `› takes a file out of the journal when it comes back under its own name`.
16. **A delete made while the folder was not running is recovered when it starts.** A tracked file that is absent at startup is journaled the same way one that vanished while watching is. `device/folders.test.ts › journals a delete that happened while it was not running`.

## What a folder does not watch

17. A dot-led directory is excluded, at any depth. `device/folders.test.ts › excludes a dot-led directory at any depth`.
18. `.marfa/` inside the folder is the folder's own state — its mapping, its journal, its queue — and is never watched and never pushed. `device/folders.test.ts › keeps its own state in .marfa and never pushes it`.
19. A file of a type outside the folder's slice is not pushed, and an item outside the slice does not become a file. `device/folders.test.ts › leaves a file outside the slice alone`.

## What a folder will not write

20. **A folder writes only inside itself.** Every component of the path is a plain name: no `..`, no separator leading out, and no symlink anywhere on the way. A path that fails this is reported and not written. A link pointing out of the folder loses the file, and one pointing back in is worse — the write lands on another item's file and truncates it — and the folder's own walk descends neither. The check reads the path and the write resolves it again, so this is a rule the folder keeps rather than one it enforces against something trying to break it. `device/folders.test.ts › refuses to write a file outside the folder`.
21. **A link the file used to carry and no longer does takes its edge with it**, where that edge is the folder's own kind. An edge the folder has never written into the file is not a link anybody removed — it arrived from somewhere else and no pull has rendered it yet, and a scan always runs before a pull — so it stays. So does an edge of a kind the folder could not have made. And a body carrying a link that resolves to nothing stands the whole removal down, because a link that names nothing and a link that has gone are the same absence. `device/folders.test.ts › takes the edge with a link the body no longer names`, `› keeps an edge the file never carried, whoever made it`, `› keeps an edge of a kind it could not have made`, `device/folders.test.ts › removes no edge at all when a link in the body names nothing`, `› remembers a link it stood down over, so a later removal still lands`.
22. **A pull does not write over a file the folder did not write.** `folders pull` runs no scan of its own, so a file that appeared since the last one is a file nothing has queued: writing an item over it loses what is there with no queue row and no line in the report. It is reported and left alone, unless it is byte for byte what the item renders to — which only that item's own file can be, because a render carries the item's id — and then the mapping takes it back. Otherwise the next scan pushes the file as a **new** item, and the one that wanted the path has no file until it wants a different name. `device/folders.test.ts › does not write over a file it never wrote`, `› takes back a file of its own the mapping had lost`.
23. **A link resolves against every file the scan holds, not only the ones it held before it started.** Two files that arrive together and name each other are one edge each way, whichever order the walk returns them in. Resolving as the walk goes makes the edge in one direction and drops the other for good, because the next scan finds both files unchanged and asks nothing. `device/folders.test.ts › makes an edge between two files that arrive together`.
24. **A pull takes away the file of an item that has left the slice**, where the bytes are what the folder last wrote. A row the pull no longer writes, trashed, archived, evicted by a catch-up or purged, leaves its file behind otherwise, bound and unmaintained, and the next scan pushes it back as an edit to an item the person cannot see. The file and its binding go; the journal is not touched and nothing is queued, because the folder is not being told the item was deleted, it is being told the folder no longer holds it. A file the person has changed since the folder wrote it stays, with its binding, and the pull reports it, and so does a file the folder never wrote at all, such as one whose create the server refused inside the same push: the folder does not decide between a person's edit and a departure, and the edit stays on the disk for the next scan to meet. `device/folders.test.ts › takes away the file of an item that left the slice, and journals nothing`, `› keeps a file the person changed after its item left, and says so`, `› keeps a file the folder never wrote whose create was refused, inside one push`.
25. **A link the person took out is not written back where the folder could not have made its edge.** An edge of another kind renders as a link like any other (7), and 21 keeps the edge when the link goes, so without this the person removes the line and the next pull writes it again, forever. The folder records, per file, the targets whose rendered link the person took out, and renders no link for them; naming the link again by hand lifts the record. The edge itself stays. `device/folders.test.ts › does not write back a link the person took out for an edge it could not have made`.

## Files that are not documents

26. **A file that is not a document becomes a file item where the folder's slice holds a file type**, created under an id the device mints as a note is (8) and typed by its MIME type, and it is left alone where the slice holds none (19) or where it is empty. Its bytes go up as an upload the create waits on (`device.md` 38). New bytes are a new upload and an update naming them, and a move alone is an update carrying the new name as the title where the old name was the item's title, and nothing where it was not, since somebody else set that title. A folder that pushed only documents would keep a photo dropped beside the notes on one machine for good. `device/folders.test.ts › pushes a file that is not a document as a file item, its bytes uploaded first`, `› keeps a title somebody set when the file moves`, `› sends an edited file item named like a document as bytes`.

27. **A pull writes a file item's bytes as its file, fetched when the pull asks for them**, and a file already holding them needs no fetch. Where they cannot be had for a reason about that file, it writes nothing and binds nothing, reports the file absent, keeps a file an earlier pull wrote, and the next pull asks again; a refused credential refuses every file alike and ends the pull instead. A pull that failed on one file's bytes would stop every other file reaching the disk, and one that wrote an empty or placeholder file would have the next scan push it back as the item's new bytes. `device/folders.test.ts › writes a file item's bytes as its file, and reports them absent where it cannot fetch them`, `› keeps the file of an item whose new bytes cannot be had`, `› ends a pull whose credential is refused, rather than counting each file absent`, `› writes an item carrying a blob_ref outside the file types as a document`.

## A file whose row the copy has lost

28. **A file bound to a row the copy no longer holds is bound to nothing.** A refused create's reconcile forgets its row (`queue-and-verdicts.md` 12), and a row the server trashes or purges leaves the copy too. Neither takes a file the person wrote away: a pull removes only a file whose bytes are the folder's own (24), so the file the person has been writing in stays. Once the person acts on the file, its bytes changed or the file moved, the next scan queues it as a new item under an id the device mints, like any file (8), and reports it as queued again. Queuing it takes the file's old binding away only where it is still this row's: in a scan where a live file has already moved onto the old name, the binding there is the live file's. Left where it was with its bytes unchanged, it is reported and nothing is sent, because the server has already answered those bytes, and a folder left watching would otherwise send them again on every pass. A scan that stopped on such a file instead would stop every file after it in the walk, and every push after that. `device/folders.test.ts › queues a file whose row the copy lost again once it changes, and says so`, `› keeps a file the folder never wrote whose create was refused, inside one push`, `› keeps a live file's binding when it takes a lost file's old name`, `› queues a file whose row the copy lost again once it moves`, `› says in words when a file is bound to an item that is gone, once while watching`.

## A save set aside against its own

29. **A save the server sets aside in a conflicted copy against this device's own earlier save stays in its file.** A save made while the folder's earlier save of the same file was waiting is made against that save, and where it goes on the earlier save's base (`queue-and-verdicts.md` 42) it can collide with it: the row keeps the earlier save's value and the newer one goes to a copy. The pull does not write the row's older save over the file holding the newest; the file is marked as holding bytes the row does not, read at the version the row is then at, and the next scan sends what it holds as an edit said to be read at that version (`queue-and-verdicts.md` 43), which the server takes where nothing has moved since. Written over, the person's newest text would leave their file for a copy they never asked for. `device/folders.test.ts › keeps a file whose newest save conflicted with its own earlier one, and sends it again`.

## Keeping up with the server

30. **A folder takes in what the server recorded since its copy's cursor, without a hydration.** `folders push` catches up after its drain and before its pull, and `folders watch` holds the event stream open beside its passes, so another device's change reaches the copy and the pass after it writes the change out. A cursor the log has aged past is met with a fresh hydration (`device.md` 16). **A copy that cannot answer is hydrated first**, whether it never hydrated, its hydration was cut short or its cursor aged out (`device.md` 4): a push after one whose hydration failed hydrates and goes on, and a watch whose hydration met the network or a failing server tries it again after a wait that doubles from a second to thirty, or the longer wait a rate limit names. **A catch-up that cannot reach the server does not stop a push's pull**: the push reports the failure and writes out the copy it holds, and where the failure left a copy that cannot answer, it reports the pull as not run and the next push hydrates first. Any other failure fails the push, and ends the watch saying the server's changes stopped reaching the folder. A folder that only ever pushed and pulled would write out what it held at its last hydration for good, and one that stopped on a failed hydration would stay stopped. `device/folders.test.ts › takes another device's change at the next push, without a hydration`, `› takes another device's change while watching, without a hydration`, `› hydrates again at a push whose cursor the log has aged past`, `› hydrates again while watching when the log ages past its cursor`, `› keeps watching through a hydration that failed, and tries it again`, `› waits out a rate limit's Retry-After before hydrating again while watching`, `› ends the watch and says so when its hydration meets an answer no retry changes`, `› hydrates at the next push after one whose hydration failed`, `› pulls at a push that cannot reach the server, and says the catch-up failed`.
