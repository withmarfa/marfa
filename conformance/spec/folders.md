# Folders

A folder is a device surface: a directory on a machine that holds a slice as files. It is a working copy and a queue like any other device (`device.md`, `queue-and-verdicts.md`) with a filesystem as its face, and every statement in those chapters holds here too.

## What a folder is

1. A folder is a view on a slice — a type list, tags or a filter — with defaults for what a new file becomes: its type, its tier and any properties the type requires that a file cannot carry. `device/folders.test.ts › is a view on a slice with defaults for a new file`.
2. A machine holds several folders, each a different slice, and they are independent: one folder's state, journal and queue are its own. `device/folders.test.ts › keeps each folder's state and queue to itself`.
3. A folder in a container is the same thing: hydrate, work in files, push, discard the container. Nothing about a folder depends on the directory outliving the work. `device/folders.test.ts › hydrates into an empty directory and pushes without holding anything else`.

## Files and items

4. A file in the folder is an item on the server and an item in the slice is a file in the folder. `device/folders.test.ts › makes a file an item and an item a file`.
5. Frontmatter becomes properties and the body is the body. A property the type does not declare travels as a property; nothing a file carries is dropped on the way in (`device.md` 23), and **the folder does not reorder a file's own fields**. What the server does with the order it is sent is the server's, and no statement anywhere says; the rule here is that the folder adds no reordering of its own. `device/folders.test.ts › carries frontmatter to properties and the body to the body`, `› writes a person's frontmatter back in the order they wrote it`.
6. **Frontmatter is only what a file opens with and delimits as frontmatter.** A body that opens with a horizontal rule is a body. Reading it as frontmatter loses the first paragraph and then writes the loss back to the server, which is silent data loss in both directions. `device/folders.test.ts › treats a body opening with a horizontal rule as a body`.
7. Links in the body become edges, and the edges of an item appear as links. An edge the folder cannot express as a link is kept on the item rather than dropped. `device/folders.test.ts › carries links to edges and edges to links`.

## Identity

8. **Rename identity is fail-closed.** A file is the same file across a rename when its device, inode and birth time match; a zero birth time yields no identity, and an identity two files share yields none. **No identity means a new item, never a guess.** Identity is resolved over the files the folder holds, so a file it never touches cannot take one away. Where a file's identity and its path name different items, **the identity decides** and the item's natural key moves with the file (23). `device/folders.test.ts › follows a rename by device, inode and birth time`, `› treats a file with no usable identity as new rather than guessing`, `› resolves identity over the files it holds, not every file in the tree`.
9. **The initial scan and the live watcher use one identity rule.** The same bytes arriving while the folder is running and the same bytes present when it starts must reach the same item; two rules turn one file into two items depending on when it appeared. `device/folders.test.ts › binds the same file to the same item whether it was present at start or arrived while running`.
10. **A folder names the source its rows are keyed by, so two devices enrolled separately share a natural key for the same file.** `folders add --source` is required and kept with the folder, and every create the folder queues names it, so the same file in the same place on two machines whose folders name one source is one item, whatever credential each machine holds, so long as each credential's key claims that source (`keys-and-oauth.md` 34). Such a create names no id of its own, so the second machine's lands on the first's row and binds the file to it (`queue-and-verdicts.md` 38). **Two machines that each hold the file before either pushes** send creates that each read no row (13), so the second is refused because the first's landed, and its copy moves onto the first's row (`queue-and-verdicts.md` 39): the file is bound to that row, what it holds goes as an edit (13), and both folders hold one item. **A folder whose credential's key does not claim its source** has every create blocked, and the drain names the source (`queue-and-verdicts.md` 40): each file stays bound to the row it was queued as, so an edit meanwhile waits for its create, and the first push after the key claims the source sends them all. The row a folder resolves a path to is the one held under its own source and that path, never another source's row under the same path. **A row under another source is an item from elsewhere to the folder, whatever its `source_id` reads as**: its file is placed by its title, a move of that file sends no key and, with the bytes unchanged, no write at all, and it is never parked to free a name, because it holds none of this folder's names. Reading another source's key as a path would give the folder's file at that path to a row it does not key, and an edit there would land on the other source's row. The source is read as the server reads a claim: trimmed as JavaScript trims, and kept trimmed, so a source with spaces or a byte order mark around it keys the rows its trimmed form names, and compared as written, so `Notes` and `notes` are two sources. A folder naming no source, one given to connectors and apps (`connector:`, `oauth:`), or one longer than the 200 UTF-16 code units a key may claim is refused. A key that differed per credential would make every file two items, and neither machine could say why. `device/folders.test.ts › binds one file to one item across two separately enrolled devices`, `› binds one file to one item when two folders hold it before either pushes`, `› tells a folder whose key does not claim its source, and sends its files once it does`, `› refuses a folder that names no source, or one it may never name`, `› resolves a path to its own source's row, never another source's under the same key`, `› treats a row under a source that differs only in case as a row from elsewhere`, `› never parks, renames or re-keys another source's row`, `› pushes a file that is not a document as a file item, its bytes uploaded first`.
11. A folder writes the item's id into the file as its own identity record. That record is the folder's, not the natural key: a file that has lost it, or never had it, is still the same item when the natural key matches, and a file carrying one that names an item the server does not hold is treated as having none. It is the folder's record and not the item's, so it is not sent: a copied file would otherwise carry the id of the item it was copied from onto a new one. `device/folders.test.ts › keeps the item id in the file as a record, and does not depend on it for identity`, `› keeps its own identity record out of what it sends the server`.
12. A rename on the server moves the file in the folder, and the next scan does not re-assert the old name. `device/folders.test.ts › moves the file when the item is renamed on the server`.

## Writing

13. **A folder create carries the version it is based on**, where the general contract leaves a version optional on a create (`queue-and-verdicts.md` 2), and a folder create is never sent without one: the version is the one the copy holds under that natural key, and zero where it holds no row, which the server takes as a create that is conditional on there being nothing there. A folder create lands on an existing row whenever the natural key already names one, so a version-less one is an update that read nothing. A version-less create onto an existing row is an overwrite of whatever is there, which is how a second machine's stale copy replaces newer server content with nothing reporting it. **A create the server refuses because the row has moved on, or because a row is there that it did not read, is never sent again** (`queue-and-verdicts.md` 39). The copy moves onto that row and the file stays bound to it, holding bytes the server has not taken, which a pull reports and does not write over (22). The next scan sends what the file holds as an edit of that row, which gets a verdict of its own, and a move of the file carries it as any move does (23). Where the folder had read the row at a version the server still holds, the edit is based on that version, whatever the copy has caught up to since, so the server merges a stale folder's edit against what it read rather than taking it as newer. **Where it had read none, or read a version the server no longer holds, the second push wins**: the edit is based on the version the server holds, so it replaces what the other machine wrote as the last writer, the other machine's version stays in the row's history and nowhere else, and the scan reports the file as sent over content this machine never read, whether the file stayed where it was or moved. Nothing here protects the other machine's content from that edit; what the folder guarantees is that it is one item, that the edit is a write with a verdict of its own rather than a create that silently overwrote, and that the report names it. Where the file holds what the row holds already, file item bytes compared by their name, nothing is sent. `device/folders.test.ts › always carries a version on a create, zero where it holds no row`, `› does not overwrite newer server content from a stale folder`, `› binds one file to one item when two folders hold it before either pushes`, `› binds one file item to one item when two folders hold it before either pushes`, `› counts an edit over unread content when the file moved before it went`, `› merges a stale folder's edit against what it read, though its copy caught up since`, `› sends a stale folder's edit over a row whose read version is thinned, and says so`.
14. **Echo suppression has no gap.** A write the folder made to its own files never comes back as a change. Every write the folder makes is either announced to the watcher before it happens or lands under a path the watcher does not watch. `device/folders.test.ts › does not read its own writes back as changes`.
15. Deletes are journaled and deferred: a file that disappears is recorded, and the delete is sent after the grace that separates a delete from the first half of a rename. `device/folders.test.ts › defers a delete past the rename grace`, `device/folders.test.ts › takes the old path out of the journal when the file comes back under a new name`, `› takes a file out of the journal when it comes back under its own name`.
16. **A delete made while the folder was not running is recovered when it starts.** A tracked file that is absent at startup is journaled the same way one that vanished while watching is. `device/folders.test.ts › journals a delete that happened while it was not running`.

## What a folder does not watch

17. A dot-led directory is excluded, at any depth. `device/folders.test.ts › excludes a dot-led directory at any depth`.
18. `.marfa/` inside the folder is the folder's own state — its mapping, its journal, its queue — and is never watched and never pushed. `device/folders.test.ts › keeps its own state in .marfa and never pushes it`.
19. A file of a type outside the folder's slice is not pushed, and an item outside the slice does not become a file. `device/folders.test.ts › leaves a file outside the slice alone`.

## What a folder will not write

20. **A folder writes only inside itself.** Every component of the path is a plain name: no `..`, no separator leading out, and no symlink anywhere on the way. A path that fails this is reported and not written. A link pointing out of the folder loses the file, and one pointing back in is worse — the write lands on another item's file and truncates it — and the folder's own walk descends neither. The check reads the path and the write resolves it again, so this is a rule the folder keeps rather than one it enforces against something trying to break it. `device/folders.test.ts › refuses to write a file outside the folder`.
21. **A link the file used to carry and no longer does takes its edge with it**, where that edge is the folder's own kind. An edge the folder has never written into the file is not a link anybody removed — it arrived from somewhere else and no pull has rendered it yet, and a scan always runs before a pull — so it stays. So does an edge of a kind the folder could not have made. And a body carrying a link that resolves to nothing stands the whole removal down, because a link that names nothing and a link that has gone are the same absence. `device/folders.test.ts › takes the edge with a link the body no longer names`, `› keeps an edge the file never carried, whoever made it`, `› keeps an edge of a kind it could not have made`, `device/folders.test.ts › removes no edge at all when a link in the body names nothing`, `› remembers a link it stood down over, so a later removal still lands`.
22. **A pull does not write over a file the folder did not write.** `folders pull` runs no scan of its own, so a file that appeared since the last one is a file nothing has queued: writing an item over it loses what is there with no queue row and no line in the report. It is reported and left alone, unless it is byte for byte what the item renders to — which only that item's own file can be, because a render carries the item's id — and then the mapping takes it back. Otherwise the next scan pushes the file as a **new** item, and the one that wanted the path has no file until it wants a different name. `device/folders.test.ts › does not write over a file it never wrote`, `› takes back a file of its own the mapping had lost`, `device/folders.test.ts › does not move an item on top of a file nobody has scanned`.
23. **A rename sends the new natural key.** A file that moved and kept its identity is the same item under a new name, so the folder sends that name with the write, under the item's id and the version it read; the server refuses a name another item holds. Without it the item keeps the old key, the next pull computes the old path from it, and the folder undoes the rename it has just reported. `device/folders.test.ts › sends the new natural key when the person renames a file`.
24. **Two files that exchange places exchange nothing else.** Each item follows its own file, so a swap is two renames whose names collide with each other. The folder parks one of them under a name that is not a path, queues the other's move, then queues the parked one back. The three are ordered rows in one durable queue, and a park left standing — a refusal, a blocked queue — is taken back by the next scan rather than left for a second device to make a second item out of. Sending both as they stand has the server refuse one, which leaves one item under the wrong name and the other under none. `device/folders.test.ts › follows a swap without giving either item the other's name`, `device/folders.test.ts › does not write a new file's body onto the item whose name it took`, `› keeps a binding for every file after a swap that also edits both`, `› follows a three-way rotation without a name landing on a held one`, `› follows a chain of renames that frees its own last name`.
25. **A link resolves against every file the scan holds, not only the ones it held before it started.** Two files that arrive together and name each other are one edge each way, whichever order the walk returns them in. Resolving as the walk goes makes the edge in one direction and drops the other for good, because the next scan finds both files unchanged and asks nothing. `device/folders.test.ts › makes an edge between two files that arrive together`.
26. **A pull takes away the file of an item that has left the slice**, where the bytes are what the folder last wrote. A row the pull no longer writes, trashed, archived, evicted by a catch-up or purged, leaves its file behind otherwise, bound and unmaintained, and the next scan pushes it back as an edit to an item the person cannot see. The file and its binding go; the journal is not touched and nothing is queued, because the folder is not being told the item was deleted, it is being told the folder no longer holds it. A file the person has changed since the folder wrote it stays, with its binding, and the pull reports it, and so does a file the folder never wrote at all, such as one whose create the server refused inside the same push: the folder does not decide between a person's edit and a departure, and the edit stays on the disk for the next scan to meet. `device/folders.test.ts › takes away the file of an item that left the slice, and journals nothing`, `› keeps a file the person changed after its item left, and says so`, `› keeps a file the folder never wrote whose create was refused, inside one push`, `› keeps the file of an item whose key moved outside the folder`.
27. **A link the person took out is not written back where the folder could not have made its edge.** An edge of another kind renders as a link like any other (7), and 21 keeps the edge when the link goes, so without this the person removes the line and the next pull writes it again, forever. The folder records, per file, the targets whose rendered link the person took out, and renders no link for them; naming the link again by hand lifts the record. The edge itself stays. `device/folders.test.ts › does not write back a link the person took out for an edge it could not have made`.

## Files that are not documents

28. **A file that is not a document becomes a file item where the folder's slice holds a file type**, keyed by its path as a note is and typed by its MIME type, and it is left alone where the slice holds none (19) or where it is empty. Its bytes go up as an upload the create waits on (`device.md` 38). New bytes are a new upload and an update naming them, and a move alone is an update carrying the new name, and the title with it where the folder gave the title (23). A folder that pushed only documents would keep a photo dropped beside the notes on one machine for good. `device/folders.test.ts › pushes a file that is not a document as a file item, its bytes uploaded first`, `› keeps a title somebody set when the file moves`, `› sends an edited file item named like a document as bytes`.

29. **A pull writes a file item's bytes as its file, fetched when the pull asks for them**, and a file already holding them needs no fetch. Where they cannot be had for a reason about that file, it writes nothing and binds nothing, reports the file absent, keeps a file an earlier pull wrote, and the next pull asks again; a refused credential refuses every file alike and ends the pull instead. A pull that failed on one file's bytes would stop every other file reaching the disk, and one that wrote an empty or placeholder file would have the next scan push it back as the item's new bytes. `device/folders.test.ts › writes a file item's bytes as its file, and reports them absent where it cannot fetch them`, `› keeps the file of an item whose new bytes cannot be had`, `› ends a pull whose credential is refused, rather than counting each file absent`, `› writes an item carrying a blob_ref outside the file types as a document`.

## A file whose row the copy has lost

30. **A file bound to a row the copy no longer holds is bound to nothing.** A refused create's reconcile forgets its row (`queue-and-verdicts.md` 12), a create onto a natural key whose row is in the bin is refused `trashed` and forgets its own (`queue-and-verdicts.md` 41), and a row the server trashes or purges leaves the copy too. None of them takes a file the person wrote away: a pull removes only a file whose bytes are the folder's own (26), so the file the person has been writing in stays. Once the person acts on the file, its bytes changed or the file moved, the next scan queues it as a new item keyed by its path, like any file (10, 13), and reports it as queued again; where that key names a row in the bin, the server acknowledges the create and writes nothing, so the create is refused `trashed` and the file is bound to nothing again, with its bytes kept and reported rather than dropped. Queuing it takes the file's old binding away only where it is still this row's: in a scan where a live file has already moved onto the old name, the binding there is the live file's. Left where it was with its bytes unchanged, it is reported and nothing is sent, because the server has already answered those bytes, and a folder left watching would otherwise send them again on every pass. A scan that stopped on such a file instead would stop every file after it in the walk, and every push after that. `device/folders.test.ts › queues a file whose row the copy lost again once it changes, and says so`, `› keeps a file the folder never wrote whose create was refused, inside one push`, `› keeps a file whose key names a row it may not read to itself, and says so`, `› refuses a create onto a row somebody trashed, and keeps the file as lost`, `› keeps a live file's binding when it takes a lost file's old name`, `› queues a file whose row the copy lost again once it moves`, `› says in words when a file is bound to an item that is gone, once while watching`.
