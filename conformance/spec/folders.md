# Folders

A folder is a device surface: a directory on a machine that holds, as files, what a saved search matches. It is a working copy and a queue like any other device (`device.md`, `queue-and-verdicts.md`) with a filesystem as its face, and every statement in those chapters holds here too.

## What a folder is

1. **A folder is a directory on a machine bound to a `system.folder` item, and the item holds its settings**: the search (2), the defaults (3), the include and ignore lists (25), the per-type first placement (19) and the removal threshold (`items.md` 49). **Each machine chooses only the directory.** `folders add <dir> --folder <id>` binds it, reading the settings from the server as it does, and is refused for an id naming an item that is not a `system.folder`, or a folder that is revoked, which has no settings to follow. **The settings are written out as one editable file, `.marfa/folder.yaml`**: a YAML map carrying the `system.folder`'s id and the version it was written from beside the settings, and the folder's only editable record of them on the machine: its store keeps the text it last wrote there, and that text's version, to tell an edit from its own write. A catch-up or a pull that moves the row rewrites the file, unless the person changed it since it was written: that is their edit, and it is sent first. `folders push`, and a watch (28), send an edit as `PATCH /folders/{id}` (`items.md` 51) based on the version the file's own `version` line names (a file with no such line, or one naming no version the server mints, is based on the version last written, and a line written as text, `"3"`, or as `3.0`, names that version, as a Markdown file's does, 7), as a Markdown file's edit is (23), so the door merges it with a change made elsewhere meanwhile: a file current with the settings sends the settings it changed, and one older than them, an editor saving an old buffer over a rewrite say, sends every setting it names, for the door to merge against what it was written from. What the door answers is the folder's settings from then on. **An edit the door refuses, one naming a search or defaults this folder cannot follow (2, 3), a file that does not parse, or one naming another folder keeps the settings in force and flags the file**: the push, the watch and the pull say why, in words and in JSON, and the same refused text is not sent again. Only the door's own answers about the edit (`400`, `403`, `404`, `409` or `422`) are a refusal: a failing server, a rate limit or a spent key reports the edit as not sent yet, and it goes again at the next pass. Where the door refused it for a conflict, the reason says to delete the file, which writes the settings in force back into it, and edit it again. A file naming the settings in force, whatever its comments, its layout or its version line, changes no setting and sends nothing, and the file is written again from the settings; an older file naming anything else is sent whole as above, even a setting it left as its version had it, since the folder keeps only the text it last wrote, and one that leaves a setting out is sent whole too, not refused, since what it leaves out may be a setting added since its version, which the door keeps. A setting taken out of a current file is refused the same way, because the door replaces a setting and never removes one: the reason says to write it empty, `[]` for a list or `{}` for a map. The folder's copy pins its `system.folder` (`device.md` 1), so a catch-up keeps it current, and every pass reads the settings from that row: a change made on any device reaches every folder bound to the item at its next pass, and one that asks for another slice, other types or another tier, is met with a fresh hydration at the next push, as is an edge type registered since that a file writes at its target (11); a watch already running takes that one only at the next push or when it starts again. **A key without read on `system.folder` cannot follow its settings**, and `folders add` is refused naming `system.folder:read`: the server answers such a folder as no folder (`keys-and-oauth.md` 20), so the device reads the key's own map at `GET /keys/current` to say which of the two it met. Adding a folder again under the same id writes the file afresh, and an edit of it not yet sent is lost. `device/folders.test.ts › reads its settings from the system.folder it is bound to`, `› takes settings changed on another device`, `› hydrates again where its changed settings ask for another slice`, `› refuses to follow settings its key cannot read, naming the permission`, `› writes its settings out as one file in .marfa/`, `› sends an edit to its settings file through the folder door`, `› keeps its settings in force and flags the file when an edit is refused`, `› rewrites its settings file when the settings change elsewhere`, `› does not write its settings file over the person's edit, and sends the edit`, `› bases an edit of its settings file on the version written in it`, `› refuses to follow an item that is not a live folder`, `› rewrites a settings file whose edit changes no setting`, `› sends a settings edit the folder door could not take for now at the next push`, `› learns an edge type the server registers, and reads its line as an edge`.
2. **The search decides what the folder holds, on every pass.** It takes the listing grammar's conditions: a type with its subtree, the tier, the state, and in its `filter` tags, `properties.<name>` and an edge to an item; and it adds `beneath` an item, which holds that item and everything it reaches along `parent-of` at any depth, as far as the key can read. It is answered from the copy as a local list answers the same conditions (`device.md` 24 and 36), with `parent-of` held whole (11, `device.md` 1). A search naming no type holds every type the key reads, `system.*` aside, and **one naming no tier holds the `library` tier**. **Its default state is active and archived**, unlike a list's default of active (`device.md` 31): an archived item keeps its file, with `state: archived` in its frontmatter (7). **A condition the core does not implement is refused**, a `backref`, a member of the search, the defaults or the removal threshold it does not know, or a state other than active and archived, none among them, when the folder is added and at any pass that meets it, never ignored: an ignored condition holds everything it would have narrowed. `device/folders.test.ts › holds exactly what its search matches`, `› holds archived items unless its search narrows state`, `› refuses a search condition it does not implement`, `› takes every type, and any default type, where its search names no type`, `› keeps an archived item's file with its state in the frontmatter`.
3. **The defaults fill what a new file leaves blank, and never touch an edit.** A new document becomes the type its `type` line names (7), or else the defaults' type, or else the search's first type that is not a file type, or else `core.note`, at the tier its `tier` line names or else the defaults' or else the search's, with the defaults' properties where its frontmatter carries none of that name and the defaults' tags where it has no `tags` line. Of the properties, the type's body field is always the file's body, so a default for it is never taken, and its title field is a blank like any other, so a default title is taken over the file's name (7). It takes the defaults' edges too, a `.txt` file and a file item as well as a Markdown file: each runs from the new item to the item named, except `parent-of`, which runs from the item named to the new one, as a child's file writes it, so a new file in a folder that searches `beneath` a project lands beneath it; a line the file writes for an edge type (11) fills that blank itself, and the default of that type is not taken. A file item's type is its bytes', so of the defaults it takes the tier, the tags and the edges. An edit of a file already bound sends what the file holds and nothing from the defaults: a default filled in over an edit would put back a value somebody removed. **Defaults whose type or tier the search does not hold are refused**, as a condition is (2): every new file would otherwise fall outside its own folder. `device/folders.test.ts › fills a new file's blanks from its defaults, never an edit's`, `› reads type, tags, tier and state as the item's own`, `› makes a new document the search's first type that is not a file type`, `› refuses defaults its search would not hold`.
4. A machine holds several folders, each bound to its own settings, and they are independent: one folder's state, journal and queue are its own. All are listed in one registry on the machine (41), each entry naming a folder's directory, the `system.folder` it follows and its store's id, which tells each where the others are and holds none of their state. `device/folders.test.ts › keeps each folder's state and queue to itself`, `› lists the folders on the Mac in one registry`.
5. A folder in a container is the same thing: add it, hydrate, work in files, push, discard the container. The settings are the `system.folder`'s, so nothing about a folder depends on the directory outliving the work. `device/folders.test.ts › hydrates into an empty directory and pushes without holding anything else`.

## Files and items

6. A file in the folder is an item on the server and an item the search matches is a file in the folder. `device/folders.test.ts › makes a file an item and an item a file`.
7. **One file is one item, and its frontmatter names that item's fields.** `type` (the type's full name), `tier`, `tags` and `state` (`active` or `archived`) are the item's own fields, read and written as such; `marfa_id` and `marfa_version` name the item and the version the file was written from (13, 23), and a version line written as text, `"3"`, or as `3.0`, is that version; a line named for an edge type or a reverse name the server lists is an edge's line (11), never a property; every other line is a property, one the type does not declare included, since nothing a file carries is dropped on the way in (`device.md` 23). Only a Markdown file has frontmatter: a `.txt` file that opens with a `---` block is all body (17). **The body and the title follow the type's `display_hints`**, those of the nearest type that declares any, taken whole as the server's read of the type takes them (`device.md` 47): the file's body is the property `body_field` names and a new file's name goes to the one `title_field` names where neither its frontmatter nor the defaults (3) fill it, so `core.event`'s body is its `description`, with `body` and `title` for a type naming neither. A line named for the body field is overwritten by the body, without a word, except the new body field's in a retype that moves the body to another property (9). A type declaring a property under one of the names a file reads as something else is reported in the pull's `uncarried`: no file can carry it, so no line is written for it and an edit leaves it on the item. **A file whose version line is the version the copy holds is current**, and so is one whose bytes before this save showed the item as the copy holds it but for their line, with nothing of its own waiting: a version step no file shows (24), or the file's own edit landed before a pull wrote the new line. A current file is sent as its item's whole properties (`items.md` 22), so a line taken out clears that property, and its own-field lines are read three-way against the folder's own last write of the file, so a change goes only where the file differs from that write. In a file the folder wrote own-field lines into at that version, no `tags` line is no tags and no `state` line is active; in one it never did, a checked-out file say, an absent own-field line leaves the item's as it is. **A tag or a state moves without a version step**, so the folder records, at each version line it writes, the tags and states another machine moved away from there; a change back to one of those is one an old buffer may still show, and it is not sent but flagged. **A file behind the copy sends no own-field change**: one whose version line is older than the copy's, other than by its own edit (23), is merged against its line, a version the copy never held included, and one whose version line is gone, or is newer than the copy's, is merged on the version the copy holds; a line taken out of either clears nothing; where its own-field lines differ from what the folder last wrote, it is flagged `behind` in the scan's `flagged` with the lines named, and the next pull writes the item's over them. So an old buffer never moves back a retype, a tag or an archive another machine made, and never loses its person's own-field line without a word. Two buffers of one version saved one after the other are the last save's, for tags and a state as for properties. A `tier` other than `feed` or `library`, a `state` other than `active` or `archived`, `tags` that are not a list of text or name an empty tag, a `type` that is empty or not text, a key that is not text, or a YAML merge key, `<<`, which a folder does not expand, makes the frontmatter unreadable (10); `tags: solo` is one tag, `tags: a, b` two, a `tags:` with no value, YAML's null, none, and a `state:` with none active; `tags: ""` and `state: ""` hold empty text, and make it unreadable. A `type` naming a type the copy does not hold is readable, and refused as 9 says. A pull writes `type` and `tier` always, `tags` where the item has any, and `state` where it is archived. In a new file these come first and in that order, then the properties in the order the item holds them; in an existing file missing fields are appended: an absent `type` or `tier` would have to mean a setting, and a change of the settings would then move every file, where tags and a state have an empty value of their own. A save that changes nothing the item holds, a reformatting, sends nothing. **A pull preserves an existing file's unchanged frontmatter bytes**, including property order, comments, quoting, number spelling, block and flow collections, block scalars, Unicode and line endings. It edits changed values in place, removes fields no longer carried and appends missing fields, including the id and version on the first push. Unchanged children of a changed mapping or sequence retain their source, including children moved within a sequence. Equivalent accepted forms of tags, state, version and edge lines are unchanged values; an explicit empty tag or active state line can therefore remain. **An alias whose anchor changes, is removed or moves after the alias is expanded only where needed to preserve the alias's intended value**; untouched anchor groups stay as written. The complete result is parsed and checked against the intended fields and body before any atomic write; if preservation cannot produce those values, the file stays unchanged and the operation reports the failure. The folder records the meaning of every file it reads or writes separately from its exact bytes, so formatting alone neither queues an edit nor revives a deleted file, and exact bytes still guard ownership and writes racing with an editor. The byte-order mark rule in 17 still applies. **Limit:** a person's own change of a tag or a state that another machine moved at the file's version is flagged, not sent, until the item's version moves 8. **Frontmatter is only what a file opens with and delimits as frontmatter.** A body that opens with a horizontal rule is a body, and so is a fence pair holding a list or a line of text, which Markdown reads as a list or a heading between rules. Reading it as frontmatter loses the first paragraph and then writes the loss back to the server, which is silent data loss in both directions. A fence pair holding YAML that does not parse as fields is frontmatter that cannot be read (10). **A UTF-8 byte-order mark before the opening fence is not text**: the file is read past it, as the same file without it would be, and the folder writes the file back without it. `device/folders.test.ts › treats a body opening with a horizontal rule as a body`, `› treats a fence pair holding a list or one line as a body`, `› reads past a byte-order mark and writes the file back without it`.
9. **Changing `type:` retypes the item**, through the server's retype (`queue-and-verdicts.md` 44), in one edit with the file's properties. **Where the two types keep their body in different properties, nothing is dropped**: the file's line for the new type's body field wins where it holds anything, and the body goes there otherwise, and the old body field keeps the body. A retype is sent only from a current file (7). A type this copy's catalog does not hold, or a file type, whose items are bytes, is refused before anything is queued and the file flagged. **A refused retype leaves the file as the person wrote it, flagged with the reason**, the server's code and message where the server refused it, and so does any other edit, tag or state of the file the server refuses (`queue-and-verdicts.md` 12), **and the hold follows the file**: through a rename, a reformatting or a later save that does not touch the refused change, each of the file's writes linked to it until answered, the pull does not write the item over the file and reports it in `flagged`, and the same bytes are not sent again. It is let go when a later save of the file lands a change in its place, an edit for an edit, a tag for the same tag, a state for a state, or when the file stops carrying the refused change. A refused edit spends no version line (23), so the next change the person makes is sent as a file at that line is, behind the copy where another machine changed it since; it takes back only its own, so a line an earlier edit of the file spent and landed stays spent, and a save from the same old buffer after the refusal is not merged against that earlier edit; a tag or a state refused beside an edit that landed leaves the line spent. 10. **Frontmatter that does not parse is held, not sent, and the file is flagged `unreadable`.** That is a fence pair (8) whose YAML does not parse, one keyed by something that is not text, one using a merge key, or one holding an own field no item can hold (7). No edit is queued for the file and the pull does not write over it: a bound file keeps its item, and a move while it is unreadable moves the binding, by its identity or by the `marfa_id` line read as text, and its placement with it, so no delete is journaled for it; a new one is not created. The scan reports it in `flagged` with the reason, and so does every pull while its binding holds it. Once it parses it is sent as any edit is. Read as a body, the frontmatter would reach the server as text, and a versioned file's item would lose every property its lines named. **A document whose bytes are not UTF-8 text is held the same way, flagged `encoding`**, a Latin-1 note say, or a `.txt` file in UTF-16, which holds a NUL byte even where it decodes as UTF-8: it is never decoded, sent or written over, a pull leaves its bytes as they are while it stays so, and saved as UTF-8 with no NUL byte it is sent. A file item's file is its bytes, whatever its name, and is never held for them. Decoded with each byte it cannot read replaced, it would reach the server without its accents, and the pull would write that back over the person's file. `device/folders.test.ts › holds a document that is not UTF-8, and never sends or rewrites it`, `› holds a file whose frontmatter does not parse`, `› keeps an unreadable file's item when it moves with no identity`.
11. **An edge is written in one file only, as a frontmatter line under its type's name, in the file at the end its type is written at** (`edges.md` 2, 18). A folder reads the edge types the server lists, each type's name, reverse name, `written_at` and cardinality, when it is added, at every hydration and catch-up, and before any scan that reads a changed file where the server can be reached, a watch's included, so a line for a type registered since is read as an edge and never sent as a property. **An edge is written at the end its type's `written_at` names**, `source` unless it says otherwise, **and at the target it is written under the reverse name**: a `parent-of` edge is `child-of: "[[Project]]"` in the child's file, and nothing in the parent's. **Where the item at that end cannot carry frontmatter**, a file item, whose file is its bytes, **the other end writes it under the name read from there**: `attached-to` is written in the attachment's own file, and an image's in its host's as `has-attachment`, unless the host's body embeds the image (12). An edge whose writing end cannot carry frontmatter, and which has no name from the other end, a `references` from an image say, is written in no file, and `in-folder` is never a line (19). Where the copy cannot tell whether the writing end carries frontmatter, a line the other end's file typed for the edge stays in that file, and the folder pins the writing end to learn it. The folder's copy holds whole every edge type written at its target (`device.md` 1), since it would otherwise hold a child's edge only where it holds the parent; and it pins the item at the other end of every edge its files write, so a line shows that item's title whether or not its file is on this machine. Each such pin is held while a file writes the edge, beside the pins a binding holds (35), and is let go once neither holds it, so two files writing one target never unpin it for each other; a pin somebody else made, by hand say, is held by a line and never let go by one. **A target is written as `"[[name]]"`**, a list of them where the end may hold more than one: the target's title, where that names it alone in the copy and can be written inside a link, **and otherwise its id, `"[[<id>]]"`, which always resolves**, so a repeated name is written as an id. **A typed name must match exactly one item, by title or file name, ignoring case and Unicode form (27)**, across what the key can read, so the folder asks the server for a name that is not an id and does not already name its edge's item; two names naming one item, differing only in case or form or one of them its id, are one target. **A name typed with an alias or a heading**, `[[name|shown]]` or `[[name#part]]`, names what comes before the `|` or the `#`, and stays as typed; where the whole text names another item, the line is flagged rather than read either way. **A name that matches none, or more than one, is flagged and left as typed; nothing is guessed.** A line that already resolves to its item is left as typed, even by a pull that writes the file, and an existing edge never changes because another item takes the same name. Where the server cannot be reached, or no server is named, a name waits, flagged, and is asked again at each scan that can reach it. A lookup the server answers with a refusal flags the file with that answer, as does one whose fifth page, for a property a title lives in, says more follow, and neither is asked again until the file changes: a name so common is named by its id. A failed lookup is its file's alone, and the scan goes on with every other. A lookup matches an item in any state but the bin, by the property its type keeps its title in. **Taking a line out removes its edge**; an edge the file never carried arrived from elsewhere, no pull has written it yet, and it stays. **A name that does not resolve, a reverse-named edge stated at the end its type is not written at** (`parent-of:` in a parent's file), **and a line naming more targets than its end may hold each change nothing of that edge type in that file**: the file is held, flagged `edges` with the reason, and left as typed, nothing is guessed, and no other file is rewritten. A line changes only edges, never the item, so a save that changes lines alone sends no edit. **Changing the target of an end that holds one edge replaces the edge the file showed in one step**: one write moves the edge's other end, under the version the copy holds (`edges.md` 10, 14), so the edge keeps its id and its properties, the end never holds none or two, and another machine never finds the item belonging to nothing between two writes. Where the end holds an edge the file has not shown yet, the line is flagged and nothing changes, since replacing it would drop an edge nobody saw. A delete answered that the edge is already gone, another machine having taken the same line out say, did what it asked and holds nothing. ## Identity

## Writing

20. **Echo suppression has no gap.** A write the folder made to its own files never comes back as a change. Every write the folder makes is recorded as its own before its bytes land, a file's in its binding as the hash of the bytes it writes and the settings file's as the text it writes, so the pass a watcher's notice of it wakes reads no change; or it lands under `.marfa/`, where no pass reads anything but the settings file (28). **Every file the folder writes lands whole or not at all**: a document, a file item's bytes, the settings file, and a file taken in from another folder across volumes (44) are each written beside their path, under a name the built-in lists never take, synced, and renamed over it, keeping the permission and the extended attributes, a Finder tag say, of the file they replace. The record of the write, and of a file taken in from another folder (44), keeps what the path was bound as before, and the settings file's the text written before, until the bytes land, so a crash in between leaves the old file the folder's own: the next scan or pull finds the new bytes there and keeps the new record, or finds them not there and puts the old one back, so the old file is never sent as the person's edit and a new file that never landed is never journaled as deleted; `folders status` reports such a file as the next scan will settle it. ## What a folder takes

25. **A folder takes what its include list names, less what its ignore list names, and never what the built-in lists name.** Both lists are settings (1) in gitignore syntax, relative to the folder's root, compared as names are (27). **An empty include list takes every path; one naming anything takes only what it names**: a path whose own name, or a directory's on its way, matches a line, a `!` line taking back what an earlier one took. **The ignore list removes what it names from whatever the include list takes**, so where both name one path the ignore list wins, and its `!` lines take back nothing the built-in lists name. **A dot-led name, at any depth, is taken only where an include line names it**, `.notes/` say, so `*.md` does not reach into `.git`: the walk enters a dot-led directory only where an include line other than a `!` one names that directory's name, and a path is taken only where every dot-led directory on its way is one the walk enters, so a pull never writes where no scan looks. **The built-in lists stand whatever the settings say**: `.marfa` (28); what a machine writes for itself, `.DS_Store`, `Thumbs.db`, `._*`, `.Spotlight-V100`, `.Trashes`, `Icon` ending in a carriage return and `desktop.ini`; what an editor keeps beside an open file, `*.swp`, `*~`, `.#*`, `#*#`, `~$*`, `*.tmp`, `.~lock.*#`, `*___jb_tmp___` and `*___jb_old___`; what a browser writes while a download or a save is under way, `*.crdownload`, `*.crswap`, `*.part` and `*.download`, a directory in Safari's case; and **secrets**, `.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_dsa*`, `id_ecdsa*`, `id_ed25519*`, `.netrc`, `.npmrc`, `.pypirc`, `.pgpass`, `.git-credentials`, `credentials`, `*credentials.json` and `credentials.db`: each a file that exists to hold a private key, a password or a token in a form anyone holding the file can use. **No include line reaches a secret**: sent, it reaches every machine and key that reads the folder and cannot be called back, where a file left out is one the person can see is missing: the scan names every file the secrets list refuses in a directory it walks, and the push and the watch say each in words, a watch once while it stands. A line that is not a pattern is refused as a search condition is (2). **A pull writes no file where the lists do not take it**, and counts the item `outside` (19). **A file the lists stop taking has left the folder, and is not deleted**: the scan neither reads it nor journals it, and counts it `unreached`, so its item keeps its binding and is not trashed; the pull neither writes it nor takes it away, and counts its item `outside`; and once the lists take it again it is its item's file as before, an edit made meanwhile sent as any is. A folder that read a new ignore line as deletes would trash every item the line covers. **Limit:** a Keynote presentation saved as one `.key` file, and a `.env.example` template, are read as secrets and not taken; each is named. `device/folders.test.ts › takes only what its include list names`, `› never takes a secret whatever its lists say`, `› ignores what its ignore list names`, `› reaches a dot-led path its include list names`, `› excludes a dot-led directory at any depth`, `› writes nothing under a dot-led directory its walk does not enter`, `› takes nothing under a dot-led directory a negated include line names`, `› says a refused secret in words once while watching`, `› never takes an editor's or a download's temporary file`.
26. **A package, and a directory the walk cannot read, is reported, and the files bound in it are held;** a directory the lists leave out is not reported (25). **A package is not walked into**: a directory named `.app`, `.bundle`, `.pages`, `.numbers`, `.key`, `.photoslibrary`, `.xcodeproj` or `.rtfd`, in any case, or another named with an extension that macOS marks as a package, by its type or the Finder's bundle bit. The scan lists it in its `directories`, flagged `package`, and a pull writes no file inside one, counting it `outside`. macOS shows and opens a package as one thing, and its insides sent as files would reach the server piece by piece and be written back into it the same way. **A directory the walk cannot read**, one whose permissions refuse it say, or holding an entry whose details cannot be read, is listed in `directories` flagged `unreadable`, with the reason, and the scan goes on with every other. A file bound inside either is counted `unreached`, neither journaled nor sent, as a file the lists stopped taking is (25), and a pull keeps it bound, counting its item `outside` where it is in a package and `unwritten` where the directory cannot be written. A scan that stopped at one directory it could not read would send nothing from any other, and one that took its files as gone would trash their items. `device/folders.test.ts › does not walk into a package`, `› holds the files of a directory it cannot read, and goes on with the rest`, `› holds the files of a directory whose entries cannot be read`.
27. **Names are compared in NFC and without regard to case**, as macOS and Obsidian compare them: two paths, names or titles that differ only in case or Unicode form are one name. **Of two files whose paths are one name, one is taken**: the one bound at its path, else the first in path order, and every other is held, flagged `name` in the scan's `flagged`, neither sent nor journaled until one is renamed; only a volume that tells such names apart, which a Mac's default volume does not, can hold both. **A pull never gives two items one name**: the item placed there later goes beside the other (19), so on a disk that holds the two as one file neither is written over the other. **A path differing from its file's own only in case or form is that file's**: the file keeps its own name and a pull does not move it, and a rename changing only case or form is not sent, so two machines never rename one file back and forth. **Links, lines, embeds, placement and the lists compare names this one way**: a typed name matches a title or a file name in any case or form (11), an embed names a file so (12), a placement so (19), and the lists match a path so (25); a name the server is asked for is asked in both forms, since the server compares the text it is sent. 28. `.marfa/` inside the folder is the folder's own state — its settings file, its mapping, its journal, its queue — and is never pushed. **It is never watched, with one exception: the settings file, `.marfa/folder.yaml` (1)**, whose edit a watch sends at its next pass; nothing else under `.marfa/` is read as a file. `device/folders.test.ts › keeps its own state in .marfa and never pushes it`, `› sends an edit to its settings file through the folder door`.

## What a folder will not write

30. **A folder writes only inside itself.** Every component of the path is a plain name: no `..`, no separator leading out, and no symlink anywhere on the way. A path that fails this is reported and not written. A link pointing out of the folder loses the file, and one pointing back in is worse — the write lands on another item's file and truncates it — and the folder's own walk descends neither. The check reads the path and the write resolves it again, so this is a rule the folder keeps rather than one it enforces against something trying to break it. **It has one exception: a folder takes in a file another folder on the machine has let go** (44), which moves the file out of that folder. `device/folders.test.ts › refuses to write a file outside the folder`, `› takes in a file another folder let go`.
31. **A body link the file used to carry and no longer does takes its `references` edge with it**, unless a `references` line still names the same item (11). A file the person has changed since the folder wrote it stays, with its binding, and the pull reports it; one the pull cannot read stays too, counted `unwritten`, since its bytes are not shown to be the folder's own. ## A file whose row the copy has lost

38. **A file bound to a row the copy no longer holds is bound to nothing.** A refused create's reconcile forgets its row (`queue-and-verdicts.md` 12), and a row the server trashes or purges leaves the copy too. ## Keeping up with the server

40. **A folder takes in what the server recorded since its copy's cursor, without a hydration.** `folders push` catches up after its drain and before its pull, and `folders watch` holds the event stream open beside its passes, so another device's change reaches the copy and the pass after it writes the change out. A cursor the log has aged past is met with a fresh hydration (`device.md` 16). **A copy that cannot answer is hydrated first**, whether it never hydrated, its hydration was cut short or its cursor aged out (`device.md` 4): a push after one whose hydration failed hydrates and goes on, and a watch whose hydration met anything environmental, the network, a timeout (`408`), a rate limit (`429`) or any `5xx`, tries it again after a wait that doubles from a second to thirty, or the longer wait a rate limit's `Retry-After` names, held to 300 seconds. **A catch-up that fails for anything environmental does not stop a push's pull**, the same failures a watch tries again: the push reports the failure and writes out the copy it holds, and where the failure left a copy that cannot answer, it reports the pull as not run and the next push hydrates first. Any other failure fails the push, and ends the watch saying the server's changes stopped reaching the folder. A folder that only ever pushed and pulled would write out what it held at its last hydration for good, and one that stopped on a failed hydration would stay stopped. `device/folders.test.ts › takes another device's change at the next push, without a hydration`, `› takes another device's change while watching, without a hydration`, `› hydrates again at a push whose cursor the log has aged past`, `› hydrates again while watching when the log ages past its cursor`, `› keeps watching through a hydration that failed, and tries it again`, `› waits out a rate limit's Retry-After before hydrating again while watching`, `› ends the watch and says so when its hydration meets an answer no retry changes`, `› hydrates at the next push after one whose hydration failed`, `› pulls at a push that cannot reach the server, and says the catch-up failed`.

## Folders on one machine

41. **The folders on a machine are listed in one registry.** `folders add` lists the folder under its resolved directory, the `system.folder` it follows and its own store, and every pass lists it again where the registry lost it or the directory moved, a running watch's included. `folders list` reads the registry. `folders remove <dir>` takes the folder off it and removes the folder's own state under `.marfa/`, leaving its files as plain files; it is refused while the folder's queue holds a write not yet answered or one blocked, which would be lost with it; a folder whose directory is missing is only taken off the list. **A folder is refused inside another listed folder's directory, or around one**, and a walk passes over any directory holding its own `.marfa/`, whose files are that folder's, and a pull writes nothing there, counting it `outside`, and a file bound there before the directory became a folder is held, counted `unreached` and never journaled, as a file the lists stopped taking is (25): nested, one file would be two folders' at once. A directory is named resolved, so one reached through a symlink is one folder, and never another folder to itself. **An entry goes four ways only**: by `folders remove`; by the folder itself, listing its store under another directory, which takes the old entry's place; by a folder listing itself at the directory the entry names, which takes its place, as two spellings of one directory are one entry; and by any read that finds the directory readable and holding no folder, its `.marfa/` removed. **A directory missing or unreadable is kept**, since it cannot be told from one renamed, on a volume not mounted, or shut for now, and a missing file in any other folder is held meanwhile (43), the reason naming `folders remove` for a folder that is gone. The registry is a file of its own, never a folder's store: `folders.json` in the machine's application data, `~/Library/Application Support/Marfa` on a Mac, or else the file `MARFA_FOLDER_REGISTRY` names, **so two registries on one machine stand in for two machines**. It is written beside itself, synced and renamed over, under a lock. **A registry that cannot be read leaves each folder standing alone**, and every push says so, a watch once while it stands: a missing file is then held rather than trashed (43), and `folders add` writes the registry afresh where the file does not parse, with no folder listed to refuse it inside, and is refused where the file cannot be opened at all, the others listing themselves again at their next pass; no pass writes over it. **A registry gone that a folder was listed in** leaves that folder's pass unable to tell a move: it holds its missing files, says so, and lists itself again. Each folder also remembers the others it found, and looks in those still folders though the registry no longer lists them. Each folder is still an independent copy with its own queue (4); what the registry gives a folder is where the others are, and each other folder is read as it stands, its directory and its store, never waited on. A folder moved inside another is not refused at its next pass; the other's walk passes over it. A machine with no home to keep a registry in leaves its folders standing alone. **One process works a folder at a time**: a second process opening a folder another holds, a `folders watch` say, is refused `reading_handle` before it reads or writes a file, a binding, the settings file or the server, whatever the command, `folders remove` included; `folders status` reads the folder's store without holding it (48), and `folders list` reads only the registry, so both answer beside it. 43. **A missing file is not trashed if it moved on the machine.** Before trashing a missing file's item (21), the folder looks in the other registered folders' directories, walked as widely as the built-in lists allow and into every dot-led directory that folder includes (25), for the same file by device, inode and birth time, or else for a file carrying that id; for a file that cannot carry an id, it looks for one with the same bytes, which counts only where it is unbound in its folder or bound there to this item, and that folder binds no other item by those bytes. **Only both folders holding the item excludes a file**: where this folder's search and the other folder's both hold it, the other's file bound to it is its own, not this one moved (45); a file bound to the item in a folder whose search does not hold it is this one moved, whether it was renamed, copied, or saved again there. **If it finds one, the move is the same item and nothing is trashed**: the binding goes, and the scan counts it `moved_away`. **If it finds none, it trashes and reports**: the scan names the path in `trashed`, and the push or the watch says in words that no folder on the machine holds the file. **Where it cannot tell, it holds**, as a delete is held while offline: the registry cannot be read, or is gone this pass (41); a listed folder is missing or cannot be read, or part of one cannot; or several files elsewhere have the file's bytes. Nothing is trashed, the scan names the file in `unsure` with the reason, and it is looked for again at the next pass. It never waits on another folder's scan. ## Large removals, size and status

46. **A removal large enough to be a mistake waits to be confirmed**, whether made on the disk or arriving through a pull. Large is more than `removal_threshold.files` files and more than `removal_threshold.fraction` of the files the folder binds: 10 and a quarter unless the settings (1) say otherwise. **On the disk**, every file missing together is counted, not only those past the grace (21), so files a watch meets a pass apart are one removal: while the count passes the threshold no delete is sent, and the scan counts them `paused`. **Through a pull**, the files of items that left by state or were trashed elsewhere (35) are counted the same way: while they pass it, none is taken away, and the pull counts them `paused`. **`folders confirm`** lets a paused removal go: each file gone from the disk is looked for in the other folders on the machine first, as a missing file past its grace is (43), so one found there is counted `moved` and its item stays, one that cannot be told yet is left for the next pass, and only one found nowhere has its delete queued, sent at the next push; the files of items that left elsewhere are taken away. **`folders restore`** cancels it: a file gone from the disk is written back from the copy, unless its item has since left the search's states or is no longer held, which no pull writes a file for: that file is let go with its binding, neither written back nor deleted, and not counted put back, save a file a document here embeds (12), which the pull writes anew where its link says, uncounted; and an item that left elsewhere is restored from the bin or moved back to a state the search holds, sent at the next push. **Limit:** a file whose item the search no longer holds for any other reason (35) is not written back, since a pull writes no such file, and its removal goes as any other. The push, the watch and the status say a removal waits, and how to let it go or put it back; a watch says it once while it stands, not at every pass. A folder whose files a person moved away by mistake, or whose items another device trashed in bulk, would otherwise lose them all in one pass. `device/folders.test.ts › pauses a large removal made on disk`, `› says a paused removal once while watching`, `› follows the settings' removal threshold`, `› lets a paused removal go once confirmed, or puts it back`, `› lets a paused file whose item left by state go when the removal is put back, rather than journaling it again`, `› looks for a paused removal's files in the other folders before confirming it`, `› pauses a large removal from another device`.
47. **A text near the server's limit is warned of.** A document whose text, as it is sent, reaches nine tenths of the request limit, 1 MiB by default, is named with its size in the scan's `warnings`, flagged `size`, and in words by the push or watch whose scan sends it; the status (48) names it too, whenever it is read. A file past the limit is refused by the server `413 request_too_large`: an edit is held with that reason (9), and a new file's create is refused as 38 says. **Limit:** the device measures against the default limit, so on an instance configured with another, the warning comes early or late. `device/folders.test.ts › warns of a text near the limit`.
48. **Every file the walk reaches, and every bound file, has a status, read with `folders status`**, from the folder's own store and its disk, asking the server nothing and holding the store for nothing, so it answers beside a running watch and never keeps one from starting (41): `in_step`; `waiting`, with what waits (a scan, an upload, a create, an edit, a tag, a state, a restore, an edge, a placement, metadata or a delete); `held`, with the flag and reason the scan or the drain gave (unreadable, encoding, refused, behind, edges, a removal waiting to be confirmed, and the rest); `unmatched` (35); `unreached`, where the lists, a package or an unreadable directory keep the walk from it (25, 26); or `outside`, where the search holds no type the file would be. ## Reading only what changed

49. **A watch's notifications are hints, and a full pass catches what they miss.** A watch's scan does not read a file whose size, modification time, executable permission (50) and identity (17) are what they were when a scan last read it, whose binding is at its path, which nothing holds (9, 10), whose last save was not set aside (39) and whose item the copy still holds (38). The size and time are taken before the read, so a change made while the file is read is read again. A file carrying the id of a skipped file's item is read with it, so a copy is told from its original (15). **The first pass reads every file, and so does one pass a minute**, as do `folders push` and `folders scan`. Two things wait for a full pass: a change that leaves the size and time as they were, which an editor restoring the time can make; and a new file that only a skipped note embeds, which is sent with it there (12). Reading every file every second costs a large folder its disk for nothing. **Limit:** this is the scan's read alone; a pull still reads a bound file it compares with its item. `device/folders.test.ts › does not reread an unchanged file`, `› finds a missed change on its full pass` (by a push; the watch's own full pass is `watch.rs`'s unit test), `› tells a copy from its unread original on a quick pass`.

## A file's permission

50. **A file item keeps its file's executable permission as `executable` on `core.file`**, which every file type inherits. A file its owner may run is created with `executable: true`, and one it may not is created without the property. A change of the permission alone is an update carrying `executable`, as is one made with new bytes. A pull gives the file the permission its item holds: when it writes the file, adding execute wherever a read bit is set or taking all three away; and to a file already in place that a scan has read, unless the file changed since, which makes the permission the person's, sent at the next scan. A permission the filesystem refuses leaves the file as it is and the pull goes on. **A volume that keeps no permissions**, such as exFAT, where every file reads as one its owner may run, is found by a probe under `.marfa/` when the folder first reads or writes a permission: there the permission is neither read nor written, and no item's is changed. A script pushed from one machine and pulled on another that would not run there has lost part of what the file is. **On macOS, every file a pull writes from the server's bytes carries the `com.apple.quarantine` mark**, as a downloaded file does, set on the new file before it lands (20): every file item's file, executable or not, and never a document, which is text the folder renders. A file already in place that a pull makes runnable is marked first. A file that cannot be marked is not written, and counted `unwritten`; one in place is left as it is. `device/folders.test.ts › keeps a file's executable permission`, `› gives a pulled file the permission its item holds`, `› gives each file a pull writes from the server's bytes the quarantine mark on macOS`, which asserts the mark on macOS alone; `compliance/types.test.ts › declares executable on core.file, which every file type inherits`.

## A folder that never settles

51. **Changes that never settle hold a watch's pass off for five seconds at most.** A watch waits for the folder to go quiet before a pass, so an editor's save made in several steps is read whole; a file changing more often than that, a log written twice a second say, would otherwise hold off every pass for as long as it is written, and with them every other file's change and every change from the server. Once five seconds have gone by since the last pass ended, the next change, on the disk or from the server, runs a pass whether or not the folder has settled, and that pass sends what changed on the disk and writes what came from the server. A document still changing is read as it stands, and read again by a later pass. **A watch reads a file that is not a document only once it has stopped changing**: one whose bytes or details changed within the watch's settle window, a quarter of a second, a picture still being copied in or a download still arriving say, is not read by that pass, and the first pass after it settles reads it. A file whose read waits still claims its identity: a rename moves its binding and placement without reading its bytes, and a replacement at the old path becomes a new item. Read as it stood, each pass would upload another part of it. **A file that never stops changing**, one written more often than the settle window for as long as the watch runs, a capture or a log kept as bytes say, is never sent by a watch: the watch names it, once while it lasts, as still changing and not sent. `folders push` and `folders scan` read every file as it stands, one still being written included, since a person runs them when they choose. `device/folders.test.ts › keeps syncing both ways while a file changes twice a second`, `› sends a file being copied in only once it stops changing, while every other file goes on`, `› says once that a file which never stops changing has not been sent`, `› keeps the item of a renamed file that is still settling (replacement %s)`.

## A folder that cannot reach the server

52. **A watch says when it cannot reach the server, once, and once when it can again.** Its pass line counts the writes the server answered and, apart from them, the writes still waiting, so a write that went nowhere never reads as sent (`queue-and-verdicts.md` 6); a pass whose drain cannot reach the server, or a stream the watch cannot have (`device.md` 40), says so in one line naming the server and why, and nothing more while it stays so, and the first pass or stream to reach it again says so in one line, and sends what waited. A hydration the watch has to try again while the server is away (40) says so once for each run of failures, not at every attempt. A push says the same of its drain. **Why a drain stopped is said too**, by a push every time and by a watch once each time it changes, so a pass that sent nothing never reads as one with nothing to send. **A refused credential stops a watch with exit 5**, the exit a one-off command gives it, saying that the writes wait until a working credential is kept: nothing it sends can land until a person replaces the key, and a watch left running on one would print the same line for days. The refusal is the server's own, naming its contract: a `401` naming none is from something in front of the server (`device.md` 42), and the watch waits it out as it waits out an unreachable server. A watch that repeated its line every pass while nothing went would read as working to the person who left it running. `device/folders.test.ts › says once that a watch cannot reach the server, and once that it can again`, `› stops a watch whose credential is refused, with the credential's exit`, `› keeps watching through a hydration that failed, and tries it again`, `› waits out a gateway refusing its key, naming no contract, without stopping`, `› says why a push's drain stopped`.
