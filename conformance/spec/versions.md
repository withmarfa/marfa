# Versions

Every item carries a `version` that starts at 1 and moves with each write to its fields, and the server keeps snapshots of earlier properties for three-way merges.

## Versioning

1. A created item has `version: 1`. `correctness/item-versioning.test.ts › version starts at 1 on creation`, `correctness/persistence.test.ts › item is retrievable by ID after creation`.
2. An update advances the version by one and the response carries the new version. `correctness/item-versioning.test.ts › version increments on update`.
3. Every update writes a snapshot of the properties before it; `GET /items/{id}/versions` lists snapshots with `item_id`, `version` and `properties`, oldest first, and an item never updated has none. Each snapshot also carries the `type`, `tier`, `occurred_at` and `source_id` the row had at that version (20). `correctness/item-versioning.test.ts › updating an item creates a version snapshot`, `› multiple updates create multiple versions`, `› version history for item with no updates is empty`, `› versions have correct item_id reference`.
4. Every update writes a snapshot and no flag asks for one: `force_snapshot` is a key the door does not declare, refused like any other (`items/update-undeclared-key`). `correctness/item-versioning.test.ts › multiple updates create multiple versions`, `› refuses a body key the update door does not declare`.
5. An unknown item's history answers `404 item_not_found`; a malformed id answers `400 invalid_id`. `correctness/item-versioning.test.ts › answers 404 for an unknown item's history and 400 for a malformed id`.

## Concurrency

Statements 6 to 9 and 11 are about the update door, which requires the version. Statement 10 is the create door, which does not: a create has no version to have read, and one sent there is a precondition on the single path that overwrites.

6. A `PATCH /items/{id}` with no `version` is refused `400 missing_required_field`. An update names the version it is based on, or it is a blind overwrite of whatever arrived since, which the contract does not offer. `correctness/item-versioning.test.ts › an update naming no version is refused`.
7. A `PATCH` naming the current version succeeds and advances it. `correctness/item-versioning.test.ts › a stale write answers version_conflict with a three-way envelope` (the first write), `compliance/error-codes.test.ts › rejects a stale write whose base version is retained` (the first write).
8. A `PATCH` naming a retained earlier version whose changes collide with changes made since answers `409 version_conflict` with `current`, `ancestor`, `conflicting_fields` in ascending order, and the type's resolved `merge_policy`; `ancestor.version` is the version the caller named, and `current` and `ancestor` each carry the row's `id` and the `type` it had at that version, so a collision on `type` shows both sides of the move. **The check covers the whole row, not only its properties**: `tier`, `occurred_at` and `source_id` are compared against the version the caller named exactly as a property is, and a collision on one of them names it in `conflicting_fields` beside any property. A field the write does not carry is not a change and cannot collide; a value equal to the one at the named version is an echo and is not one either, so it is neither refused nor written back. `correctness/item-versioning.test.ts › a stale write answers version_conflict with a three-way envelope`, `› refuses a stale write that collides on tier, occurred_at or source_id`, `compliance/error-codes.test.ts › rejects a stale write whose base version is retained`, `correctness/merge-policy.test.ts › keep-both and LWW arrive in one 409, and the resolution reads back`.
9. A `PATCH` naming a version for which no snapshot exists, including 0 and a number never issued, or whose snapshot is of a type the credential may not read (21), answers `409 ancestor_unavailable` with `current`, the row's `id` included, and `requested_version` and no ancestor, and is never merged automatically. `correctness/item-versioning.test.ts › a version no client ever read answers ancestor_unavailable`, `compliance/error-codes.test.ts › rejects an update naming a version that never existed`.
10. A `POST /items` whose `(source, source_id)` resolves a live row may carry a `version`, and then that upsert is conditional and answers the update door's envelopes: `409 version_conflict` for a stale value, `409 ancestor_unavailable` for one no snapshot covers. Without a `version` the upsert stays unconditional, because a caller creating a row it has never read has no version to name. **Either envelope names the row the natural key resolved in `current.id`**, which is the one way the caller learns it: the request named a key and not an id, and neither envelope reaches a key that may not write that row, which is refused before it without the row named (`items/natural-key-unreadable`), and a device refused here has to know which row refused it before it can hold that row rather than a second copy of it (`queue-and-verdicts.md` 39). A repeated `id`, and a natural key resolving a trashed row, are acknowledged rather than written, so neither has a precondition to fail. `sync/idempotency.test.ts › a create naming a stale version on an existing row is refused`, `› takes a create's version of zero as the claim that there is no row`.
11. A stale write whose changed fields do not collide with the fields changed since is merged: only the caller's genuine changes are applied over the current row, `tier`, `occurred_at` and `source_id` included. **Under `properties_mode: replace` the body is the whole of the caller's properties**, so a field the ancestor had and the body lacks is a change the caller made: the merge clears it, and it collides with a change the other writer made to that field since, which answers `409 version_conflict` naming it. A merged write is told from a clean one by its version, more than one step past the one the caller named. A stale write naming `retype: true` moves the row to the named type as one at the current version does where nothing collides, with or without `properties`, and its merged properties are held to that type: a field the body echoes at the ancestor's value is not applied, so where the other writer removed it since and the type entered requires it, the write is refused `400 invalid_properties` naming the field and nothing moves. A move onto a row another writer has moved since the version the caller read collides on `type`, named in `conflicting_fields` beside any other collision, whatever the write carries and whatever `conflict` asks: landing it would undo a move the caller never saw. The verdict on a stale write is taken on its merged result and nothing else: a field the other writer added since, which the caller's body does not name and the ancestor never had, is kept and satisfies the type, where the same body laid over the current row would not. A clear both writers made is an echo, and a key named like a member every object inherits is judged by what the row holds. The row is held to its type only where the write carries properties or a move, stale or not: a type may gain a required field while rows that lack it stand, and a stale write of `tier`, `occurred_at` or `source_id` alone merges as it would have before the field was required. `correctness/merge-policy.test.ts › non-conflicting writes from two clients both apply (different fields)`, `correctness/item-versioning.test.ts › merges a stale write on an item field nobody else changed`, `› clears a field a stale replace leaves out, where nobody changed it since`, `› refuses a stale replace that leaves out a field the other writer changed since`, `› moves the type on a stale write as on a current one`, `› refuses a stale move whose merged properties fall short of the type entered`, `› holds a stale write to the type only where it carries properties or a move`, `› moves the type with retype alone at a stale version`, `› refuses a stale move onto a row another writer moved since, naming type`, `› judges a stale write by its merged result, not by the body laid over the current row`, `› takes a clear both writers made as an echo`, `› clears a field named like a prototype member as any other`.

## Merge policy

12. `GET /types/{id}` returns the type's resolved `merge_policy`, inheritance already walked: `fields` naming per-field strategies and a `default`. For `core.note`, `body` and `notes` are `keep_both_copies` and everything else falls to `last_writer_wins`. `compliance/types.test.ts › GET /types/core.note returns the artifact-declared merge_policy`, `correctness/item-versioning.test.ts › a stale write answers version_conflict with a three-way envelope`.
13. A colliding write sent with `?conflict=auto` is resolved by the server in one transaction: a `last_writer_wins` field takes the later writer; a `keep_both_copies` field keeps the server's value on the original and writes the losing value to a sibling item of the same type tagged `conflicted-copy`, carrying the original row's `source` rather than the losing writer's: an update names no source, so there is no writer's source to carry, and the sibling is a copy of the row rather than a record of who lost. **The sibling carries the original's tags beside `conflicted-copy`, and a copy of the edges that are the original's own**: those its own file would write (`edges.md` 2), an outbound edge of a type written at its source and an inbound one of a type written at its target, each announced `edge.created` after the sibling's `item.created`. Its place under its parent and what it is about come with it; a track that names its album does not make the copy its album. Of those, only what a second holder may take: the type's cardinality allows it (not the original's children, each of which has one parent, and not a `supersedes`), the writer could have made it, judged as `POST /edges` judges it, with write on the source's type and on the edge type and read on the target's (`edges.md` 21, 24), and the other end is not in the bin; and discarding the copy, the ordinary thing done with one, neither reaches what the original points at nor is held back by it, so no outbound edge of a type that cascades and no edge of a type that blocks. A copy with no edges and no tags sits outside every project, tag and view the original was in, which is where nobody looks for it. Beside those, the copy is linked to the original by a `derived-from` edge of its own (22), and takes none of the original's outbound `derived-from` edges (24). `sync/conflict.test.ts › gives the conflicted copy the original's tags and every edge a second copy may hold`, `› gives the conflicted copy no edge its writer could not have made, and none to a row in the bin`, `› gives the conflicted copy only the edges the original's own file writes, none that cascade or block`, `compliance/events-contract.test.ts › announces edge.created for an edge a conflicted copy is given`. A colliding `tier`, `occurred_at` or `source_id` takes the later writer and the resolution reports `last_writer_wins` for it: they are the row's own fields rather than properties, so the type declares no strategy for one and `keep_both_copies` has nothing to mean, a sibling being a copy of the properties. An echoed one is not a change and is left where the other writer put it. A field a `replace` cleared that collides is resolved the same way: `last_writer_wins` clears it, and `keep_both_copies` keeps the server's value on the row and leaves the field off the sibling. A colliding write that also moves the type is not resolved, whatever `conflict` asks: the policy is the type being left's, and a copy the resolution wrote would belong to neither type, so it answers `409 version_conflict` and moves nothing. The sibling carries neither the row's natural key nor its link (`items/link-keep-both` and `items/link-keep-both-required`), so where the row's type requires its `link_field`, itself or through a parent, a colliding write that would write one is not resolved either, and answers `409 version_conflict`, moving nothing: the copy could not be a row of the type (`compliance/links.test.ts › leaves the link off a keep-both copy of a row`, `› does not resolve into a copy where the type requires its link`). `sync/conflict.test.ts › keeps both copies in one write where the type says to`, `› resolves a colliding item field to the later writer, and leaves an echoed one alone`, `› resolves a field a stale replace cleared by the policy: cleared under last-writer-wins, kept and left off the copy under keep-both`, `› refuses to resolve a colliding write that also moves the type`, `› applies a clear nobody collided with under conflict=auto, and resolves nothing`.
14. The same stale write without `?conflict=auto` is refused `409 version_conflict`. `sync/conflict.test.ts › keeps both copies in one write where the type says to` (the control before the resolved write).
15. The resolution the suite performs client-side from the envelope lands the same way: keep-both fields spawn a `conflicted-copy` sibling, written by one `POST /items` that carries its `derived-from` edge to the original (22), and last-writer-wins fields take the later writer, per field, through the policy default and through a child type's override. `correctness/merge-policy.test.ts`.

## Edges

16. An edge is created at `version: 1`; an edge `PATCH` naming a stale version is refused, one naming the current version is accepted, and one naming no version is refused `400 missing_required_field` exactly as an item's is. `correctness/edges/edges-crud.test.ts`, `sync/edge-version.test.ts › refuses an update naming a stale version and accepts the current one`, `› refuses an update naming no version`.
17. A `PATCH` naming a stale version and carrying nothing to merge — edges and a version, and none of `properties`, `tier`, `occurred_at` or `source_id` — answers `409 version_conflict` with `current`, the row's `id` included, and no `ancestor`, `conflicting_fields` or `merge_policy`. There is no ancestor to compare against and no field that could have collided, and offering either would name a resolution that cannot be performed. A stale edge `PATCH` (16) carries the same shape, with `current` the whole edge. `correctness/item-versioning.test.ts › answers an edges-only stale write with the envelope minus its merge half`, `correctness/edges/edges-crud.test.ts › refuses a stale edge update, under current and not under edge`.

## Version zero

18. **The server never mints version 0.** A created row is at 1 (1), and every write moves the number up, so no version the server has ever issued is zero and no snapshot is ever recorded under it. That is what makes zero usable as a claim rather than as a reading: a create carrying `version: 0` says the caller read no row under the natural key it names, and is a precondition that there is none. On an empty natural key it creates, and the row it makes is at 1. On one that already names a row it is a version no snapshot covers, so it answers `409 ancestor_unavailable` like any other (9). `sync/idempotency.test.ts › takes a create's version of zero as the claim that there is no row`.

## State

19. **A change of state moves neither the version nor its history.** The version counts writes to the item's own fields, its properties, `type`, `tier`, `occurred_at` and `source_id`, and `state` is not among them: `POST /items/{id}/transition`, `DELETE /items/{id}`, `POST /items/{id}/restore` and a `transition` run by `POST /items/bulk-actions` each answer and leave the row at the version it had, and none of them adds to `GET /items/{id}/versions`. A version is the content a write is based on and a snapshot is the content an update left behind, so a version that moved on a state change would make an edit queued against the content it read stale for no change to that content, and a snapshot recorded at a version that does not move would be a second row under a number the next update records again. A client watching for change watches `state` and `updated_at` as well as the version, or the event stream, which announces every state change (`events.md` 7). The purge precondition reads the version on the same terms (`items/purge-version`), and so does a device catching up (`device.md` 13). `correctness/item-versioning.test.ts › moves neither the version nor its history on a transition, a delete or a restore`.

## Reach

20. **A snapshot is read under the type it was written under.** Each snapshot `GET /items/{id}/versions` answers names the `type` the row had at that version beside its `tier`, `occurred_at` and `source_id`, and the door answers only the snapshots of types the credential may read: a row moved from a type the credential may not read into one it may keeps the snapshots it left behind, and they are left out rather than refused, because they hold the old type's properties. The door still asks read on the row's type now (`404 item_not_found` without it). It pages by cursor, oldest first: `limit` (1 to 200, default 50) and `cursor` from the last page's `next_cursor`, a page filled past the snapshots left out, and `next_cursor: null` on the last; a cursor that is malformed or was issued by another listing, and a parameter the door does not declare, answer `400 validation_error`. `GET /items/{id}?include=versions` carries the first page as `versions`, which the listing continues. `compliance/version-reach.test.ts › names the type each snapshot was written under`, `› leaves out of the history the snapshots of a type the key may not read`, `› leaves them out of the history the item read carries`, `› pages the history and fills a page past what the key may not read`.
21. **A stale write is held to the same reach.** A write naming a version is merged against that version's snapshot and may be answered with it as `ancestor`, so a snapshot of a type the credential may not read answers `409 ancestor_unavailable`, as one thinned away does (9), and is never merged: on `PATCH /items/{id}`, on a conditional `POST /items` (10) and on a `POST /items/bulk` entry, where it is the entry's code. A credential reading the type is answered the ordinary `version_conflict` envelope, its `ancestor` naming that type. `compliance/version-reach.test.ts › answers a stale update naming an unreadable snapshot ancestor_unavailable`, `› does not merge a stale update against a snapshot the key may not read`, `› answers a conditional create naming an unreadable snapshot ancestor_unavailable`, `› answers a bulk entry naming an unreadable snapshot ancestor_unavailable`.

## A conflicted copy and its original

Statements 22 to 29 hold for every conflicted copy the server writes (13). `PATCH /items/{id}?conflict=auto` is the one door that writes one: `POST /items` and `POST /items/bulk` take no `conflict` mode.

22. WHEN the server writes a conflicted copy, the server MUST write, in the same transaction, one `derived-from` edge whose source is the copy and whose target is the original, with no properties and at `version: 1`.
    **Reason:** the verdict and the answer name the copy once (`queue-and-verdicts.md` 11), and nothing else joins the two rows: without the edge, an app that reads the copy later, on this device after a restart or on another device, cannot show it beside its original, and an app that reads the original cannot find the copies made from it. `derived-from` is the shipped edge type for a row made from another (`edges.md` 2), many-to-many, written at its source, and it orphans the other end on delete, so the copy's file writes it and discarding either row leaves the other.
    **Tests:** `sync/conflict.test.ts › links the conflicted copy to its original with one derived-from edge, whatever edge grants the writer holds`, `correctness/merge-policy.test.ts`.

23. WHEN the server writes a conflicted copy, the server MUST write the edge of 22 whatever edge grants the writer holds.
    **Reason:** the edge is part of the server's own resolution, as a cascade is part of a delete, and a link that came and went with the writer's grants would leave some copies unlinked for good. It discloses nothing the writer cannot read: the answer names only the copy, and the edge doors and the stream hold the edge to read on `derived-from` and on the copy's type, which is the original's (`edges.md` 22, 23).
    **Tests:** `sync/conflict.test.ts › links the conflicted copy to its original with one derived-from edge, whatever edge grants the writer holds`.

24. WHEN the server writes a conflicted copy, the server MUST NOT copy onto it an outbound `derived-from` edge of the original.
    **Reason:** the copy is made from the original, which keeps its own provenance, so a reader follows the copy's one `derived-from` edge to its original without having to tell that edge from the original's own.
    **Tests:** `sync/conflict.test.ts › gives the conflicted copy none of the original's own derived-from edges, though its writer could have made them`, `› links the conflicted copy to its original with one derived-from edge, whatever edge grants the writer holds`.

25. WHEN the server writes a conflicted copy, the server MUST announce the edge of 22 as `edge.created` after the copy's `item.created` and before the original's `item.updated`.
    **Reason:** a subscriber applies the copy before an edge that names it as source, and meets the copy and its link before the original's update, so it never holds the original past the losing edit with nothing that leads to that edit.
    **Tests:** `compliance/events-contract.test.ts › announces a conflicted copy's link to its original between the copy's create and the original's update`. The server's own suite asserts the order in the log (`packages/server/src/routes/conflict-sibling-reaches-the-log.test.ts`).

26. WHEN the server executes again, under the same `Idempotency-Key`, a write that wrote a conflicted copy, the server MUST NOT write a second copy or a second edge of 22.
    **Reason:** a retry is the same edit, and a second copy or a second link would show the person a conflict they had once as two.
    **Tests:** `sync/conflict.test.ts › links the conflicted copy to its original with one derived-from edge, whatever edge grants the writer holds`. The server's own suite asserts it for an execution the replay cache does not answer (`packages/server/src/routes/conflict-sibling-reaches-the-log.test.ts`).

27. WHEN the original of a conflicted copy is trashed, the server MUST keep the edge of 22.
    **Reason:** a trash keeps every edge of the row it trashes, so a restore brings the original back beside its copy.
    **Tests:** `sync/conflict.test.ts › keeps the link while the original is in the bin, and a purge of the original takes the link and leaves the copy`.

28. WHEN the original of a conflicted copy is purged, the server MUST remove the edge of 22, announced as `edge.deleted` carrying `purged_with` (`edges.md` 17).
    **Reason:** the edge has no row to point at once the original is gone.
    **Tests:** `sync/conflict.test.ts › keeps the link while the original is in the bin, and a purge of the original takes the link and leaves the copy`.

29. WHEN the original of a conflicted copy is purged, the server MUST leave the copy as it was.
    **Reason:** the copy holds the text the person lost, which a purge of the original does not decide about; `derived-from` orphans the other end on delete (`edges.md` 16).
    **Tests:** `sync/conflict.test.ts › keeps the link while the original is in the bin, and a purge of the original takes the link and leaves the copy`.
