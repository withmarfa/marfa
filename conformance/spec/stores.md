# Stores

Where a blob's bytes live, and the rules that keep them. A store is a place bytes live: the disk every upload lands on, and an object store attached beside it when one is configured. The referee boots its server with both, so every statement about the object store is asserted against one rather than left to a deployment nobody runs.

## The stores and the log

1. An instance keeps bytes in a disk store and, when one is configured, an object store. `GET /blobs/stores` lists them to the operator key, each with an `id`, a `kind` of `disk` or `s3`, a `locator` a person can read (for an object store, `s3://<bucket>/<prefix>` and nothing else, so no credential can be in it), a `policy`, and `attached_at`; a working key is refused `403 forbidden`. `compliance/blob-stores.test.ts › lists the disk store and the object store to the operator key`, `› refuses the listing to a working key`.
2. Every store's policy is `all`, the one policy this build defines: the store wants every blob. The set is open, and the presets a store that wants less will need are named by the first such store. `compliance/blob-stores.test.ts › lists the disk store and the object store to the operator key`.
3. The location log records which stores hold which blob. `GET /blobs/{hash}/locations` answers it for one blob, to a credential that may read the blob (`blobs.md` 15): each row names a store, whether it is `detached`, when the copy was `recorded_at` and when a check last found it present and intact (`verified_at`, `null` until one has). A new upload's one location is the disk store, unverified. `compliance/blob-stores.test.ts › records a new blob's location as the disk store`.
4. The locations of an unknown hash answer `404 blob_not_found`, of a malformed one `400 validation_error`. `compliance/blob-stores.test.ts › answers 404 for the locations of an unknown hash and 400 for a malformed one`.

A store's id is its own: it is read from a marker the store holds, not from the configuration that named it, so a fresh folder or bucket is a fresh store with no copies claimed. A store the configuration no longer names stays listed with `detached_at` set, and its copies stop counting. Neither is observable over HTTP against a server the referee booted once, so neither is a statement here; the server's own suite proves both, in `packages/server/src/storage/blob-store.test.ts` and `blob-layer.test.ts`.

## The rules that keep the bytes

5. Every attached store holds every blob, because every store's policy is `all`, and the `blob-replicate` background job is what makes that true: a run copies blobs a store lacks from a store that has them, records each copy only after the receiving store has verified the bytes hash to their name, and answers `{copied, bytes, remaining}`; a run is bounded by count and by bytes, replication is woken again after a run that copied some of a backlog it could not finish, and every upload wakes it. After it has run to `remaining: 0`, a new upload's locations name the disk store and the object store, each with its own `recorded_at`. `compliance/blob-rules.test.ts › replicates every blob to the object store and records the copies, and the link becomes the store's own`.
6. A link to a blob's bytes never passes them through a relay. `GET /blobs/{hash}/url` answers a link the instance serves until the object store holds the blob, and that store's own signed link once it does: a URL whose host is the store's rather than the instance's, which fetches the bytes byte-identical with no credential (`blobs.md` 11). `compliance/blob-rules.test.ts › replicates every blob to the object store and records the copies, and the link becomes the store's own`.
7. A blob keeps at least `min_copies` live copies, the instance's `MARFA_BLOB_MIN_COPIES` (`1` unless set), which `GET /blobs/stores` reports beside the stores. `DELETE /blobs/{hash}/locations/{store}` (operator key) drops one store's copy and its row in the log only when at least that many would remain; otherwise it answers `409 copies_below_minimum` and the copy stays. A store that holds no copy of the blob, or that is not attached, answers `404 blob_location_not_found`; a working key is refused `403 forbidden`. `compliance/blob-rules.test.ts › drops a copy while the minimum holds and refuses the drop that would break it`.
8. The `blob-integrity` background job checks the copies the log claims, store by store, least recently checked first, bounded by rows and by bytes: a disk copy is re-hashed, an object-store copy is asked for by name and size. A copy found present and intact gets `verified_at`; one found missing or altered is struck from the log, with an error line and an audit row, and replication puts it back from another store. `compliance/blob-rules.test.ts › stamps a good copy and strikes a corrupt one, which replication then restores`.
9. The `blob-orphans` background job reports before it deletes. A run computes the blobs nothing references (an item in any lifecycle state, a metadata extension, an edge's properties, a version snapshot and a nonterminal property-update job's patch are references; what counts as one is statement 10), records each with the time a run first said so, forgets any that is referenced again, and purges only what an earlier run reported longer ago than `MARFA_BLOB_CLEANUP_GRACE_MS` (a report exactly that old waits for the next run): from the registry and the log first, then from every attached store, so a purge cut short leaves no row naming bytes that are gone and the next run deletes what it left (`blobs.md` 26). `GET /blobs/orphans` (operator key) is the report, each row a `hash`, `mime_type`, `size_bytes` and `reported_at`; a working key is refused `403 forbidden`. The referee boots its server with the grace at zero, so the run after a report purges. `compliance/blob-rules.test.ts › reports an unreferenced blob on one run and purges it on the next, never one an item names`.
10. **A digest anywhere in a string is a reference.** An item in any lifecycle state, a metadata extension, an edge's properties, a version snapshot or a queued or in-progress `update_properties` job's patch references a blob when any string in it holds the blob's digest: any run of exactly 64 lowercase hex characters with no further lowercase hex character on either side counts as a reference to `sha256:` and that run, whatever else stands beside it. So a whole value, a `sha256:` link inside text such as a Markdown body, an escaped or URL-encoded one (`sha256%3A…`), and the bare hex `GET /blobs/{hash}` also serves are all references, and a run of 63 or 65 is not one. A job's patch counts recursively by this same rule; its filter, tags and other action inputs do not count. Enqueueing such a job lifts existing reports in the transaction that stores it. A stale walk cannot start or keep a report for a blob a current job holds, and the final purge transaction checks current job state again. A canceled, failed or completed job retains no input, so bytes nothing else references are reported afresh after the job ends before a later run may purge them. Retention grants no blob-read reach (`blobs.md` 15), and an unknown digest is still accepted without lending. `packages/server/src/routes/bulk-action-blob-retention.test.ts` covers queued bytes through completion, terminal release, reopen and recovery, canonical digest forms and enqueue ordering; `packages/server/src/storage/sqlite/bulk-blob-inputs.test.ts` covers the bounded scan, atomic enqueue and current transactional checks. A note that links an image in its body keeps the image's bytes after the file item that named it is trashed and purged and the `blob-orphans` job has run twice, while an image no item names any more is purged by the same runs, and a blob named only in an edge's properties, as a whole value or inside text, is kept by them too while one nothing names is purged. `compliance/blob-rules.test.ts › keeps a blob a note links in its body after the file item naming it is purged`, `› keeps a blob named only in an edge's properties`.

The three background jobs run on their own cadences (`MARFA_BLOB_REPLICATE_INTERVAL_MS`, `MARFA_BLOB_INTEGRITY_INTERVAL_MS`, `MARFA_BLOB_CLEANUP_INTERVAL_MS`) and the fixtures drive them through `POST /background-jobs/{name}/run` (`background-jobs.md` 3), which is why each rule is a statement about a run rather than about a clock. The bounds a run keeps to (`MARFA_BLOB_REPLICATE_BATCH`, `MARFA_BLOB_REPLICATE_BATCH_BYTES`, `MARFA_BLOB_INTEGRITY_BATCH`, `MARFA_BLOB_INTEGRITY_BATCH_BYTES`) are not observable against a server the referee booted once; the server's own suite proves them (`packages/server/src/background-jobs/blob-replicate.test.ts`, `blob-integrity.test.ts`).

When a committed per-copy deletion cannot remove its external bytes, the server MUST retain the cleanup intent. While cleanup intents remain, bounded cleanup runs MUST advance past each attempted intent in a durable retry order, including after restart. New intents MUST join the tail of that order.

Reason: one failing store deletion must not prevent later healthy cleanup or lose the failed copy's ownership record. Native `packages/server/src/background-jobs/blob-copy-cleanup.test.ts` exercises bounded cleanup with a persistent disk failure, a later healthy copy, new arrivals and reopened storage; `external-audit.test.ts` exercises drop, strike, replacement and purge ownership.
