# Read views

A working copy needs proof that its inventory, direct reads and event stream belong to the same authorized view. Ordinary reads and write receipts do not provide that proof.

## Copy stream and proof grammar

1. **A copy stream is exactly `GET /events?edges=all&copy=1`.** Bootstrap omits both resume headers. Resume sends exactly one `Last-Event-ID` and one `X-Marfa-Read-View`. Its cursor is `0` or a decimal string beginning with a nonzero digit, at most `9223372036854775807`; its read view is exactly 64 lowercase hexadecimal characters. Other or duplicate query keys, a type filter, missing or alternate edge mode, another copy value, empty or malformed proof headers, duplicate proof headers and unpaired resume headers answer `400 validation_error` before a stream starts. A read-view header on an ordinary stream is refused the same way. Ordinary stream grammar remains as stated in `events.md` 3 and 4. `compliance/read-views.test.ts › rejects every alternate copy grammar before starting a stream`.
2. **Bootstrap announces one coherent instance, log head and read view before a client reads pages.** Both no-id markers have exactly `{event_type,cursor,instance_id,read_view}`, all strings, and the body `event_type` matches the SSE event name, `stream_cursor` or `stream_live`. The instance is the existing nonempty root `instance_id`, compared exactly. The live marker follows completed replay and held delivery; its cursor is at least the announced head, resume cursor and every event ID it delivered. Resume retains the expected instance and read view. No known head means no tuple or live certificate: the bounded opening ends incomplete rather than inventing a head. `compliance/read-views.test.ts › bootstraps and resumes with one instance, cursor and opaque read view`. Opening failures and delivery races require the server's controlled route fixtures because public HTTP cannot delay an internal head read or final snapshot at a chosen instruction.
3. **The read view is an opaque HMAC-SHA256 certificate**, using a purpose key derived from the instance's existing authentication secret. Its canonical input binds the instance, effective read projection and durable structural generation. It carries no policy plaintext, bearer-token ID or new session ledger. Ordinary content, metadata, tier, state and write-only authority changes do not change it. A successful retype, source move of an edge, type or edge-type topology change, or silent removal changes the structural generation in the transaction that commits it. A read projection change changes the certificate even when no event is published. `compliance/read-views.test.ts › keeps the read view across content, metadata and write-only authority changes`, `› refuses stale HTTP and resume proofs before resource lookup after retype or read narrowing`. The storage fixtures hold generation settlement and snapshot coherence at controlled transaction barriers; certificate equality over HTTP alone does not establish that internal implementation.

## Conditional reads

4. **Conditional copy reads send one `X-Marfa-Read-View` request header.** Supported doors are GET `/items`, `/items/{id}`, `/items/{id}/edges`, `/edges`, `/edges/{id}`, `/types`, `/edge-types` and `/keys/current`. Existing query grammar still applies, and conditional item pages require `include=metadata` or a comma list containing metadata. An unsupported conditional GET, malformed or duplicate header, or metadata-free conditional item page answers `400 validation_error`. Missing header selects ordinary mode with no copy certificate. `compliance/read-views.test.ts › walks conditional metadata pages to explicit null and certifies every supported read door`, `› rejects unsupported conditional doors, malformed proofs and metadata-free item pages`.
5. **Each conditional result is a fresh coherent read.** Authority, configuration, durable generation, topology, rows and projected metadata or edges are read in one short snapshot, and compared before an empty-type or resource refusal. A matching 2xx or snapshot-attributed resource 403/404 carries exactly the matching response `X-Marfa-Read-View` and `Cache-Control: no-store`, after the snapshot closes successfully. It carries no body certificate or additional instance header. Generic validation, authentication, server failures and mismatches carry no certificate. Existing contract, error and request headers remain. A certified resource 404 means that this view did not return the resource; it does not prove global nonexistence. `compliance/read-views.test.ts › certifies matching resource absence without certifying generic validation or authentication failures`, `› refuses stale HTTP and resume proofs before resource lookup after retype or read narrowing`.
6. **Metadata item pages carry `{data:[{item,metadata,listed:true}],next_cursor:string|null}`.** Every page has an explicit `next_cursor`; a bounded walk ends only at explicit null, and a matching certificate on one page does not certify absence across pages on its own. Direct item envelopes retain their existing extras and add a required boolean `listed`; each requested neighbor also carries it. The boolean classifies the effective item-set source filter before a device's local type or tier slicing. A directly authorized item excluded from the source-filtered inventory remains readable by ID and has `listed:false`. Edge envelopes do not acquire `listed`. `compliance/read-views.test.ts › walks conditional metadata pages to explicit null and certifies every supported read door`, `› classifies source-excluded direct items and neighbors without admitting them to a listed page`.
7. **A write receipt is never a read certificate.** Item, edge and folder write receipts retain their existing shapes without a response or body certificate. A device settles the original receipt and obtains a fresh conditional read before adopting the resulting baseline, even if its local generation did not change. The read-view header is neither a mutation precondition nor a write fingerprint. `POST /items/bulk-get` remains its existing parallel item and metadata arrays; it is not a conditional copy inventory door. `compliance/read-views.test.ts › returns item, edge and folder write receipts without a read-view certificate`.

## Change and termination

An approved app can read copy content while `/keys/current` refuses its bearer kind. That matching, snapshot-attributed `403 forbidden` carries the conditional certificate; the same ordinary refusal carries none. `compliance/read-views.test.ts › certifies an approved app's current-key refusal under its matching read view`.

8. **A mismatch before a conditional HTTP response or copy stream starts answers `409 read_view_changed`.** Its body is exactly `{"error":{"code":"read_view_changed","message":"The read view changed. Rebuild the working copy."}}`, with no policy or resource details and no certificate. It takes precedence over the empty-read-reach or resource 403/404 the changed view would otherwise answer. `compliance/read-views.test.ts › refuses stale HTTP and resume proofs before resource lookup after retype or read narrowing`.
9. **After a copy stream starts, a changed view sends one no-id `event: read_view_changed`, with exactly `{"event_type":"read_view_changed"}`, then closes.** It reveals no cursor, new certificate, instance or resource detail, and sends no later frame or live certificate. Stream setup, each replay or live decision, held classification and release, final live marker and heartbeat compare the same view within a fresh short snapshot; no SQL transaction spans a network wait. Every item or metadata copy frame also carries required boolean `listed`, including delete, restore and metadata changes. Source-excluded but directly authorized carriers still arrive with `listed:false`, so an existing pin can process them. Edge frame shapes remain unchanged. `compliance/read-views.test.ts › ends an open copy stream with a no-id detail-free terminal after a structural change`, `› delivers source-excluded update, metadata, delete and restore carriers with listed false`. Quiet-heartbeat and chosen replay/hold/finalization races require controlled server fixtures.

The device's materialization and expiry obligations are stated in `device.md`; a matching HTTP page alone cannot make hydration complete. Only a validated live marker after complete page traversal and replay can certify completion.
