# Inbound webhooks

A connector's webhook endpoint is an address a sender such as GitHub posts to without a credential. The server stores each delivery as it arrived and answers at once; it never reads, verifies or acts on one, and it holds no sender's secret. The connector that owns the endpoint reads its deliveries with its own key, checks that each came from its sender, and marks it handled. The webhooks the instance sends are outbound ones, `events.md` 12 to 17.

## Endpoints

1. `POST /connectors/{id}/endpoints` with `{label?, duplicate_header?}`, from the connector's own key or the operator key, answers `201` with `{id, connector_id, label, duplicate_header, path, created_at, retired_at}`: `path` is `/inbound/` and 43 characters of base64url in full in this answer alone, and `duplicate_header` is lowercased. `GET /connectors/{id}/endpoints` lists the registration's endpoints to the same two keys, newest first with retired ones included, each `path` redacted to `/inbound/****` and its last four characters. Another key is refused `403 forbidden` on both doors, an id no registration carries answers `404 connector_not_found`, and a label outside 1 to 200 characters or a duplicate header that is not a header name answers `400 validation_error`. `compliance/inbound-webhooks.test.ts › makes an endpoint for the connector's own key and the operator, answering its address once`, `› refuses another key, an unknown registration and a header that is no header name`.
2. A registration holds at most ten live endpoints: the eleventh answers `409 conflict`, and retiring one frees its place. `compliance/inbound-webhooks.test.ts › holds a registration to ten live endpoints, and a retired one frees a place`.
3. `DELETE /connectors/{id}/endpoints/{endpoint_id}`, from the connector's own key or the operator key, retires the endpoint and answers it with `retired_at` set; it stays listed, retiring it again answers the same `retired_at`, and an id the registration does not hold answers `404 endpoint_not_found`. From then its address answers as statement 7 says, and the deliveries it already stored stay readable. `compliance/inbound-webhooks.test.ts › retires an endpoint, after which its address is not served`.
4. An endpoint answers only while its registration and the registration's key stand. Once the key is revoked its address answers as statement 7 says, and removing the registration (`connectors.md` 4) removes its endpoints and every delivery they stored, which the server's own `routes/inbound.test.ts` shows by reading the tables. `compliance/inbound-webhooks.test.ts › stops answering once the registration's key is revoked`, `› goes with its registration, and its deliveries with it`.
5. Making and retiring an endpoint write audit rows, `inbound_endpoint.create` and `inbound_endpoint.retire`, against the endpoint's id; retiring one already retired writes none, and neither does a receipt or a handled mark. `compliance/inbound-webhooks.test.ts › audits a creation and a retirement once each, and neither a receipt nor a handled mark`.

## The receiving door

6. `POST /inbound/{token}` with no credential, at a live endpoint's `path`, answers `202 {id}` and stores the delivery: the method, the query string as sent, every header in the order and case it arrived with repeats kept, and the body byte for byte, with the server's own clock as `received_at`. The door reads no credential: an `Authorization` header is stored like any other, and a key presented there is not stamped as used (`keys-and-oauth.md` 14). `compliance/inbound-webhooks.test.ts › stores the body byte for byte, the headers as they arrived and the query as sent`, `› stores a signed delivery whose signature verifies over the stored bytes`, `› reads no key on a receipt, never stamping one used, and stores the header like any other`.
7. An address no live endpoint holds answers what a path the server does not serve answers, `404 not_found` in the same envelope, and nothing is stored. `compliance/inbound-webhooks.test.ts › answers an address no endpoint holds as a path the server does not serve`.
8. A body over the instance's limit, 25 MiB unless `MARFA_INBOUND_MAX_BYTES` names another, answers `413 request_too_large` and nothing is stored; a body at the limit is stored. A body that has not arrived whole within `MARFA_INBOUND_READ_TIMEOUT_MS`, 30 seconds unless named, answers `408 request_timeout` and nothing is stored, so a sender that stalls holds none of the instance's bytes for longer; that is asserted against a server booted for it. `compliance/inbound-webhooks.test.ts › refuses a body over the limit, and stores one at it`, `› answers request_timeout to a body that does not arrive in time, and stores nothing`.
9. While the instance's limiter is on, each endpoint takes `RATE_LIMIT_INBOUND_REQUESTS` receipts per window, 600 unless the instance names a number; the one past it answers `429 rate_limited` with `Retry-After`, and another endpoint's window is its own. Asserted against a server booted for it, because the run's own server has the limiter switched off. `compliance/inbound-webhooks.test.ts › holds each endpoint to its own rate window`.
10. Receipt insertion checks a registration's prospective unhandled delivery count and body bytes in the same writer transaction that stores its metadata and body. `MARFA_INBOUND_BACKLOG_DELIVERIES` defaults to 10,000 and `MARFA_INBOUND_BACKLOG_BYTES` to 1 GiB, across all its endpoints including retained deliveries from retired endpoints. A receipt that would exceed either limit is refused `503 inbound_unavailable` with `Retry-After`; exactly full body-byte capacity can accept a zero-byte receipt if row and retained limits permit it. Handling frees pending capacity. A body that would take the bytes the instance holds in flight past `MARFA_INBOUND_IN_FLIGHT_BYTES`, 100 MiB unless named, is refused the same way. A sender can retry a refused delivery. `compliance/inbound-webhooks.test.ts › refuses while the backlog is full, and takes again once it drains`, `› refuses while the backlog's bytes are full`, `› checks prospective bytes and accepts a zero body at exactly full pending bytes`, `› refuses a body that would pass the bytes the instance holds in flight`. The server's own `routes/inbound.test.ts › checks concurrent completed bodies in the insertion transaction` holds concurrent body completion to the cap.
11. A receipt announces nothing on the event stream. `compliance/inbound-webhooks.test.ts › announces nothing on the event stream`.

## Reading and handling

12. `GET /connectors/{id}/deliveries` lists a registration's deliveries oldest first, without their bodies, each as `{id, endpoint_id, received_at, method, query, headers, size, sha256, duplicate_of, handled_at, outcome}`: the unhandled ones unless `state` is `handled` or `any`, narrowed to one endpoint by `endpoint_id`, `limit` at most 200 and 50 unless given, and a page the `limit` cut answering a `next_cursor` that reaches the rest; a query key it does not declare is refused (`search-and-filters.md` 8). `GET /connectors/{id}/deliveries/{delivery_id}/body` answers the body byte for byte as `application/octet-stream`, whatever the sender declared, and an id the registration does not hold answers `404 delivery_not_found`. `compliance/inbound-webhooks.test.ts › lists oldest first by cursor, narrowed by state and endpoint`, `› refuses a query key the listing does not declare, rather than answering unfiltered`, `› stores the body byte for byte, the headers as they arrived and the query as sent`.
13. Only the connector's own key reads or marks its deliveries: another key and the operator key are refused `403 forbidden` on all three doors, and nothing is marked. Another connector naming the delivery under its own registration reaches nothing either: the body and the mark answer `404 delivery_not_found`, and its listing narrowed to the other's endpoint is empty. `compliance/inbound-webhooks.test.ts › reads and marks to the connector's own key alone`.
14. `POST /connectors/{id}/deliveries/handled` with `{ids, outcome}`, at most 200 ids and `outcome` one of `processed`, `duplicate` or `rejected`, marks each delivery with `handled_at` and the outcome and answers `{data}` with them in the order named. The first mark stands, so marking again answers it unchanged; a request naming an id the registration does not hold answers `404 delivery_not_found` and marks nothing. `compliance/inbound-webhooks.test.ts › keeps the first mark, and marks nothing when an id is not the connector's`.
15. On an endpoint made with a `duplicate_header`, a delivery repeating that header's value carries `duplicate_of`: the earliest retained delivery on the same endpoint that carried it, as `{id, outcome}`, the outcome being how that delivery was handled or `null`. Both are stored. A delivery with a new value, or one on an endpoint naming no header, carries `null`. `compliance/inbound-webhooks.test.ts › marks a repeat of the duplicate header with the first delivery and how it was handled`.
16. `GET /` names `inbound_webhooks` among its features. `compliance/instance.test.ts › describes itself at the root`.

17. All retained receipts, handled or pending, count toward a registration's retained capacity across live and retired endpoints. `MARFA_INBOUND_RETAINED_DELIVERIES` defaults to 10,000 rows and `MARFA_INBOUND_RETAINED_BYTES` to 1 GiB, both positive safe integers. The immutable internal charge is body bytes plus canonical UTF-8 JSON metadata (`id`, `endpoint_id`, `connector_id`, `received_at`, `method`, `query`, ordered `headers`, `size`, `sha256`, `dedupe_key`, `handled_at:null`, `outcome:null`) plus 32 bytes reserved for handling. Derived `duplicate_of` is excluded. This bounds logical charged storage, not SQLite file size or memory usage; the internal charge is omitted from public delivery JSON. Exceeding either retained limit is the same capacity refusal as statement 10, including when expiry is disabled. Handling neither releases retained capacity nor changes the charge. `compliance/inbound-webhooks.test.ts › bounds handled zero-body receipts across live and retired endpoints of a registration`, `› counts query metadata when every retained body has zero bytes`.
18. `PUT /config` accepts optional integer values from 0 through 36500 for `inbound_handled_retention_days` and `inbound_pending_retention_days`, read back by `GET /config`. Absent fields use `MARFA_INBOUND_HANDLED_RETENTION_DAYS` (7 by default) and `MARFA_INBOUND_PENDING_RETENTION_DAYS` (30 by default); zero keeps that class regardless of age and does not disable capacity. Full replacement, unknown-field refusal, instance identity round trips and `config.manage` standing remain. `compliance/inbound-webhooks.test.ts › round trips retention overrides and refuses invalid values`.

**A fixture cannot age a retained receipt over HTTP.** The `inbound-delivery-cleanup` job resolves current retention overrides once each pass, ages handled receipts from `handled_at` and pending receipts from `received_at`, and runs every minute unless `MARFA_INBOUND_CLEANUP_INTERVAL_MS` names another integer interval from 1 through 2147483647 milliseconds (the native timer limit). A pass projects at most 500 candidates ordered by the appropriate age timestamp and id, through two indexed age classes with at most 500 candidates each before the merge. It deletes a prefix targeting 32 MiB of charged storage, allowing one oversized first eligible row to progress, and reports deleted and remaining work. Metadata deletion and body cascades commit together; subsequent ordinary passes resume without an unlimited drain. Capacity refusal never evicts pending work; only configured age expiry removes it. These bounds do not claim constant SQLite internal scan work. The server's own `routes/inbound.test.ts` asserts expiry, zero retention, rollback, batch ordering and resume.

**That the door answers quickly whatever the connector is doing is not stated here, because no fixture can time it fairly.** It looks the address up by its hash and counts the endpoint's rate window before reading the body, then rechecks current endpoint/key standing and duplicate-header policy and prospective registration capacity inside the insertion transaction; it waits on nothing a connector does. A write that meets the database's write lock past its budget answers `503 write_contention` (`errors/contention`), which a sender records as a failed delivery.

**That no address, header, query or body reaches the server's logs is not stated here, because the fixtures cannot read them.** The server's own `routes/inbound.test.ts` reads what the server writes while it takes a delivery, and the address appears there only as `/inbound/****` and its last four characters. Unknown receipt insertion failures become a fixed safe error before logging, exception reporting, active-span recording or error notification; the original SQL wrapper, parameters and cause do not enter those sinks. Real metadata and body insertion failures assert this with synthetic sentinels, alongside rollback and typed write-contention controls. This receipt boundary does not claim to sanitize unrelated storage paths.
