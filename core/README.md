# Marfa core

The Rust engine every native client embeds: a local SQLite working copy of a slice of one Marfa server, kept current from its event log, read locally, and written to through a queue that holds each write until the server answers it. `conformance/spec/device.md`, `queue-and-verdicts.md` and `folders.md` say what it does; the fixtures under `conformance/src/suites/device/` hold the `marfa` binary to them.

| Crate            | What it is                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| `marfa-core`     | The engine. `src/contract.rs` is written from `openapi.json` by `pnpm generate`                              |
| `marfa-cli`      | The `marfa` binary                                                                                           |
| `bindings/swift` | The UniFFI crate and `build.sh`, which packages it for `withmarfa/marfa-swift`; a cargo workspace of its own |
| `bindings/node`  | The napi-rs module `@withmarfa/core`                                                                         |

## The binary

`marfa --help` lists every command, the exit codes and the `--json` error shape; `marfa operations` maps each published operation to its command. `marfa device --db PATH` is a working copy, and `marfa folders` a folder on disk that carries its own store.

- **Requests:** every command sends through `marfa_core::http::Http`, the stack the working copy uses: it follows no redirect, reads the contract header on every answer, and renews a refused credential once. A command waits up to 90 seconds for an answer to begin and as long again to read it, which an operation that works before it answers needs; an upload waits on the server's work, and a streamed answer fails after 45 seconds of silence. The binary writes each path, query name, body key and enum value by hand. `commands/driven.rs` runs each command in this process against a local server that refuses every request but the root, and holds each request a command sends, up to that refusal, to `openapi.json`: the method and path, each query name, each key of a JSON body, and each enum value a flag names. A flag that takes any text leaves its value to the server. A rename in the document fails that test.
- **Docs:** `marfa docs` reads the public docs site, which is not a Marfa server, so it is the one command that does not send through `Http`. It has a small client of its own in `commands/docs.rs` that sends no credential, checks no contract, follows up to five redirects, and waits 10 seconds to connect and 30 seconds each for an answer to begin and to be read. It refuses `--url` and `--key`. It reads `https://docs.marfa.so`, or the address in `MARFA_DOCS_URL`.
- **Server:** `--url`, then `MARFA_API_URL`, then the server a kept credential made current.
- **Credential:** `--key`, then `MARFA_API_KEY`, then the operating system's keychain, where `marfa keys keep` and `marfa login` put one. Never a plain file. With both variables set, a command reads and writes no keychain, which is how an agent runs it. Prefer the variable, the keychain, or standard input (`marfa keys keep` reads the key from it) to `--key`: a process argument is readable by other users of the machine and stays in shell history.
- **Plain `http`:** before a command sends a credential, a device code or a refresh token to an `http` address whose host is not `localhost`, in `127.0.0.0/8` or `::1`, it prints one warning to standard error naming the address, and goes on. `--allow-http`, or `MARFA_ALLOW_HTTP` set to `1`, `true`, `yes` or `on`, states that it is intended, for a private network that is already encrypted, and silences it. Each address is warned of once per run. A refusal in `--json` follows the warning line on standard error.
- **Synced and network storage:** when `folders add` makes a folder, or a watch starts on one, in a directory below `Library/Mobile Documents` (iCloud Drive) or `Library/CloudStorage` (the File Provider services, such as Dropbox, OneDrive, Google Drive and Box) of the home directory, in a directory macOS reports as ubiquitous (`isUbiquitousItem`, as it does for `Desktop` and `Documents` with iCloud's "Desktop & Documents" on, and for every File Provider item, so the warning names iCloud Drive or another cloud service), or on a file system `statfs` reports as `smbfs`, `nfs`, `afpfs` or `webdav` (macOS) or as NFS, CIFS or SMB2 (Linux), it prints one warning to standard error naming the cause, and goes on. The home directory is the one the operating system records for the user and the one `HOME` names. Each folder is warned of once per run, including when a watch of every folder starts it again. A refusal in `--json` follows the warning line on standard error. A provider that keeps its files elsewhere is not detected. The core makes the finding (`Folder::storage_cause`), and the Swift binding gives it to an app on `Folders::add`'s answer and on the watch's `Watching` event; the command line prints the warning.
- **Unattended runs:** `MARFA_KEYCHAIN` names a keychain file to use instead of the person's, on macOS, and refuses every prompt. Tests and CI use it; CI fails a run that changed the login keychain's `marfa` entries.

Refresh, `login`, `logout`, `keys keep` and `keys forget` coordinate through one private lock per stored server for each credential store, independent of `HOME`, `TMPDIR` and `XDG_RUNTIME_DIR`. The lock files contain no credentials. For the person's own keychain, they stay under `.marfa-credential-locks` in the home directory recorded by the operating system. For a keychain file that `MARFA_KEYCHAIN` names, they stay in a folder beside the file, named for it with `.locks` added, so a run that removes its keychain's folder leaves no locks behind; a keychain file in `~/Library/Keychains` uses the home directory's locks, because the person's own keychain is one of them. Leave lock files in place while commands may be running. An unsafe lock path is refused before reading or changing stored credentials. `keys forget` works offline without refreshing a token. Logout removes the local sign-in and reports whether server revocation succeeded; without a saved revocation endpoint, it reports `revoked: false`.

### Process outcomes

| Exit | Meaning                                                                               |
| ---- | ------------------------------------------------------------------------------------- |
| 0    | Completed, including a completed drain containing refused writes                      |
| 1    | Request refused or invalid, including another contract                                |
| 2    | Invalid command line, missing store, or missing server                                |
| 3    | Environmental failure, including network failure, rate limits, and full local storage |
| 4    | Working-copy or queue rule, other store fault, or unavailable credential storage      |
| 5    | Missing or refused credential, or ended sign-in                                       |

`device drain` preserves its complete stdout report when it exits 3 for an unavailable pass or undelivered writes, or 5 for a credential-stopped pass. It prints no second error envelope for these report outcomes. Credential stop takes precedence if both occur. A completed pass with refused writes exits 0 and its plain output separately counts refused verdicts; JSON retains each typed verdict. Held writes alone do not make an environmental failure. A direct renewal error prints its typed error on stderr with empty stdout; earlier answers remain committed and the current queued request, idempotency key, and refusal count stay unchanged. Local renewal failures carry no invented server status. An environmental renewal failure while sending a queued request returns the unavailable report; a renewal failure during a follow-up read can end the call with its typed error.

A copy saves before it has reached a server. `device types declare` takes the types an app saves, as one JSON object or an array, and `device types declared` lists them; until it hydrates the copy checks each write against them and the types Marfa ships, and a hydration registers the ones the instance lacks where the key may, and says which it could not. A drain needs a completed hydration: until the first one completes, it is refused `no_cursor` and sends nothing. A follow on a copy never hydrated, or whose hydration was interrupted, instead waits for a hydration to complete, asking the server nothing, and one on an expired copy is refused `copy_expired`; `device follow` holds the store while it waits, so no other process can hydrate it meanwhile. A follow that has its server again after losing it drains the queue once where a drain has work, on a thread of its own so the stream is still read, and tells `queue.drained` with the drain's report or `queue.not_drained` with the error it ended with; a folder's watch drains in its own pass instead. That drain waits for one under way to end and does only the work left. The follow ending, by a stop or an error, stops that drain as a drain's stop does. `device types served` and `device edge-types served` read the server's catalog without hydrating, so a slice can be chosen first. `hydrate`, `catch-up`, `drain` and the two `served` reads stop on Ctrl-C and exit 3 with the code `canceled`, leaving the store consistent: a stopped hydration refuses reads, a stopped catch-up keeps its cursor, and a stopped drain leaves unsent writes queued. A stop does not wait on an upload in flight, which can take as long as the server takes, or on a write whose operation takes an `Idempotency-Key` in `openapi.json` (an item or edge write): that write stays queued as sent, under its key, an answer to it that arrives later is dropped, and the next drain sends it again. The server answers a keyed write from its record of the key, and takes an upload by its bytes. It keeps no record for a tag, metadata or extension write and would apply one sent again over a newer change, so a stop waits for that write's answer, within the request's time limits, before the drain ends. Each binding takes a `Stop`; the caller raises it when its language's cancellation is requested.

Reading commands on an absent store, including `--reader` and `device changes`, report `no_store` and exit 2. Queue JSON retains dependency history; plain “waiting on” names only unresolved dependencies.

## Folder directories

Read [remote folder health](marfa-cli/FOLDER-HEALTH.md) with `marfa folders health FOLDER_ID` to inspect the last reports from each sign-in and local copy.

A program on the machine can see whether folder syncing runs, and how each folder fares, in the [record of folder watches](marfa-cli/FOLDER-WATCH-RECORD.md) that `marfa folders watch` keeps beside the folder registry.

A folder remains bound to the directory it opened. If that directory or its state is replaced during a pass, the pass reports `root_gone` and a watch waits for the original binding to return. Admission resolves symbolic links in the directories above the folder, such as `/var` and `/tmp` on macOS, and records the resolved path. It does not follow a symbolic link at the folder's own directory, at any component below it, or at any component that a later `..` climbs back out of, and refuses such a path with `invalid`, naming the first such link. A path in which a `..` climbs back out of a directory that does not exist is refused with `invalid` before anything is created. Every command but an add takes a path that the folder registry lists as listed, without resolving it again, and every command but an add and a removal refuses it with `invalid` where a symbolic link now stands in it. Any other spelling reaches a listed folder only where that folder's listed path, opened without following links, is the directory the spelling reaches; where a listed path now reaches that directory only through a symbolic link, the spelling could mean either folder, and every command but an add and a removal refuses it with `invalid`.

A `marfa folders add` that is refused or fails removes what it made: each directory it created, such as the folder's own directory and its `.marfa`, and each file it put in `.marfa`. It keeps every directory and file that was there before, and removes nothing from a `.marfa` that already holds a store. An add refused after it writes the folder's settings, as one that would sit inside another folder is, has already replaced any `.marfa/folder.yaml` that was there. It removes a directory only while that directory is still the one it made and is empty, and it follows no link.

`marfa folders remove` removes the folder's database, cache, and settings while preserving its item files. It leaves empty administrative directories, including `.marfa`, in place. It never follows a symbolic link. It takes a path through one only where that path is exactly the path the registry lists, and refuses any other path through a link with `invalid`, naming the listed path of the folder that path reaches. It deletes a listed folder's state only where the store at the folder's listed path is the one the registry lists for it; otherwise, as when the directory is gone or now reached through a symbolic link, it only takes the folder off the list, and reports `removed` as `false` with the reason. A removal that deletes a folder's state also takes every registry entry for that folder's store off the list, so a folder moved since it was listed leaves no entry behind. An empty `.marfa` does not identify a nested folder or prevent adding the directory again. Folder storage is supported on Apple platforms and Linux on filesystems that report nonzero file and directory creation times. A root without usable birth identity, or an unsupported platform, is refused before administrative state is created. Entries without usable birth identity are held. An incomplete inventory, including an unreadable file or child directory, suppresses missing-file journaling and deletion throughout the folder until a complete pass can rule out a move.

`marfa folders watch` with no directory watches every folder the registry lists, each with a watch of its own on a thread of its own, in one process. Each folder uses the server its copy was hydrated from: with the command's own credential where that is the server the command names, and otherwise with the credential the keychain keeps for that server, so a key named for one server is never sent to another. A folder that has never hydrated uses the server the command names. The registry is read again every 2 seconds: a folder listed since joins the watch, and the watch of one no longer listed ends. A registry that cannot be read leaves the folders watched as they are. A folder that cannot be opened, because its first sync waits, its directory cannot be found, another process works it, or there is no credential for its server, is reported once and tried again every 5 seconds. A folder whose watch ends, as when the server refuses its credential or its changes stop reaching it, is reported once and tried again after 60 seconds; one whose credential was refused is opened again only with another credential. A reason is reported again only when it changes, or after the folder was watched in between. Every line about one folder names its directory, and with `--json` each such line is one JSON object with a `dir` field. A folder whose directory is gone can be removed, and leaves the watch.

One process works a folder at a time. A command that works a folder, such as `folders add` over an existing folder, `folders confirm`, `folders restore`, `folders remove`, `folders scan`, `folders pull`, `folders push`, `folders hydrate` or `folders unmatched --remove`, and finds it held asks the process holding it to let it go, and waits up to 10 seconds. A watch, of one folder or of every folder, sees the request within a fraction of a second, finishes the step of its pass under way (sending the settings file's edit, the scan, the drain or the pull, so no write is cut off), lets the folder go and says so, and goes on with the other folders it watches. It tries the folder again every second, with the server and credential it began with, and takes it back, saying so, once the command ends. A folder the command removed or took off the registry leaves the watch, and a watch of that folder alone ends. A folder held by another process, with no command asking for it, for more than 10 seconds is said once to be held by another process, and watched again once that process lets it go. A process that does not let go in time, such as a suspended watch, one whose step waits on a slow server, or another command still working the folder, leaves the command refused with `reading_handle`. The request is a lock the asking command holds in the folder's `.marfa` directory while it waits and works, which the system lets go however the command ends, so a command that crashes never leaves the folder blocked. A request that cannot be made, as in a read-only `.marfa`, leaves the command waiting all the same and then refused with the reason. A watch never asks, so a second watch of a folder is refused at once.

## Claim and recover locally

Run the CLI as the server's operating-system account, using the absolute path in `MARFA_CONTROL_SOCKET`:

```sh
marfa --socket /run/marfa/control.sock setup open
marfa --socket /run/marfa/control.sock setup claim --email owner@example.com
marfa --socket /run/marfa/control.sock owner recover
```

`setup open` issues a five-minute, single-use handoff and opens the browser. Use `--no-browser` to print the link. `setup claim` and `owner recover` ask for a hidden password. For automation, add `--stdin` and send a JSON object containing `email` and `password` for claim, or `password` for recovery. For a remote terminal claim, use `--url https://marfa.example setup claim`; its JSON input also needs `code`. Secrets are never command-line options. Recovery ends browser sessions and keeps ordinary keys, apps and passkeys.

`--socket` cannot be combined with `--url`, `--key`, `MARFA_API_URL` or `MARFA_API_KEY`. It uses no keychain and never falls back to HTTP. A command that streams its answer, such as `blobs download`, reaches the server through the socket too. Local authority carries no key, so a command whose operation needs one, such as `export`, `events` or `items list`, gets `401` from the server, and the command says it needs a key, which `--socket` does not carry. Linux requires `getfacl` from the `acl` package. The socket directory must be owned by the server account with mode `0700`, without access ACLs or symbolic links. The socket is `0600`. A live collision is refused. After a crash, the server replaces a stale socket only when a connection is refused. A live listener or a non-socket file at that path is left intact and prevents startup. The listener holds a reservation on a private `<socket-path>.lock` file until its socket cleanup finishes. The file stays on disk, and a process crash releases the reservation automatically. Do not delete that file while a server is running or starting. Distinct processes need distinct socket paths.

Set `MARFA_CONTROL_ONLY=true` to run only the private listener when public HTTP cannot start. In the service container, `marfa-entrypoint control-only` starts that mode against the configured database; stop an existing listener or choose a distinct private socket path first.

## Build and check

```sh
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets --no-deps -- -D warnings
cargo nextest run --locked --workspace
cargo build -p marfa-cli   # the device fixtures refuse a binary older than its source
```

Then the same three in `bindings/swift`. Every test binary runs under `scripts/test-limits.sh`, which caps the file size and processor time it can take.

`marfa-cli/COMMANDS.md` is the reference for every command, written as Markdown from the clap command tree: the global options and exit codes once, then each command's description, usage, and tables of its arguments and options. The docs site includes it as its CLI reference. A test fails when the committed file is out of date; after changing a command or its help text, regenerate it with `MARFA_WRITE_COMMANDS=1 cargo test -p marfa-cli --bin marfa reference` and commit it. The site renders the file as MDX, so another test fails on a `<`, `>`, `{`, or `}` outside a code span or fenced code block. In help text, put a placeholder or any other of these characters in backticks.

`scripts/server-up.sh` claims a fresh instance through its private socket and mints an ordinary working key with explicit permissions. It exports `MARFA_TEST_KEY`, `MARFA_TEST_SOCKET`, and the throwaway owner credentials from `scripts/test-owner.example.env` as `MARFA_TEST_OWNER_EMAIL` and `MARFA_TEST_OWNER_PASSWORD`. With `MARFA_SERVER_KEEP`, the key and owner survive restart. Incomplete kept credentials are refused. `scripts/server-keys.test.sh` exercises both boots and the owner's sign-in. Linux requires the `acl` package so the server can check socket ACLs.

### Which jobs run

Three jobs check the core. `scripts/ci-required.ts` decides from the changed paths which of them a pull request runs. A draft pull request runs none of them; marking it ready for review, and every push after, runs the ones its changes name.

- **`Core checks (Linux)`** (`ci.yml`, Ubuntu) runs the three commands above for the core workspace. It is the only job that lints the credential store used when the operating system is not macOS, and the only one that tests the in-memory test keychain the tests use in its place. A pull request runs it when it changes the core, `openapi.json` or `ci.yml`; a change to the Swift crate alone does not.
- **`Core checks`** (`ci.yml`, macOS) runs the same three commands, with the tests under a check that the login keychain is unchanged, then the three in `bindings/swift`. It keeps the macOS keychain and the Apple builds. A pull request runs it when it changes the core, `openapi.json` or `ci.yml`. Its last step runs `bindings/swift/build.sh`, as `withmarfa/marfa-swift` does, when the change reaches the Swift crate, its lockfile or the script, so a dependency bump that stops the Swift glue from generating fails here.
- **`Core / Rust, bindings, live`** (`core-live.yml`, macOS) runs the tests that need a live server (`scripts/server-up.sh` boots one; `--run-ignored only` runs them), builds the Swift crate in release mode for the Apple targets, builds and tests the Node module, and proves the Node binding against a booted server. `ci.yml` calls it for a pull request that changes the core, `openapi.json`, `core-live.yml` or `ci.yml`, so `Full CI` waits for it. The Node module's JavaScript, test and script files run only here.

A push to `main` runs `ci.yml` in full unless it reaches only the format check and `ci.yml` passed on the commit before it. It runs `core.yml`, which calls the live job, when it changes the core, `openapi.json`, `core.yml`, `core-live.yml`, or the server and the packages the live tests boot it from. The nightly run and a manual dispatch run every job.

A pull request that changes the server and leaves `openapi.json` alone runs none of the three. A server change that breaks the live tests or the Node binding's proof is therefore found on the push to `main`, not before the merge. The Ubuntu jobs in `ci.yml` that run the conformance suite and the CLI scenarios build the `marfa` binary and run no Rust tests.

## Telemetry

The core can report its own work, and sends it nowhere itself. It records through the [`tracing`](https://docs.rs/tracing) crate, and the host decides where the records go by installing a subscriber, such as an OpenTelemetry layer. Telemetry is off until a host turns it on in two steps:

1. Enable the `telemetry` Cargo feature of `marfa-core`. Without it no tracing code or dependency is built, and the Swift and Node bindings leave it off.
2. Install a `tracing` subscriber in the host process. Until one is installed, `tracing` drops every record.

```toml
marfa-core = { path = "marfa-core", features = ["telemetry"] }
```

Cargo builds a package with a feature when any package in the same build asks for it. A command such as `cargo build --workspace` therefore builds the Node module's copy of `marfa-core` with the feature too, as soon as the `marfa` binary enables it. Build the Node module from its own directory, as `pnpm run build` does.

| Span       | Covers                                                | Fields                                                           |
| ---------- | ----------------------------------------------------- | ---------------------------------------------------------------- |
| `drain`    | One drain pass, called or started by a follow         | `outcome`, `answered`, `held`, `undelivered`, `unsent`, `unmade` |
| `catch_up` | One `Core::catch_up`                                  | `outcome`, `applied`, `skipped`                                  |
| `write`    | One queued write sent to the server, inside a `drain` | `outcome`, `kind`, `status`                                      |
| `search`   | One `Core::search` or `Core::search_shown`            | `outcome`, `hits`                                                |

`outcome` says how the operation ended. A `catch_up` ends `ok`, `error` or `canceled`, and a `search` ends `ok` or `error`. A `drain` can also end `unavailable`, where the server could not be reached or asked for time, or `credential_refused`. A `write` ends `answered`, `unavailable`, `error`, or `canceled` where a stop left it in flight. `kind` is the queued write's kind, such as `create_item`.

Two events carry `code`, the same word `CoreError::code` gives everywhere else: an `ERROR` event when an operation returns an error, and a `WARN` event when a request the `drain` makes gets no answer or cannot get through, and the drain leaves the work for a later pass. A failure is recorded once: a write error that ends the drain is only the drain's `ERROR`. A write the server answers, even with a 5xx or a 429, records no event; its `write` span ends `unavailable` with the `status`. A stop the caller raises ends the span `canceled` and records no event.

The core records only an operation's name, a count, an `outcome`, a write's kind, an HTTP status and an error `code`. It never records an item's content, title, tag, id, key or natural key, a credential, an address, a header, a path, a query or an error message. `marfa-core/src/telemetry.rs` is the only source file outside the tests that names `tracing`, and `marfa-core/src/telemetry_tests.rs` runs each operation with recognizable secrets and fails if any reaches a span or an event.

### In the `marfa` binary

The binary enables the feature and installs a subscriber that exports over OTLP, but only when the environment names a collector. With none named it installs nothing, starts no thread and sends nothing, and its standard output, standard error and exit codes are what they would be without telemetry. The settings are the standard OpenTelemetry variables, and two for PostHog:

| Variable                                                          | Effect                                                                                                                                    |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                                     | The collector's base address, `http` or `https`. The trace goes to `v1/traces` under it. Setting it turns telemetry on.                   |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`                              | The address the trace goes to, as written. It also turns telemetry on and takes precedence.                                               |
| `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_EXPORTER_OTLP_TRACES_HEADERS` | Headers as `key=value` pairs separated by commas, values percent-encoded. The traces variable wins for a header both name.                |
| `OTEL_EXPORTER_OTLP_TIMEOUT`, `OTEL_EXPORTER_OTLP_TRACES_TIMEOUT` | Milliseconds one send may take. The default is 2000. The binary waits no longer than this at exit.                                        |
| `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG`                  | `always_on` (the default), `always_off` or `traceidratio` with a ratio from 0 to 1. A `parentbased_` form acts as the sampler it wraps.   |
| `OTEL_SERVICE_NAME`                                               | The service name on the trace. The default is `marfa-cli`.                                                                                |
| `OTEL_SDK_DISABLED`                                               | `true` turns telemetry off.                                                                                                               |
| `MARFA_POSTHOG_HOST`                                              | The PostHog host that receives a failed run's exception, `https` or, to this machine, `http`. It needs the next variable and an endpoint. |
| `MARFA_POSTHOG_PROJECT_TOKEN`                                     | The PostHog project token for those exceptions. It needs the previous variable and an endpoint.                                           |

A malformed `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` turns telemetry off for that run. Without `--json` it prints one line on standard error that names the variable and never its value; with `--json` it prints nothing, since standard error is then one JSON object. A query in the base address stays a query: `http://host:4318/?token=abc` posts to `/v1/traces?token=abc`. A header, timeout, sampler or ratio that cannot be used is left out, and the default applies.

Each run is one trace. Its root span is named for the command path, such as `marfa items create`, and carries `exit_code`. The core's spans are beneath it, including those made on other threads. A command that fails adds an `error` event to the root with `code`, the CLI's error code, and `exit_code`; a command that exits 3 or 5 after printing a drain report has an event with `exit_code` only. A command that ends because Ctrl-C stopped it (including a `canceled` hydration, catch-up, drain or served read, which exits 3), or because its output was closed, is not a failure: it keeps its `exit_code` and adds no event and no error status. A command line that clap refuses is not a run and exports nothing.

The binary exports only the command path, `exit_code`, `dropped_spans`, the core's span names, counts, outcomes, kinds, statuses and error codes, durations, and `error` and `warning` events with `code`. `marfa-cli/src/telemetry/layer.rs` holds the list of field names and drops every other field, and any value that is not a short plain word. An error message, an argument, an address, a key, a path and an item's content are therefore never sent, even though a message can echo them. Adding a field means adding it to that list.

The binary posts OTLP/HTTP JSON with the HTTP client it already uses, so the build adds no second HTTP stack and no async runtime. It does not implement protobuf, gzip, gRPC, metrics, logs or a retry, and it ignores `OTEL_EXPORTER_OTLP_PROTOCOL`. A collector that accepts only protobuf receives nothing useful. A redirect is not followed, so a header reaches only the address named. A proxy named by `HTTPS_PROXY`, `HTTP_PROXY` or `ALL_PROXY` carries the post to a collector on another host and is not used for one on this machine, which a proxy cannot reach.

Spans are sent from a thread of their own, in batches of at most 512 every 5 seconds, so that a long-lived command such as `folders watch` reports while it runs. At most 2048 spans wait for a send; past that a span is dropped and the root's `dropped_spans` counts it. At the end of a run the binary sends what is left and waits up to the timeout, whatever the collector does. A collector that is unreachable, slow or refusing never changes the output or the exit code, and the binary reports none of those failures.

`folders watch`, `events` and `device changes` run until the person stops them, and the `device` commands that stop on Ctrl-C (`hydrate`, `follow`, `catch-up`, `drain` and the `served` reads) end when stopped. Ctrl-C ends each of these through its normal exit, so the trace is sent first. `folders watch`, `events` and `device changes` then exit with status 130, which `marfa --help` lists with the exit codes; the others keep the exit they give a stopped command. A `folders watch` pass, in any folder it watches, that has not finished 2 seconds after Ctrl-C, because it waits on a server that does not answer, is left behind and the watch ends anyway; what it had not finished stays queued or on disk. `folders watch` of one folder, `events` and `device changes` take Ctrl-C once they are open, so before then Ctrl-C ends the process as the signal does and sends nothing; a watch of every folder takes it from the start. A second Ctrl-C ends the process at once with status 130 and sends nothing. A command with no stop of its own, such as a request in flight, is ended by Ctrl-C and sends nothing, and so is a process that is killed.

A failed command can also reach PostHog's error tracking, which groups `$exception` events that a trace does not produce. The binary sends one only when an OTLP endpoint, `MARFA_POSTHOG_HOST` and `MARFA_POSTHOG_PROJECT_TOKEN` are all set and `OTEL_SDK_DISABLED` is not `true`, the three settings the server asks for. With any of them missing the binary loads and sends nothing, and its exit codes are unchanged. Its output is unchanged too, except that with an endpoint and exactly one of the two PostHog variables set, it prints one line on standard error that names the variable and never its value, and prints nothing under `--json`; the trace is exported as usual. The host must be an `https` address, or an `http` address on this machine (`localhost`, `127.0.0.0/8` or `::1`), because the project token travels in the request body, and `--allow-http` does not widen that. For any other host, and for an address that carries a user name or password, the binary prints the same one line and sends nothing. A query or fragment in the host is dropped.

A run fails by the rule of the trace's `error` event: not a run that Ctrl-C stopped, and not a `canceled` one. A command that panics also fails: the binary ends the trace as failed with status 101, sends one event of type `panic`, and lets the panic go on, so its message on standard error and its exit status are what they are without telemetry. The panic's message and location are never sent, since either can carry content. The binary posts one event to `/i/v0/e/` under the host, with the HTTP client it already uses, once, with no retry, no redirect and no reading of the answer past its status. It posts beside the trace's last send and waits within the same timeout (`OTEL_EXPORTER_OTLP_TIMEOUT`, 2000 milliseconds by default), so a PostHog that is unreachable, slow or refusing neither changes the output or the exit code nor holds the exit past that timeout. A proxy is used or not by the trace's rule above. `OTEL_TRACES_SAMPLER` does not apply: the exception is sent whether or not the trace is sampled.

The event has no person. Its distinct id is random and new for each process, `$process_person_profile` is `false` and `$geoip_disable` is `true`, and the binary stores no id. Its properties are:

- **The exception:** `$exception_list` with one entry, whose `type` is the CLI's error code and whose `value` is a fixed sentence for that kind of error, and `$exception_level` set to `error`. It has no stack trace, because a CLI error has none. A run that fails with an exit status and no error, as a drain does when its report exits 3 or 5, has the type `exit` and the meaning of that exit code.
- **The run:** `command`, the command's names without any argument (`items create`), `error_code` where there is an error, `exit_code`, `service.name` as the trace's, `service.version`, `$os`, `arch`, `$lib` and `$lib_version`.

The `value` is never the error's message, which can echo a field name, an id, a path or an address. `marfa-cli/src/telemetry/describe.rs` holds one static sentence for each kind of error, and a new kind does not compile until it has one. The project token is in the request body's `api_key` field and nowhere else. An argument, an address, a key, a path and an item's content are never sent.

## Bindings

Swift: `bindings/swift/build.sh` builds the XCFramework and its glue for macOS, iOS and the simulator. `withmarfa/marfa-swift` runs it at the commit it pins.

`cargo-swift` embeds one UniFFI bindgen, and the crate's `uniffi` has to write the metadata that bindgen reads. `build.sh` pins `cargo-swift`; `Cargo.toml` and `.github/dependabot.yml` keep `uniffi` to the version that `cargo-swift` embeds. To move to a newer `uniffi`, wait for a `cargo-swift` release that embeds the matching bindgen, then change the `cargo-swift` pin, `uniffi` and the Dependabot ignore in one pull request.

Node: it sits outside the pnpm workspace, so every pnpm call carries `--ignore-workspace`:

```sh
cd bindings/node
pnpm install --ignore-workspace
pnpm --ignore-workspace run build
pnpm --ignore-workspace run check
pnpm --ignore-workspace run test
```

Every surface names a core error by `CoreError::code`: the `code` in the binary's `--json` envelope, and `code` on an error the Node module throws or rejects with. The Node error is an `Error` whose message starts `code: `, with the properties the Swift error carries as fields: `serverCode`, `status`, `retryAfterSeconds`, `origin`, `location`, `path`, `reason`, `unsent`, `expected`, `got`, `served`, `writeSent` and `hash`, each where the error has it. `onEnd` of a `follow` receives that same error, or one coded `listener_threw` where an `onChange` threw. The Swift error answers `code()` with the same word, held by a test that crosses every `CoreError`. A catch-up keeps the catalog it took whatever ends it, so a failed one says whether it changed: `catalogChanged` on the Node error, `CatchUpError.Failed(error:catalogChanged:)` in Swift, and `catalog_changed` in the binary's `--json` envelope.

`scripts/binding-proof.sh` drives the built Node binding through an offline write and its verdict against a real server.
