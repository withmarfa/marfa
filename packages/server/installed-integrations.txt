# What this image installs into MARFA_INTEGRATIONS_ROOT.
#
# The image build stages exactly these and nothing else, and the in-image
# verification asserts that exactly these arrived, in the shape declared.
# Removing one is an edit here, which is a decision somebody makes on
# purpose, rather than a directory quietly shrinking and the image getting
# smaller with it.
#
# One name per line. Blank lines are ignored and everything from a # to the
# end of a line is a comment. A name is `<namespace>/<name>`, the manifest
# identifier, and it is also the directory the integration lives in under
# integrations/ today; when integrations are ordinary published packages
# this becomes the install list and a name gains a package specifier
# beside it.
#
# The two-segment shape is enforced rather than assumed. A name is
# interpolated straight into the image build's staging paths, so a segment
# reading `..` would write outside the staging directory; the parser
# refuses that shape instead of trusting this file to be well formed. A
# segment beginning with `_` or `.` is refused for the mirror of that
# reason: discovery skips those as scaffolding, so such a name would ship
# in the image and never load.
#
# A name may carry the marker `manifest-only`, which says the integration
# ships a manifest and no dispatchable entry. The verification holds the
# declaration to that: a plain name must have built a handler entry, and a
# manifest-only name must not have. Without the marker an integration could
# lose its handler and still verify, which was the one kind of shrink the
# old count did catch.
#
# Nothing carries the marker today, and it earns its place anyway. What it
# buys is not the manifest-only case, which currently has no instance; it
# is the strictness a plain name can then be held to. Drop the marker and
# the verification has to accept `dist/manifest.js` for every name, because
# it can no longer tell a deliberate manifest-only entry from an
# integration that quietly lost its handler. So the marker protects the
# fourteen names that do not carry it.
#
# A name here with no matching directory fails the build, and a directory
# with no name here is not shipped. The suite holds the two in agreement,
# so an integration nobody declared fails in seconds rather than during a
# build.
#
# The scaffold under integrations/_template is deliberately absent, and its
# flat, underscore-prefixed directory is not the `<namespace>/<name>` shape a
# name here has. It is a starting point for authors rather than an
# integration, and the runtime's discovery skips it for the same reason.
#
# The fixture the verification dispatches through is absent for a different
# reason: it is the server's own, staged outside this root entirely and
# dropped from the image once the verification has passed. Nothing about it
# is installable, so naming it here would be a claim the image would then
# have to make good.
#
# Installing nothing is a real deployment shape, and it is spelled with a
# line reading `none` rather than by an empty file. An empty file is what a
# bad merge leaves behind, and an image that ships an empty integrations
# root boots a substrate with no registrations and says nothing about it, so
# the two cases must not look alike.
