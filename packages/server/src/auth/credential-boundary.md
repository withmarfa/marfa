# Credential persistence boundaries

This integration targets Better Auth and OAuth Provider 1.7.1. The provider's [adapter guide](https://www.better-auth.com/docs/guides/create-a-db-adapter) requires a real transaction callback for transactional behavior. The [Drizzle adapter](https://www.better-auth.com/docs/adapters/drizzle) remains responsible for model mapping and SQL. Marfa wraps that adapter and gives it the transaction-aware Drizzle handle used by its own stores.

## The database unit

`credential-adapter.ts` audits all seven mutation methods: `create`, `update`, `updateMany`, `delete`, `deleteMany`, `consumeOne`, and `incrementOne`. Provider transaction callbacks receive the same facade. A nested operation joins the normal SQLite connection and registry/commit-hook frame; it cannot commit an independent provider connection. A zero-row result records no mutation. Model names and safe row, user, and client IDs identify records; credential values, verification identifiers, passwords, codes, private keys, and cookie values are excluded.

Owner creation prepares the password before one user/account/audit transaction. Sign-in verifies the password before persisting its session and success audit. Registration stores its final requested scope in the original client creation unit. Browser and device consent hold the pair consent lock around provider consent/code mutations, the device approval's widening of the client's scope ceiling, token narrowing, projection, events, and audit. Grant withdrawal and retirement hold that same lock around the complete cascade. Projection updates merge only the changed fields, preserving concurrent properties.

Token exchange, password change, and client revocation use a lazy persistence phase. Authentication, remote client-key retrieval, and password work precede its first write. The phase retains the actual response until its local persistence tail and audit commit. RFC 7009 acquires its pair lock before the writer. Its provider mutation and Marfa cascade are in the same unit; no after-hook performs a second cascade. Refresh replay deliberately commits its withdrawal and observation before returning an OAuth refusal.

A request tracks every owned adapter promise, including calls the provider does not await. The first persistence/read failure remains sticky even if the provider catches it. Expected transaction callback protocol refusals are not storage failures. Captured request and transaction scopes have an explicit active lifetime; retained adapter calls fail after finalization. A failed commit is never replayed. A positive durable audit witness can settle a lost acknowledgement as committed; an unavailable witness leaves the outcome unknown, suppressing raw credentials, cookies, redirects, and notifications.

## Session termination

An app is not the browser that approved it, so ending a browser session ends that browser and nothing an app holds. The provider binds every access and refresh token to the session that approved it and sweeps the tokens bound to a session whenever one ends. `credential-adapter.ts` therefore stores each created token with no session, so every door that ends a session reaches no app: sign-out, the three revocations, a password change, the provider's end-session and the lookup of an expired session. An authorization code is a different row and stays bound to its browser, so a code is exchanged only while that browser lives, and the ID token a code exchange issues still names the session for the provider's end-session door; one a refresh issues names none.

`session-end-audit.ts` runs the provider's session-deletion hook inside the credential phase, so the session's end and its audit commit together. The provider finds the apps to notify of a session's end through the tokens bound to it, so none is notified: telling an app its person's browser ended would invite it to sign the person out.

Native controls cover caught lookup and deletion failure, a refused audit, and each door above leaving an app's access, refresh and consent in place. These controls also protect password changes and the provider's single, all and other-session revocation endpoints.

The source-resolved storage census is separate: `storage/audit-census.json` accounts for every declared storage method and production mutation call. Its dynamic provider boundary points here. Authentication rate limits, expired-session retention, last-use telemetry, and internal scheduler state retain their documented operational exemptions. Provider device polling changes are audited with their local refusal outcome; a protocol refusal does not imply rollback of an intentional observation.

## Native evidence

Every negative case has a successful control. SQLite triggers reject audit inserts at the real configured handler boundary. The suites assert prior rows, live authority, response/cookie suppression, and retry after a known rollback. Driver-level controls fail before COMMIT or after the native COMMIT, and separately make the audit witness unavailable. `credential-preparation.test.ts` performs the real password algorithms while another writer succeeds; `credential-lifetime.test.ts` holds an actual configured-handler adapter call and rejects a retained callback after finalization.

Key/bootstrap and retention controls are in `key-audit-atomicity.test.ts`, `bootstrap-audit-outcome.test.ts`, and `credential-retention-audit.test.ts`. The audit writer has one awaited API, `AuditStore.log`; there is no swallowed writer, alias, audit tracker, or drain. Publication follows the shared committed-outcome rules.
